# 0. Mục Tiêu

Tài liệu này chỉ có **một** mục tiêu:

> Làm sao biết một implementation là đúng?

Câu trả lời:

```
Run Test Vector

↓

100%

↓

Cyclone Compatible
```

Không phỏng vấn, không đọc code, không tin lời hứa. Chạy test vector và so byte.

---

# 1. Định Nghĩa

## 1.1 Cyclone Compatible

```
Một implementation được gọi là Cyclone Compatible
khi và chỉ khi nó pass 100% test vector trong tài liệu này.
```

Không có "compatible một phần". Không có 98%. Một vector fail nghĩa là tồn tại một dữ liệu mà implementation này và implementation khác bất đồng — và bất đồng đó sẽ xảy ra im lặng trên production.

## 1.2 Test Vector là gì

Test vector là một cặp:

```
(giá trị logic, chuỗi byte)
```

Không phải cặp (lời gọi hàm, kết quả trả về). Vector không nhắc tên method, không nhắc ngôn ngữ, không nhắc API — đúng như tinh thần của RFC-0002.

## 1.3 Bốn phép kiểm

Mỗi vector được dùng theo tối đa bốn chiều:

| Phép kiểm | Nội dung | Kết quả mong đợi |
|-----------|----------|------------------|
| **Encode** | giá trị → byte | Byte giống hệt vector |
| **Decode** | byte → giá trị | Giá trị bằng vector |
| **Round-trip** | giá trị → byte → giá trị | Bằng giá trị ban đầu |
| **Reject** | byte không hợp lệ → decode | MUST bị từ chối |

Vector ở §3–§8 dùng cho ba phép đầu. Vector ở §9 chỉ dùng cho phép thứ tư.

# 2. Quy Tắc Chạy

```
1. Mọi vector MUST pass. Không có ngoại lệ, không có skip.
2. So sánh là so sánh BYTE, không phải so sánh chuỗi hiển thị.
3. Reject vector MUST bị từ chối. Từ chối là bắt buộc, không phải khuyến nghị.
4. Round-trip MUST bằng giá trị gốc, không phải "gần bằng".
```

**Không được** làm những việc sau để cho test pass:

```
✗ Chuẩn hoá NaN về một bit pattern
✗ Sắp xếp lại field
✗ Cắt bớt chuỗi vượt giới hạn
✗ Bỏ qua enum không xác định
✗ Coi "khác 0" là true
```

Mỗi việc trên đều làm test xanh trong một implementation và đỏ khi ghép với implementation khác.

# 4. Float

Float được kiểm theo **bit pattern**, không theo tên giá trị (RFC-0002 §2.3).

## 4.1 f32

| ID | Bit pattern | Giá trị | Byte |
|----|-------------|---------|------|
| F-001 | `0x00000000` | `0.0` | `[00 00 00 00]` |
| F-002 | `0x80000000` | `-0.0` | `[00 00 00 80]` |
| F-003 | `0x3F800000` | `1.0` | `[00 00 80 3F]` |
| F-004 | `0x3FC00000` | `1.5` | `[00 00 C0 3F]` |
| F-005 | `0x4048F5C3` | `3.14` | `[C3 F5 48 40]` |
| F-006 | `0x7F800000` | `+Infinity` | `[00 00 80 7F]` |
| F-007 | `0xFF800000` | `-Infinity` | `[00 00 80 FF]` |

## 4.2 f64

| ID | Bit pattern | Giá trị | Byte |
|----|-------------|---------|------|
| F-020 | `0x0000000000000000` | `0.0` | `[00 00 00 00 00 00 00 00]` |
| F-021 | `0x8000000000000000` | `-0.0` | `[00 00 00 00 00 00 00 80]` |
| F-022 | `0x3FF0000000000000` | `1.0` | `[00 00 00 00 00 00 F0 3F]` |
| F-023 | `0x7FF0000000000000` | `+Infinity` | `[00 00 00 00 00 00 F0 7F]` |

## 4.3 NaN — bit pattern preservation

| ID | Bit pattern vào | Byte | Bit pattern ra |
|----|-----------------|------|----------------|
| F-030 | `0x7FC00000` | `[00 00 C0 7F]` | `0x7FC00000` |
| F-031 | `0x7FC00001` | `[01 00 C0 7F]` | `0x7FC00001` |
| F-032 | `0xFFC00000` | `[00 00 C0 FF]` | `0xFFC00000` |

Cả ba đều là `NaN`. Vector này bắt lỗi implementation **canonical hoá NaN**: nếu F-031 cho ra `[00 00 C0 7F]`, implementation đã sửa dữ liệu của người dùng.

⚠️ Round-trip cho NaN MUST so sánh **bit pattern**, không dùng phép `==` của ngôn ngữ. Trong hầu hết ngôn ngữ `NaN == NaN` cho `false`, dùng nó sẽ fail sai.

## 4.4 Không normalize

| ID | Kiểm tra | Kỳ vọng |
|----|----------|---------|
| F-040 | `0.0` và `-0.0` | Byte **khác nhau** (F-001 ≠ F-002) |
| F-041 | Round-trip `-0.0` | Vẫn là `-0.0`, không thành `0.0` |

# 5. String

`Length` là **số byte UTF-8**, không phải số ký tự.

| ID | Giá trị | Byte |
|----|---------|------|
| S-001 | `""` | `[00 00 00 00]` |
| S-002 | `"abc"` | `[03 00 00 00 61 62 63]` |
| S-003 | `"Alice"` | `[05 00 00 00 41 6C 69 63 65]` |
| S-004 | `"中"` | `[03 00 00 00 E4 B8 AD]` |
| S-005 | `"Xin chào"` | `[09 00 00 00 58 69 6E 20 63 68 C3 A0 6F]` |

**S-004 và S-005 là hai vector quan trọng nhất của mục này.**

```
"中"

1 ký tự
3 byte

↓

Length MUST = 3
```

```
"Xin chào"

8 ký tự
9 byte   (à = C3 A0, 2 byte)

↓

Length MUST = 9
```

Implementation nào ghi `Length = 1` cho S-004 hoặc `Length = 8` cho S-005 là đang đếm **ký tự**. Đây là lỗi phổ biến nhất ở C#, Java và JavaScript.

# 6. Bytes

| ID | Giá trị | Byte |
|----|---------|------|
| B-001 | `[]` | `[00 00 00 00]` |
| B-002 | `[FF FE]` | `[02 00 00 00 FF FE]` |
| B-003 | `[00 00]` | `[02 00 00 00 00 00]` |

B-002 chính là chuỗi byte mà `String` phải **từ chối** (N-020). Cùng byte, khác kiểu, khác kết quả — đó là quyết định schema-level, decoder không suy đoán từ nội dung.

# 7. Array

`Count` là **số phần tử**, không phải số byte.

| ID | Kiểu | Giá trị | Byte |
|----|------|---------|------|
| A-001 | `Array<u32>` | `[]` | `[00 00 00 00]` |
| A-002 | `Array<u32>` | `[1,2,3]` | `[03 00 00 00 01 00 00 00 02 00 00 00 03 00 00 00]` |
| A-003 | `Array<String>` | `["a","bc"]` | `[02 00 00 00 01 00 00 00 61 02 00 00 00 62 63]` |
| A-004 | `Array<Array<u8>>` | `[[1,2],[]]` | `[02 00 00 00 02 00 00 00 01 02 00 00 00 00]` |
| A-005 | `Array<bool>` | `[true,false,true]` | `[03 00 00 00 01 00 01]` |

A-002 bắt lỗi **count vs byte length**: giá trị đúng là `3`, không phải `12`.

A-004 bắt lỗi array lồng nhau: `count = 2`, phần tử đầu `count = 2` + `[01 02]`, phần tử sau `count = 0` và **không có byte nào thêm**.

# 8. Struct & Enum

## 8.1 Struct cơ bản

```
struct Item { id: u32; name: String }
```

| ID | Giá trị | Byte |
|----|---------|------|
| T-001 | `Item{ id=42, name="Sword" }` | `[2A 00 00 00 05 00 00 00 53 77 6F 72 64]` |

## 8.2 Struct rỗng

```
struct Empty { }
```

| ID | Giá trị | Byte |
|----|---------|------|
| T-002 | `Empty{}` | `[]` — **0 byte** |

## 8.3 Struct lồng nhau

```
struct Vector3 { x: f32; y: f32; z: f32 }
struct Body    { pos: Vector3; hp: u32 }
```

| ID | Giá trị | Byte |
|----|---------|------|
| T-003 | `Vector3{1.5, 2.5, 3.5}` | `[00 00 C0 3F 00 00 20 40 00 00 60 40]` |
| T-004 | `Body{ pos=Vector3{1.5,2.5,3.5}, hp=100 }` | `[00 00 C0 3F 00 00 20 40 00 00 60 40 64 00 00 00]` |

Struct lồng được ghi **inline**: không length prefix, không delimiter, không header.

## 8.4 Field ordering — vector quan trọng nhất

```
struct Mixed { a: u8; b: u32; c: u8 }
```

| ID | Giá trị | Byte | Tổng |
|----|---------|------|------|
| T-010 | `Mixed{ a=1, b=2, c=3 }` | `[01 02 00 00 00 03]` | **6 byte** |

Vector này bắt hai lỗi cùng lúc:

```
12 byte              →  implementation đang copy layout bộ nhớ (có padding/alignment)
[02 00 00 00 01 03]  →  compiler đã sắp xếp lại field
```

Thứ tự trên wire là thứ tự **khai báo**, luôn luôn (RFC-0002 §5.1).

```
struct Order { z: u8; a: u8 }
```

| ID | Giá trị | Byte |
|----|---------|------|
| T-011 | `Order{ z=1, a=2 }` | `[01 02]` |

Ra `[02 01]` nghĩa là implementation đang sắp field theo **alphabet**. Đây là lỗi thật, thường gặp khi lấy field từ reflection rồi sort cho "ổn định".

## 8.5 Enum

```
enum PlayerState { Idle=0, Walk=1, Run=2, Jump=3 }
```

| ID | Giá trị | Byte |
|----|---------|------|
| E-001 | `Idle` | `[00 00 00 00]` |
| E-002 | `Walk` | `[01 00 00 00]` |
| E-003 | `Jump` | `[03 00 00 00]` |

| ID | Kiểm tra | Kỳ vọng |
|----|----------|---------|
| E-010 | Kích thước encode của mọi enum | Luôn **4 byte**, không phụ thuộc số lượng member |

E-010 bắt lỗi implementation "tối ưu" enum 4 member thành 1 byte. Enum luôn là `UInt32` — đó là quyết định protocol, không phải tối ưu lưu trữ (RFC-0002 §7).

# 9. Reject Vector

Byte stream dưới đây **MUST** bị từ chối. Đây là nhóm test dễ bị bỏ qua nhất và cũng là nhóm bắt được nhiều bug nhất.

| ID | Kiểu | Byte vào | Vì sao không hợp lệ |
|----|------|----------|---------------------|
| N-001 | `bool` | `[02]` | Không phải `00`/`01` |
| N-002 | `bool` | `[FF]` | Không phải `00`/`01` |
| N-010 | `u32` | `[00 00 00]` | Thiếu byte |
| N-011 | `u64` | `[01 02 03 04]` | Thiếu byte |
| N-020 | `String` | `[02 00 00 00 FF FE]` | Không phải UTF-8 hợp lệ |
| N-021 | `String` | `[03 00 00 00 ED A0 80]` | UTF-8 mã hoá surrogate → không hợp lệ |
| N-022 | `String` | `[05 00 00 00 41 6C 69]` | `Length = 5` nhưng chỉ còn 3 byte |
| N-023 | `String` | `[64 00 00 00 41 6C 69 63 65]` | `Length = 100` nhưng chỉ còn 5 byte |
| N-030 | `Array<u32>` | `[03 00 00 00 01 00 00 00]` | `Count = 3` nhưng chỉ có 1 phần tử |
| N-031 | `Array<u32>` | `[FF FF FF FF]` | `Count = 4294967295` nhưng không còn byte nào |
| N-040 | `enum{0,1}` | `[63 00 00 00]` | Giá trị 99 không nằm trong tập định nghĩa |
| N-041 | `enum{0,1}` | `[02 00 00 00]` | Giá trị 2 không nằm trong tập định nghĩa |

## 9.1 Quy tắc cho Reject Vector

```
Từ chối là MUST.
Tên lỗi là SHOULD.
```

Implementation MUST từ chối. Việc phân loại lỗi (Unexpected EOF / Invalid Bool / Invalid Enum / Invalid UTF-8 / Length Overflow) SHOULD theo RFC-0002 §10, nhưng conformance **không kiểm tra chuỗi thông báo lỗi** — cách báo lỗi nằm ngoài Specification.

## 9.2 N-023 và N-031 — kiểm tra trước khi cấp phát

Hai vector này kiểm đúng một điều: implementation có **kiểm tra length trước khi cấp phát** không.

```
Count = 4294967295

↓

Nếu implementation cấp phát trước rồi mới đọc

↓

Cố cấp phát 16 GB

↓

Out of Memory / Crash
```

Pass N-031 bằng cách "crash rồi bắt exception" **không tính là pass**. Phải từ chối trước khi cấp phát.

# 10. Round-trip

| ID | Kiểm tra |
|----|----------|
| R-001 | Mọi vector ở §3–§8: `value → bytes → value` bằng giá trị gốc |
| R-002 | Mọi vector ở §3–§8: `bytes → value → bytes` bằng byte gốc |
| R-003 | Struct lồng 3 tầng round-trip đúng |
| R-004 | `Array` rỗng round-trip vẫn là `Array` rỗng, không thành `null` |
| R-005 | `String` rỗng round-trip vẫn là `""`, không thành `null` |
| R-006 | `-0.0` round-trip vẫn là `-0.0` |
| R-007 | `NaN` round-trip giữ nguyên bit pattern |

R-004 và R-005 bắt lỗi ngôn ngữ nào coi rỗng là null (hoặc ngược lại). Cyclone không có `null` — rỗng và không tồn tại là hai khái niệm khác nhau, và khái niệm thứ hai không tồn tại trong v1.

# 11. Cross-Implementation

Hai implementation cùng pass §3–§10 vẫn nên kiểm chéo:

| ID | Kiểm tra |
|----|----------|
| X-001 | A encode → B decode → giá trị đúng |
| X-002 | B encode → A decode → giá trị đúng |
| X-003 | A encode và B encode cùng dữ liệu → **byte giống hệt nhau** |

X-003 là phép kiểm mạnh nhất trong toàn bộ tài liệu này. Nó không cần biết A và B viết bằng gì.

Ma trận công bố:

```
          │  Go   │  C#   │ Rust  │  C
──────────┼───────┼───────┼───────┼──────
   Go     │   —   │  ✅   │  ✅   │  ✅
   C#     │  ✅   │   —   │  ✅   │  ✅
   Rust   │  ✅   │  ✅   │   —   │  ✅
   C      │  ✅   │  ✅   │  ✅   │   —
```

# 13. Cái Gì KHÔNG Thuộc Conformance

Conformance chỉ kiểm byte. Những thứ sau **không** được kiểm và **không** được dùng để đánh giá:

| Không kiểm | Vì sao |
|-----------|--------|
| Hình dạng API (`Encode()`, `WriteU32`…) | Specification không quy định API |
| Có generate code hay không | Viết tay vẫn hợp lệ |
| Có dùng annotation hay không | Cách diễn đạt schema là tự do |
| Nội dung chuỗi thông báo lỗi | Cách báo lỗi ngoài Specification |
| Hiệu năng, allocation, throughput | Không đổi hình dạng byte |
| Giá trị `MaxStringLength` mặc định | Giới hạn cấu hình không phải part của protocol |

Một implementation chậm hơn 10 lần nhưng pass 100% vector **vẫn là** Cyclone Compatible. Một implementation nhanh nhất thế giới mà fail một vector thì **không**.
