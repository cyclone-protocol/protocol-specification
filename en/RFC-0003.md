# 0. Objective

This document has only one objective:

> How to know if an implementation is correct?

Answer:

```
Run the Test Vectors

↓

100%

↓

Cyclone Compatibility
```

No interviews, no code review, and no empty promises. Run the test vectors and compare the byte data.

---

# 1. Definition

## 1.1 Cyclone Compatibility

```
An implementation is considered Cyclone Compatible

if and only if it passes 100% of the test vectors in this document.

```

The concept of "partial compatibility" doesn't exist. There's no such thing as achieving 98% compatibility. Just one failed vector means that data from one implementation and another will yield different results - a difference that can be subtle in the production environment.

## 1.2 What is a Test Vector?

A test vector is a pair of values:

```
(logical value, byte string)

```

It's not a pair (function call, return value). This vector doesn't refer to method names, programming languages, or APIs - in keeping with the spirit of RFC-0002.

## 1.3 Five Tests

Each vector is used for up to five test aspects:

| Test | Content | Expected Result |
|-----------|----------|------------------|
| **Encode** | value → byte | Identical byte sequence to vector |
| **Decode** | byte → value | Value equals vector |
| **Round-trip** | value → byte → value | Equals original value |
| **Reject** | invalid byte → decode | MUST be rejected |
| **Compat** | byte read by a different version of Model (RFC-0002 §9.1) → decode | NOT allowed to reject |

The vectors in §3–§8.5 are used for the first three tests. The vectors in §8.6 are used only for the Compatibility test. The vector in §9 is used only for the Reject operation.

---

# 2. Run Rules

```
1. All vectors MUST pass. No exceptions, no skips.
2. Comparison is byte comparison, not string comparison.
3. Rejecting vectors is REQUIRED. Rejection is mandatory, not recommended.
4. The return value MUST equal the original value, not an "approximation".
```

Do not perform the following actions to pass the test:

```
- Normalize NaN to bit pattern
- Rearrange fields
- Ignore undefined enums
- Treat "non-zero" as true

```

Each of these actions will result in a green test in one implementation and a red test when combined with another implementation.

# 4. Float

Float values are checked by bit pattern, not by value name (RFC-0002 §2.3).

## 4.1 f32

| ID | Bit pattern | Value | Byte |
|----|-------------|---------|------|
| F-001 | `0x00000000` | `0.0` | `[00 00 00 00]` |
| F-002 | `0x80000000` | `-0.0` | `[00 00 00 80]` |
| F-003 | `0x3F800000` | `1.0` | `[00 00 80 3F]` |
| F-004 | `0x3FC00000` | `1.5` | `[00 00 C0 3F]` |
| F-005 | `0x4048F5C3` | `3.14` | `[C3 F5 48 40]` |
| F-006 | `0x7F800000` | `+Infinity` | `[00 00 80 7F]` |
| F-007 | `0xFF800000` | `-Infinity` | `[00 00 80 FF]` |

## 4.2 f64

| ID | Bit patterns | Value | Bytes |
|----|-------------|---------|-------|
| F-020 | `0x0000000000000000` | `0.0` | `[00 00 00 00 00 00 00 00]` |
| F-021 | `0x8000000000000000` | `-0.0` | `[00 00 00 00 00 00 00 80]` |
| F-022 | `0x3FF0000000000000` | `1.0` | `[00 00 00 00 00 00 F0 3F]` |
| F-023 | `0x7FF0000000000000` | `+Infinity` | `[00 00 00 00 00 00 F0 7F]` |

## 4.3 NaN - Bit Pattern Preservation

| ID | Bit Pattern Input | Byte | Bit Pattern Output |
|----|-----------------|------|----------------|
| F-030 | `0x7FC00000` | `[00 00 C0 7F]` | `0x7FC00000` |
| F-031 | `0x7FC00001` | `[01 00 C0 7F]` | `0x7FC00001` |
| F-032 | `0xFFC00000` | `[00 00 C0 FF]` | `0xFFC00000` |

All three are `NaN`. This vector catches errors during implementation in NaN normalization: if F-031 outputs `[00 00 C0 7F]`, then the implementation has modified user data.

⚠️ The round-trip conversion for NaN MUST compare bit patterns, not use the language's `==` operator. In most languages, `NaN == NaN` returns `false`, using it will fail.

## 4.4 No Normalization

| ID | Check | Expectation |
|----|----------|---------|
| F-040 | `0.0` and `-0.0` | Different **bytes** (F-001 ≠ F-002) |
| F-041 | Round-trip `-0.0` | Still `-0.0`, not `0.0` |

# 5. String

`Length` is the number of UTF-8 bytes, not the number of characters.

| ID | Value | Byte |
|----|---------|------|
| S-001 | `""` | `[00 00 00 00]` |
| S-002 | `"abc"` | `[03 00 00 00 61 62 63]` |
| S-003 | `"Alice"` | `[05 00 00 00 41 6C 69 63 65]` |
| S-004 | `"中"` | `[03 00 00 00 E4 B8 AD]` |
| S-005 | `"Xin chào"` | `[09 00 00 00 58 69 6E 20 63 68 C3 A0 6F]` |

**S-004 and S-005 are the two most important vectors in this section.**

```
"中"

1 character

3 bytes

↓

Length MUST = 3
```

```
"Xin chào"

8 characters

9 bytes (à = C3 A0, 2 bytes)

↓

Length MUST = 9
```

Any implementation that writes `Length = 1` for S-004 or `Length = 8` for S-005 is counting characters. This is the most common error in C#, Java, and JavaScript.

# 6. Bytes

| ID | Value | Byte |
|----|---------|------|
| B-001 | `[]` | `[00 00 00 00]` |
| B-002 | `[FF FE]` | `[02 00 00 00 FF FE]` |
| B-003 | `[00 00]` | `[02 00 00 00 00 00]` |

B-002 is the byte string that `String` must reject (N-020). Same byte, different type, different result - it's a schema-level decision; the decoder doesn't infer from the content.

# 7. Array

`Count` is the number of elements, not the number of bytes.

| ID | Type | Value | Byte |
|----|------|---------|------|
| A-001 | `Array<u32>` | `[]` | `[00 00 00 00]` |
| A-002 | `Array<u32>` | `[1,2,3]` | `[03 00 00 00 01 00 00 00 02 00 00 00 03 00 00 00]` |
| A-003 | `Array<String>` | `["a","bc"]` | `[02 00 00 00 01 00 00 00 61 02 00 00 00 62 63]` |
| A-004 | `Array<Array<u8>>` | `[[1,2],[]]` | `[02 00 00 00 02 00 00 00 01 02 00 00 00 00]` |
| A-005 | `Array<bool>` | `[true,false,true]` | `[03 00 00 00 01 00 01]` |

Error A-002 detects a count error compared to byte length: the correct value is `3`, not `12`.

Error A-004 detects a nested array error: `count = 2`, the first element `count = 2` + `[01 02]`, the second element `count = 0`, and there are no extra bytes.

# 8. Model & Enum

## 8.1 Basic Model

```
model Item { id: u32; name: String }
```

| ID | Value | Byte |
|----|---------|------|
| T-001 | `Item{ id=42, name="Sword" }` | `[2A 00 00 00 05 00 00 00 53 77 6F 72 64]` |

## 8.2 Empty Model

```
model Empty { }
```

| ID | Value | Byte |
|----|---------|------|
| T-002 | `Empty{}` | `[]` - **0 byte** |

## 8.3 Nested Model

```
model Vector3 { x: f32; y: f32; z: f32 }
model Body    { pos: Vector3; hp: u32 }
```

| ID | Value | Byte |
|----|---------|------|
| T-003 | `Vector3{1.5, 2.5, 3.5}` | `[00 00 C0 3F 00 00 20 40 00 00 60 40]` |
| T-004 | `Body{ pos=Vector3{1.5,2.5,3.5}, hp=100 }` | `[00 00 C0 3F 00 00 20 40 00 00 60 40 64 00 00 00]` |

Nested models are written inline: no length prefix, no delimiter, no header.

## 8.4 Field Order - Most Important Vector

```
Model Mixed { a: u8; b: u32; c: u8 }
```

| ID | Value | Byte | Total |
|----|---------|------|------|
| T-010 | `Mixed{ a=1, b=2, c=3 }` | `[01 02 00 00 00 03]` | **6 bytes** |

This vector catches two errors at once:

```
12 bytes → compiler is copying memory layout (padding/aligning)

[02 00 00 00 01 03] → compiler has rearranged the field
```

The order on the transmission line is the declared order, always (RFC-0002 §5.1).

```
model Order { z: u8; a: u8 }
```

| ID | Value | Byte |
|----|---------|------|
| T-011 | `Order{ z=1, a=2 }` | `[01 02]` |

Error `[02 01]` means the compiler is sorting the field alphabetically. This is a real error, often encountered when retrieving fields from reflection and then sorting them for "stable".

## 8.5 Enum

```
enum PlayerState { Idle=0, Walk=1, Run=2, Jump=3 }

```

| ID | Value | Byte |
|----|---------|------|
| E-001 | `Idle` | `[00 00 00 00]` |
| E-002 | `Walk` | `[01 00 00 00]` |
| E-003 | `Jump` | `[03 00 00 00]` |

| ID | Check | Expect |
|----|----------|---------|
| E-010 | Encoding the size of each enum | Always 4 bytes, regardless of the number of members |

E-010 catches an implementation error that "optimizes" a 4-member enum to 1 byte. The enum is always `UInt32` - this is a protocol decision, not storage optimization (RFC-0002 §7).

## 8.6 Differences between versions

```
model ItemV1 { id: u32 }
model ItemV2 { id: u32; name: String }
```

| ID | Write model | Read model | Byte | Expectation |
|----|-----------|-----------|------|---------|
| V-001 | ItemV1 | ItemV2 | `[2A 00 00 00]` | MUST NOT be rejected; `id=42`, `name` has no data |
| V-002 | ItemV2 | ItemV1 | `[2A 00 00 00 05 00 00 00 53 77 6F 72 64]` | MUST NOT be rejected; `id=42`, 9 extra bytes ignored |

V-001 and V-002 are compatible vectors (§1.3): only valid when the missing or extra bytes are exactly within the field boundary, not in the middle of the field.

Compare with N-022: both are "missing bytes", but N-022 is missing a byte in the middle of the `String` field (length read, data not fully read), so it MUST be rejected. Confusing these two cases – treating any Model that reads missing/extra bytes as a version difference, even if it's in the middle of the field – is the most common compliance error when adding version difference support (RFC-0002 §9.1).

# 9. Reject Vector

The stream of bytes below MUST be rejected. This is the most easily overlooked test group and also the group that detects the most errors.

| ID | Type | Input Byte | Reason Invalid |
|----|----------|--------|-------------|
| N-001 | `bool` | `[02]` | Not `00`/`01` |
| N-002 | `bool` | `[FF]` | Not `00`/`01` |
| N-010 | `u32` | `[00 00 00]` | Missing byte |
| N-011 | `u64` | `[01 02 03 04]` | Missing byte |
| N-020 | `String` | `[02 00 00 00 FF FE]` | Not valid UTF-8 |
| N-021 | `String` | `[03 00 00 00 ED A0 80]` | UTF-8 substitution encoding → invalid |
| N-022 | `String` | `[05 00 00 00 41 6C 69]` | `Length = 5` but only 3 bytes remain |
| N-023 | `String` | `[64 00 00 00 41 6C 69 63 65]` | `Length = 100` but only 5 bytes remain |
| N-030 | `Array<u32>` | `[03 00 00 00 01 00 00 00]` | `Count = 3` but only 1 element remains |
| N-031 | `Array<u32>` | `[FF FF FF FF]` | `Count = 4294967295` but no bytes remain |
| N-040 | `enum{0,1}` | `[63 00 00 00]` | Value 99 is not in the definition set |
| N-041 | `enum{0,1}` | `[02 00 00 00]` | The value 2 is not in the definition set |

---

## 9.1 Vector Rejection Rules

```
Rejection is MANDATORY.
```
The implementation MUST be rejected. Error classification (unexpected EOF / invalid Boolean / invalid Enum / invalid UTF-8 / length overflow) SHOULD follow RFC-0002 §10, but compliance does not check the error message string - the error reporting method is outside the Specification.

## 9.2 N-023 and N-031 - Pre-allocation checks

These two vectors check exactly one thing: whether the implementation checks the length before allocation.

```
Number of times = 4294967295

↓

If the implementation allocates first and then reads

↓

Attempting to allocate 16 GB

↓

Out of memory / Program crash
```

Passing N-031 by "causing a program crash and catching an exception" is not counted as passing. It must be rejected before allocation.

# 10. round-trip

| ID | Check |
|----|----------|
| R-001 | Each vector in §3–§8: `value → byte → value` equals the original value |
| R-002 | Each vector in §3–§8: `byte → value → byte` equals the original byte |
| R-003 | The nested 3-layer round-trip pattern is correct |
| R-004 | An empty `Array` remains an empty `Array` in a round-trip, not a `null` |
| R-005 | An empty `String` remains a `""` in a round-trip, not a `null` |
| R-006 | A `-0.0` remains a `-0.0` in a round-trip |
| R-007 | The value `NaN` retains the bit pattern during round-trip transmission |

R-004 and R-005 catch errors where languages treat empty values as null (or vice versa). Cyclone has no `null` - empty and non-existent are two different concepts, and the latter does not exist in version v1.1.

# 12. Conformance Report

Two implementations that pass §3–§10 still need to be cross-checked:

| ID | Check |
|----|----------|
| X-001 | A encodes → B decodes → true value |
| X-002 | B encodes → A decodes → true value |
| X-003 | A encodes and B encode the same data → identical bytes |

X-003 is the most rigorous check in this entire document. It doesn't need to know which language A and B are written in.

# 13. Elements NOT within the scope of compliance testing

Compliance testing focuses only on byte representation. The following aspects are not tested and are not used for evaluation:

| Element not tested | Reason |
|-----------|--------|
| API structure (`Encode()`, `WriteU32`…) | Specification does not require the use of a specific API |
| Whether the source code is automatically generated | Handwritten source code is still valid |
| Use of annotations | Flexible schema representation |
| Error message content | Error reporting mechanism outside the scope of the specification |
| Performance, memory allocation, throughput | These factors do not change the byte representation |
| Default value of `MaxStringLength` | Configuration limitations are not within the scope of the protocol |

An implementation that runs 10 times slower but passes 100% of the test vectors is still considered compatible with Cyclone. Conversely, the fastest implementation in the world that fails even one test vector is not considered compatible.
