# 0. Goal

This document has exactly **one** goal:

> How do I know an implementation is correct?

The answer:

```
Run Test Vectors

↓

100%

↓

Cyclone Compatible
```

No interviews, no code reading, no trusting promises. Run the test vectors and compare bytes.

---

# 1. Definitions

## 1.1 Cyclone Compatible

```
An implementation is called Cyclone Compatible
if and only if it passes 100% of the test vectors in this document.
```

There is no "partially compatible". There is no 98%. One failing vector means there exists data on which this implementation and another disagree — and that disagreement will happen silently in production.

## 1.2 What a test vector is

A test vector is a pair:

```
(logical value, byte sequence)
```

Not a pair of (function call, return value). A vector never names a method, a language, or an API — exactly in the spirit of RFC-0002.

## 1.3 Four checks

Each vector is used along up to four axes:

| Check | Content | Expected result |
|-------|---------|-----------------|
| **Encode** | value → bytes | Bytes identical to the vector |
| **Decode** | bytes → value | Value equals the vector |
| **Round-trip** | value → bytes → value | Equals the original value |
| **Reject** | invalid bytes → decode | MUST be rejected |

Vectors in §3–§8 are used for the first three checks. Vectors in §9 are used only for the fourth.

---

# 2. Running Rules

```
1. Every vector MUST pass. No exceptions, no skips.
2. Comparison is a BYTE comparison, not a display-string comparison.
3. Reject vectors MUST be rejected. Rejection is mandatory, not a recommendation.
4. Round-trip MUST equal the original value, not "approximately equal".
```

You **must not** do any of the following to make a test pass:

```
✗ Canonicalize NaN to one bit pattern
✗ Reorder fields
✗ Truncate strings that exceed a limit
✗ Ignore undefined enum values
✗ Treat "non-zero" as true
```

Each of these turns a test green in one implementation and red the moment it meets another.

# 4. Float

Floats are checked by **bit pattern**, not by value name (RFC-0002 §2.3).

## 4.1 f32

| ID | Bit pattern | Value | Bytes |
|----|-------------|-------|-------|
| F-001 | `0x00000000` | `0.0` | `[00 00 00 00]` |
| F-002 | `0x80000000` | `-0.0` | `[00 00 00 80]` |
| F-003 | `0x3F800000` | `1.0` | `[00 00 80 3F]` |
| F-004 | `0x3FC00000` | `1.5` | `[00 00 C0 3F]` |
| F-005 | `0x4048F5C3` | `3.14` | `[C3 F5 48 40]` |
| F-006 | `0x7F800000` | `+Infinity` | `[00 00 80 7F]` |
| F-007 | `0xFF800000` | `-Infinity` | `[00 00 80 FF]` |

## 4.2 f64

| ID | Bit pattern | Value | Bytes |
|----|-------------|-------|-------|
| F-020 | `0x0000000000000000` | `0.0` | `[00 00 00 00 00 00 00 00]` |
| F-021 | `0x8000000000000000` | `-0.0` | `[00 00 00 00 00 00 00 80]` |
| F-022 | `0x3FF0000000000000` | `1.0` | `[00 00 00 00 00 00 F0 3F]` |
| F-023 | `0x7FF0000000000000` | `+Infinity` | `[00 00 00 00 00 00 F0 7F]` |

## 4.3 NaN — bit pattern preservation

| ID | Bit pattern in | Bytes | Bit pattern out |
|----|----------------|-------|-----------------|
| F-030 | `0x7FC00000` | `[00 00 C0 7F]` | `0x7FC00000` |
| F-031 | `0x7FC00001` | `[01 00 C0 7F]` | `0x7FC00001` |
| F-032 | `0xFFC00000` | `[00 00 C0 FF]` | `0xFFC00000` |

All three are `NaN`. These vectors catch implementations that **canonicalize NaN**: if F-031 produces `[00 00 C0 7F]`, the implementation has modified user data.

⚠️ Round-trip for NaN MUST compare **bit patterns**, not the language's `==` operator. In most languages `NaN == NaN` is `false`, and using it will fail incorrectly.

## 4.4 No normalization

| ID | Check | Expectation |
|----|-------|-------------|
| F-040 | `0.0` and `-0.0` | Bytes **differ** (F-001 ≠ F-002) |
| F-041 | Round-trip `-0.0` | Still `-0.0`, not turned into `0.0` |

# 5. String

`Length` is the **number of UTF-8 bytes**, not the number of characters.

| ID | Value | Bytes |
|----|-------|-------|
| S-001 | `""` | `[00 00 00 00]` |
| S-002 | `"abc"` | `[03 00 00 00 61 62 63]` |
| S-003 | `"Alice"` | `[05 00 00 00 41 6C 69 63 65]` |
| S-004 | `"中"` | `[03 00 00 00 E4 B8 AD]` |
| S-005 | `"Xin chào"` | `[09 00 00 00 58 69 6E 20 63 68 C3 A0 6F]` |

**S-004 and S-005 are the two most important vectors in this section.**

```
"中"

1 character
3 bytes

↓

Length MUST = 3
```

```
"Xin chào"

8 characters
9 bytes   (à = C3 A0, 2 bytes)

↓

Length MUST = 9
```

An implementation that writes `Length = 1` for S-004 or `Length = 8` for S-005 is counting **characters**. This is the most common bug in C#, Java and JavaScript.

# 6. Bytes

| ID | Value | Bytes |
|----|-------|-------|
| B-001 | `[]` | `[00 00 00 00]` |
| B-002 | `[FF FE]` | `[02 00 00 00 FF FE]` |
| B-003 | `[00 00]` | `[02 00 00 00 00 00]` |

B-002 is exactly the byte sequence that `String` must **reject** (N-020). Same bytes, different type, different outcome — that is a schema-level decision; the decoder never infers it from content.

# 7. Array

`Count` is the **number of elements**, not the number of bytes.

| ID | Type | Value | Bytes |
|----|------|-------|-------|
| A-001 | `Array<u32>` | `[]` | `[00 00 00 00]` |
| A-002 | `Array<u32>` | `[1,2,3]` | `[03 00 00 00 01 00 00 00 02 00 00 00 03 00 00 00]` |
| A-003 | `Array<String>` | `["a","bc"]` | `[02 00 00 00 01 00 00 00 61 02 00 00 00 62 63]` |
| A-004 | `Array<Array<u8>>` | `[[1,2],[]]` | `[02 00 00 00 02 00 00 00 01 02 00 00 00 00]` |
| A-005 | `Array<bool>` | `[true,false,true]` | `[03 00 00 00 01 00 01]` |

A-002 catches the **count vs. byte length** bug: the correct value is `3`, not `12`.

A-004 catches nested-array bugs: `count = 2`, the first element is `count = 2` + `[01 02]`, the second is `count = 0` and **no further bytes**.

# 8. Struct & Enum

## 8.1 Basic struct

```
struct Item { id: u32; name: String }
```

| ID | Value | Bytes |
|----|-------|-------|
| T-001 | `Item{ id=42, name="Sword" }` | `[2A 00 00 00 05 00 00 00 53 77 6F 72 64]` |

## 8.2 Empty struct

```
struct Empty { }
```

| ID | Value | Bytes |
|----|-------|-------|
| T-002 | `Empty{}` | `[]` — **0 bytes** |

## 8.3 Nested struct

```
struct Vector3 { x: f32; y: f32; z: f32 }
struct Body    { pos: Vector3; hp: u32 }
```

| ID | Value | Bytes |
|----|-------|-------|
| T-003 | `Vector3{1.5, 2.5, 3.5}` | `[00 00 C0 3F 00 00 20 40 00 00 60 40]` |
| T-004 | `Body{ pos=Vector3{1.5,2.5,3.5}, hp=100 }` | `[00 00 C0 3F 00 00 20 40 00 00 60 40 64 00 00 00]` |

Nested structs are written **inline**: no length prefix, no delimiter, no header.

## 8.4 Field ordering — the most important vector

```
struct Mixed { a: u8; b: u32; c: u8 }
```

| ID | Value | Bytes | Total |
|----|-------|-------|-------|
| T-010 | `Mixed{ a=1, b=2, c=3 }` | `[01 02 00 00 00 03]` | **6 bytes** |

This vector catches two bugs at once:

```
12 bytes             →  the implementation is copying memory layout (padding/alignment)
[02 00 00 00 01 03]  →  the compiler reordered the fields
```

Wire order is **declaration** order, always (RFC-0002 §5.1).

```
struct Order { z: u8; a: u8 }
```

| ID | Value | Bytes |
|----|-------|-------|
| T-011 | `Order{ z=1, a=2 }` | `[01 02]` |

Producing `[02 01]` means the implementation is sorting fields **alphabetically**. This is a real bug, common when fields come from reflection and are then sorted "for stability".

## 8.5 Enum

```
enum PlayerState { Idle=0, Walk=1, Run=2, Jump=3 }
```

| ID | Value | Bytes |
|----|-------|-------|
| E-001 | `Idle` | `[00 00 00 00]` |
| E-002 | `Walk` | `[01 00 00 00]` |
| E-003 | `Jump` | `[03 00 00 00]` |

| ID | Check | Expectation |
|----|-------|-------------|
| E-010 | Encoded size of every enum | Always **4 bytes**, regardless of member count |

E-010 catches implementations that "optimize" a 4-member enum into 1 byte. An enum is always `UInt32` — a protocol decision, not a storage optimization (RFC-0002 §7).

# 9. Reject Vectors

The byte streams below **MUST** be rejected. This is the most commonly skipped group of tests, and the one that catches the most bugs.

| ID | Type | Input bytes | Why invalid |
|----|------|-------------|-------------|
| N-001 | `bool` | `[02]` | Not `00`/`01` |
| N-002 | `bool` | `[FF]` | Not `00`/`01` |
| N-010 | `u32` | `[00 00 00]` | Missing bytes |
| N-011 | `u64` | `[01 02 03 04]` | Missing bytes |
| N-020 | `String` | `[02 00 00 00 FF FE]` | Not valid UTF-8 |
| N-021 | `String` | `[03 00 00 00 ED A0 80]` | UTF-8-encoded surrogate → invalid |
| N-022 | `String` | `[05 00 00 00 41 6C 69]` | `Length = 5` but only 3 bytes remain |
| N-023 | `String` | `[64 00 00 00 41 6C 69 63 65]` | `Length = 100` but only 5 bytes remain |
| N-030 | `Array<u32>` | `[03 00 00 00 01 00 00 00]` | `Count = 3` but only 1 element present |
| N-031 | `Array<u32>` | `[FF FF FF FF]` | `Count = 4294967295` but no bytes remain |
| N-040 | `enum{0,1}` | `[63 00 00 00]` | Value 99 is not in the defined set |
| N-041 | `enum{0,1}` | `[02 00 00 00]` | Value 2 is not in the defined set |

## 9.1 Rules for Reject Vectors

```
Rejection is MUST.
The error name is SHOULD.
```

An implementation MUST reject. Classifying the error (Unexpected EOF / Invalid Bool / Invalid Enum / Invalid UTF-8 / Length Overflow) SHOULD follow RFC-0002 §10, but conformance **does not check error message strings** — how errors are reported is outside the Specification.

## 9.2 N-023 and N-031 — check before allocating

These two vectors check exactly one thing: does the implementation **validate length before allocating**?

```
Count = 4294967295

↓

If the implementation allocates first and reads after

↓

Attempts to allocate 16 GB

↓

Out of Memory / Crash
```

Passing N-031 by "crashing and catching the exception" **does not count as a pass**. It must be rejected before allocation.

# 10. Round-trip

| ID | Check |
|----|-------|
| R-001 | Every vector in §3–§8: `value → bytes → value` equals the original value |
| R-002 | Every vector in §3–§8: `bytes → value → bytes` equals the original bytes |
| R-003 | A 3-level nested struct round-trips correctly |
| R-004 | An empty `Array` round-trips as an empty `Array`, not `null` |
| R-005 | An empty `String` round-trips as `""`, not `null` |
| R-006 | `-0.0` round-trips as `-0.0` |
| R-007 | `NaN` round-trips with its bit pattern preserved |

R-004 and R-005 catch languages that treat empty as null (or the reverse). Cyclone has no `null` — empty and absent are two different concepts, and the second one does not exist in v1.

# 11. Cross-Implementation

Two implementations that both pass §3–§10 should still be cross-checked:

| ID | Check |
|----|-------|
| X-001 | A encodes → B decodes → correct value |
| X-002 | B encodes → A decodes → correct value |
| X-003 | A and B encode the same data → **byte-identical output** |

X-003 is the strongest check in this entire document. It does not need to know what A and B are written in.

Published matrix:

```
          │  Go   │  C#   │ Rust  │  C
──────────┼───────┼───────┼───────┼──────

   C#     │  ✅   │   —   │  ✅   │  ✅
   Rust   │  ✅   │  ✅   │   —   │  ✅
   C      │  ✅   │  ✅   │  ✅   │   —
```

# 12. Conformance Report

An implementation publishes its results in this format:

```
Implementation : cyclone-go
Version        : 0.3.1
Spec           : RFC-0002 v1

§3  Primitives       ✅  28/28
§4  Float            ✅  16/16
§5  String           ✅   5/5
§6  Bytes            ✅   3/3
§7  Array            ✅   5/5
§8  Struct & Enum    ✅   9/9
§9  Reject           ✅  12/12
§10 Round-trip       ✅   7/7
§11 Cross-impl       ⚠️  not yet checked against another implementation

Conclusion: Cyclone Compatible
```

A single ❌ anywhere in §3–§10:

```
Conclusion: NOT Cyclone Compatible
```

There is no intermediate state.

# 13. What Is NOT Part Of Conformance

Conformance checks bytes only. The following are **not** checked and **must not** be used to judge an implementation:

| Not checked | Why |
|-------------|-----|
| API shape (`Encode()`, `WriteU32`…) | The Specification does not mandate an API |
| Whether code is generated | Handwritten is equally valid |
| Whether annotations are used | How the schema is expressed is free |
| Error message strings | Error reporting is outside the Specification |
| Performance, allocations, throughput | They do not change the byte shape |
| The default value of `MaxStringLength` | Configured limits are not part of the protocol |

An implementation 10× slower that passes 100% of the vectors **is** Cyclone Compatible. The fastest implementation in the world that fails one vector **is not**.
