# RFC-0003 - Conformance

## Status

Final

## Version

1.1.0

## Author

Ha Duy Thang

---

# 0. Goal

This document answers one question:

> How do I know whether an implementation is correct?

The answer:

```
Run the test vectors

↓

100%

↓

Fomoxa Compatible
```

The evaluation does not rely on interviews, code review or the author's assurances. It relies only on running the test vectors and comparing bytes.

---

# 1. Definitions

## 1.1 Fomoxa Compatible

```
An implementation is Fomoxa Compatible
if and only if it passes 100% of the test vectors in this document.
```

There is no "partially compatible" level such as 98%. One failed vector means there is data on which this implementation and another implementation disagree, and that divergence happens silently in production.

## 1.2 What is a test vector?

A test vector is a pair:

```
(logical value, byte sequence)
```

It is not a pair of (function call, return value). Like RFC-0002, a vector names no method, language or API.

## 1.3 Five checks

Each vector serves up to five checks:

| Check | Content | Expected result |
|-----------|----------|------------------|
| Encode | value → bytes | Bytes identical to the vector |
| Decode | bytes → value | Value equals the vector |
| Round-trip | value → bytes → value | Equals the original value |
| Reject | invalid bytes → decode | MUST be rejected |
| Compat | bytes read by a different Model version (RFC-0002 §9.1) → decode | MUST NOT be rejected |

Vectors in §3–§8.5 serve the first three checks. Vectors in §8.6 serve Compat only. Vectors in §9 serve Reject only.

---

# 2. Execution rules

```
1. Every vector MUST pass. No exceptions, no skips.
2. Comparison is byte comparison, not string comparison.
3. Reject vectors MUST be rejected; this is not a recommendation.
4. Returned values MUST equal the originals, never "approximately".
```

Do not do any of the following to pass:

```
- Normalize NaN bit patterns
- Reorder fields
- Ignore unknown enums
- Treat "non-zero as true"
```

Each of those makes a test pass in one implementation and fail when cross-tested against another.

# 4. Float

Floats are tested by bit pattern, never by value name (RFC-0002 §2.3).

## 4.1 f32

| ID | Bit pattern | Value | Bytes |
|----|-------------|---------|------|
| F-001 | `0x00000000` | `0.0` | `[00 00 00 00]` |
| F-002 | `0x80000000` | `-0.0` | `[00 00 00 80]` |
| F-003 | `0x3F800000` | `1.0` | `[00 00 80 3F]` |
| F-004 | `0x3FC00000` | `1.5` | `[00 00 C0 3F]` |
| F-005 | `0x4048F5C3` | `3.14` | `[C3 F5 48 40]` |
| F-006 | `0x7F800000` | `+Infinity` | `[00 00 80 7F]` |
| F-007 | `0xFF800000` | `-Infinity` | `[00 00 80 FF]` |

## 4.2 f64

| ID | Bit pattern | Value | Bytes |
|----|-------------|---------|------|
| F-020 | `0x0000000000000000` | `0.0` | `[00 00 00 00 00 00 00 00]` |
| F-021 | `0x8000000000000000` | `-0.0` | `[00 00 00 00 00 00 00 80]` |
| F-022 | `0x3FF0000000000000` | `1.0` | `[00 00 00 00 00 00 F0 3F]` |
| F-023 | `0x7FF0000000000000` | `+Infinity` | `[00 00 00 00 00 00 F0 7F]` |

## 4.3 NaN: bit pattern preservation

| ID | Bit pattern in | Bytes | Bit pattern out |
|----|-----------------|------|----------------|
| F-030 | `0x7FC00000` | `[00 00 C0 7F]` | `0x7FC00000` |
| F-031 | `0x7FC00001` | `[01 00 C0 7F]` | `0x7FC00001` |
| F-032 | `0xFFC00000` | `[00 00 C0 FF]` | `0xFFC00000` |

All three are `NaN`. This group detects NaN normalization: if F-031 emits `[00 00 C0 7F]`, the implementation has modified user data.

A NaN round-trip MUST compare bit patterns, never the language `==` operator. In most languages `NaN == NaN` returns `false`, so a comparison with `==` always fails.

## 4.4 No normalization

| ID | Check | Expected |
|----|----------|---------|
| F-040 | `0.0` and `-0.0` | Different bytes (F-001 ≠ F-002) |
| F-041 | Round-trip `-0.0` | Still `-0.0`, never `0.0` |

# 5. String

`Length` is the UTF-8 byte count, not the character count.

| ID | Value | Bytes |
|----|---------|------|
| S-001 | `""` | `[00 00 00 00]` |
| S-002 | `"abc"` | `[03 00 00 00 61 62 63]` |
| S-003 | `"Alice"` | `[05 00 00 00 41 6C 69 63 65]` |
| S-004 | `"中"` | `[03 00 00 00 E4 B8 AD]` |
| S-005 | `"Xin chào"` | `[09 00 00 00 58 69 6E 20 63 68 C3 A0 6F]` |

S-004 and S-005 check that the length counts bytes, not characters.

```
"中"

1 character
3 bytes

↓

Length MUST = 3
```

```
"Xin chào"

8 characters
9 bytes   (à = C3 A0, 2 bytes)

↓

Length MUST = 9
```

An implementation writing `Length = 1` for S-004 or `Length = 8` for S-005 is counting characters, which is the most common bug in C#, Java and JavaScript.

# 6. Bytes

| ID | Value | Bytes |
|----|---------|------|
| B-001 | `[]` | `[00 00 00 00]` |
| B-002 | `[FF FE]` | `[02 00 00 00 FF FE]` |
| B-003 | `[00 00]` | `[02 00 00 00 00 00]` |

B-002 is the exact byte sequence a `String` must reject (N-020). The same bytes produce a different outcome depending on the type. The type is decided at the schema layer; the decoder never infers it from content.

---

# 7. Array

`Count` is the element count, not the byte count.

| ID | Type | Value | Bytes |
|----|------|---------|------|
| A-001 | `Array<u32>` | `[]` | `[00 00 00 00]` |
| A-002 | `Array<u32>` | `[1,2,3]` | `[03 00 00 00 01 00 00 00 02 00 00 00 03 00 00 00]` |
| A-003 | `Array<String>` | `["a","bc"]` | `[02 00 00 00 01 00 00 00 61 02 00 00 00 62 63]` |
| A-004 | `Array<Array<u8>>` | `[[1,2],[]]` | `[02 00 00 00 02 00 00 00 01 02 00 00 00 00]` |
| A-005 | `Array<bool>` | `[true,false,true]` | `[03 00 00 00 01 00 01]` |

A-002 detects element count confused with byte length. The correct value is `3`, not `12`.

A-004 checks nested arrays: `count = 2`, first element `count = 2` + `[01 02]`, second element `count = 0` with no surplus bytes.

# 8. Model & Enum

## 8.1 Basic Model

```
model Item { id: u32; name: String }
```

| ID | Value | Bytes |
|----|---------|------|
| T-001 | `Item{ id=42, name="Sword" }` | `[2A 00 00 00 05 00 00 00 53 77 6F 72 64]` |

## 8.2 Empty Model

```
model Empty { }
```

| ID | Value | Bytes |
|----|---------|------|
| T-002 | `Empty{}` | `[]` - 0 bytes |

## 8.3 Nested Model

```
model Vector3 { x: f32; y: f32; z: f32 }
model Body    { pos: Vector3; hp: u32 }
```

| ID | Value | Bytes |
|----|---------|------|
| T-003 | `Vector3{1.5, 2.5, 3.5}` | `[00 00 C0 3F 00 00 20 40 00 00 60 40]` |
| T-004 | `Body{ pos=Vector3{1.5,2.5,3.5}, hp=100 }` | `[00 00 C0 3F 00 00 20 40 00 00 60 40 64 00 00 00]` |

Nested Models are written inline: no length prefix, no delimiter, no header.

## 8.4 Field order

```
model Mixed { a: u8; b: u32; c: u8 }
```

| ID | Value | Bytes | Total |
|----|---------|------|------|
| T-010 | `Mixed{ a=1, b=2, c=3 }` | `[01 02 00 00 00 03]` | 6 bytes |

This vector detects two bugs at once:

```
12 bytes → the implementation is copying the memory layout (padding/alignment)

[02 00 00 00 01 03] → the implementation reordered the fields
```

Wire order is always declaration order (RFC-0002 §5.1).

```
model Order { z: u8; a: u8 }
```

| ID | Value | Bytes |
|----|---------|------|
| T-011 | `Order{ z=1, a=2 }` | `[01 02]` |

An output of `[02 01]` means the implementation sorts fields alphabetically. This bug appears when fields are pulled by reflection and then sorted "for stability".

## 8.5 Enum

```
enum PlayerState { Idle=0, Walk=1, Run=2, Jump=3 }
```

| ID | Value | Bytes |
|----|---------|------|
| E-001 | `Idle` | `[00 00 00 00]` |
| E-002 | `Walk` | `[01 00 00 00]` |
| E-003 | `Jump` | `[03 00 00 00]` |

| ID | Check | Expected |
|----|----------|---------|
| E-010 | Encoded size of every enum | Always 4 bytes, regardless of member count |

E-010 detects an implementation that "optimizes" a 4-member enum down to 1 byte. Enums are always `UInt32`, by the protocol decision in RFC-0002 §7.

## 8.6 Version skew

```
model ItemV1 { id: u32 }
model ItemV2 { id: u32; name: String }
```

| ID | Writer Model | Reader Model | Bytes | Expected |
|----|-----------|-----------|------|---------|
| V-001 | ItemV1 | ItemV2 | `[2A 00 00 00]` | MUST NOT be rejected; `id=42`, `name` has no data |
| V-002 | ItemV2 | ItemV1 | `[2A 00 00 00 05 00 00 00 53 77 6F 72 64]` | MUST NOT be rejected; `id=42`, 9 surplus bytes ignored |

V-001 and V-002 are Compat vectors (§1.3). They are valid only when the missing or surplus bytes land exactly on a field boundary, never inside a field.

Compare with N-022: both are "missing bytes", but N-022 loses bytes inside a `String` field (length read, data incomplete), so it MUST be rejected. Confusing the two cases is the most common conformance bug when adding version skew support (RFC-0002 §9.1).

# 9. Reject vectors

The byte streams below MUST be rejected. Implementations skip this group most often, and it detects the most bugs.

| ID | Type | Input bytes | Reason it is invalid |
|----|----------|----------|-----------|
| N-001 | `bool` | `[02]` | Not `00`/`01` |
| N-002 | `bool` | `[FF]` | Not `00`/`01` |
| N-010 | `u32` | `[00 00 00]` | Missing bytes |
| N-011 | `u64` | `[01 02 03 04]` | Missing bytes |
| N-020 | `String` | `[02 00 00 00 FF FE]` | Not valid UTF-8 |
| N-021 | `String` | `[03 00 00 00 ED A0 80]` | UTF-8 surrogate → invalid |
| N-022 | `String` | `[05 00 00 00 41 6C 69]` | `Length = 5` but only 3 bytes remain |
| N-023 | `String` | `[64 00 00 00 41 6C 69 63 65]` | `Length = 100` but only 5 bytes remain |
| N-030 | `Array<u32>` | `[03 00 00 00 01 00 00 00]` | `Count = 3` but only 1 element remains |
| N-031 | `Array<u32>` | `[FF FF FF FF]` | `Count = 4294967295` but no bytes remain |
| N-040 | `enum{0,1}` | `[63 00 00 00]` | Value 99 is outside the defined set |
| N-041 | `enum{0,1}` | `[02 00 00 00]` | Value 2 is outside the defined set |

## 9.1 Reject vector rules

```
Rejection is MANDATORY.
```

Implementations MUST reject. Error classification (unexpected EOF / invalid bool / invalid enum / invalid UTF-8 / length overflow) SHOULD follow RFC-0002 §10. Conformance does not test error message strings, because error reporting falls outside the Specification.

## 9.2 N-023 and N-031: check before allocating

These two vectors test whether the implementation checks length before allocating.

```
Count = 4294967295

↓

If the implementation allocates before reading

↓

It attempts a 16 GB allocation

↓

Out of memory / crash
```

Crashing and catching the exception does not count as passing N-031; the byte stream MUST be rejected before allocation.

# 10. Round-trip

| ID | Check |
|----|----------|
| R-001 | Every vector in §3–§8: `value → bytes → value` equals the original value |
| R-002 | Every vector in §3–§8: `bytes → value → bytes` equals the original bytes |
| R-003 | A 3-level nested Model round-trips exactly |
| R-004 | An empty `Array` stays an empty `Array` after round-trip, never `null` |
| R-005 | An empty `String` stays `""` after round-trip, never `null` |
| R-006 | `-0.0` stays `-0.0` after round-trip |
| R-007 | `NaN` keeps its bit pattern after round-trip |

R-004 and R-005 detect languages that turn empty values into null, or the reverse. Fomoxa has no `null`. Empty and absent are two different concepts, and the second does not exist in v1.1.

# 11. Cross-implementation testing

Two implementations that both pass §3–§10 still need cross-testing:

| ID | Check |
|----|----------|
| X-001 | A encodes → B decodes → correct value |
| X-002 | B encodes → A decodes → correct value |
| X-003 | A and B encode the same data → identical bytes |

X-003 is the strictest check in this document and does not depend on the languages A and B are written in.

Result matrix:

| --- | Go | C# | Rust | C |
|----|----|----|----|----|
| Go | - | ✅ | ✅ | ✅ |
| C# | ✅ | - | ✅ | ✅ |
| Rust | ✅ | ✅ | - | ✅ |
| C | ✅ | ✅ | ✅ | - |

# 12. Conformance report

An implementation publishes its results in this form:

```
Implementation: fomoxa-go
Version: 0.3.1
Spec: RFC-0002 v1.1

§3  Primitive        ✅  27/27
§4  Float            ✅  16/16
§5  String           ✅   5/5
§6  Bytes            ✅   3/3
§7  Array            ✅   5/5
§8  Model & Enum     ✅  12/12
§9  Reject           ✅  12/12
§10 Round-trip       ✅   7/7
§11 Cross-impl       ⚠️  not yet tested against another implementation

Conclusion: Fomoxa Compatible
```

If any line in §3–§10 shows ❌:

```
Conclusion: NOT Fomoxa Compatible
```

There is no intermediate state.

# 13. What conformance does NOT cover

Conformance examines byte representation only. The following are not tested and are not used for evaluation:

| Not tested | Reason |
|-----------|--------|
| API shape (`Encode()`, `WriteU32`…) | The Specification mandates no particular API |
| Whether the code is generated | Hand-written code is equally valid |
| The use of annotations | Schema representation is free |
| Error message content | Error reporting falls outside the Specification |
| Performance, allocation, throughput | They do not change the byte representation |
| The default value of `MaxStringLength` | Configured limits are not part of the protocol |

An implementation 10x slower that passes 100% of the test vectors is Fomoxa Compatible. A faster implementation that fails one vector is not.
