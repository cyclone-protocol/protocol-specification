# RFC-0001 - What is Cyclone?

## Status

Final

## Version

1.1.0

## Author

Ha Duy Thang

---

# 1. One-sentence summary

> Cyclone is a binary wire format specification that defines how data is represented as bytes, ensuring that the same data always produces a unique byte sequence across different languages, runtime environments, and implementations.

Cyclone defines a protocol, not a specific implementation.

---

# 2. What Cyclone is not

Please read this section first to avoid misunderstandings:

```
- Networking Framework      - RPC Framework
- Game Engine               - Transport Protocol
- Serialization Library     - Proprietary SDK
```

Cyclone does not handle the following:

```
- TCP / UDP / QUIC      - Retransmission     - Packet ordering
- Matchmaking           - Prediction         - Replication logic
- Encryption            - Compression        - Checksum
```

Those components are built on top of Cyclone. Cyclone addresses only one question:

```
What byte format must the data follow?
```

---

# 3. The problem Cyclone solves

## 3.1 Real-world scenario

A real-world system typically consists of the following components:

```
Server                Go
Client                C# / Unity
Tools                 Rust
Data Analysis         Python
Devices               C on microcontrollers
```

All five components need to understand the same `Player` entity. And in many use cases, they require more than just a shared understanding - they need to generate identical byte sequences.

## 3.2 Why is generating "identical byte sequences" difficult?

Each language has its own internal logic, and that logic influences how data is represented:

| Source of difference | Example |
|----------------------|---------|
| Memory layout | Compilers reorder fields to minimize padding |
| Alignment | `struct { u8; u32; u8 }` occupies 12 bytes in RAM, instead of 6 bytes |
| Endianness | Big-endian on certain architectures |
| String length | C#/Java count characters; Go/Rust count bytes |
| Enum size | `int` might be 4 bytes in one place but 8 bytes elsewhere |
| Floating-point numbers | `NaN` normalization; merging `-0.0` with `0.0` |

Each of the differences mentioned above results in a different byte stream. And the biggest risk is:

```
An incorrect schema often does NOT cause an error.

It silently produces incorrect data.
```

## 3.3 Why common formats do not solve this problem

| Format | Issue regarding the "same data → same bytes" requirement |
|-----------|-----------------------------------------------------------|
| JSON | Text-based; key order is undefined; floating-point representation varies by implementation; large size |
| Protobuf | Official documentation states that serialization does not guarantee a canonical form: map order, unknown fields, and version differences can all alter the output byte result |
| MessagePack | A single integer might have multiple valid representations (`int8`, `int16`, `int32`...) → multiple byte streams for the same value |
| Reflection-based (`BinaryFormatter`, `pickle`...) | Dependent on runtime and version; incompatible across programming languages ​​|

Common characteristic: they are designed for flexibility. Flexibility implies the existence of multiple valid ways to encode the same data. For the use cases in §5.1, this multiplicity of valid representations is precisely the problem that needs to be solved.

## 3.4 Problem Summary

```
Given the same schema
and the same logical value,

Model  →  Encode  →  Bytes
Bytes  →  Decode  →  Model

must yield identical results
across all systems implementing the standard.
```

That is all Cyclone guarantees. Nothing more, nothing less.

---
# 4. How Cyclone Solves the Problem

Cyclone solves problems by eliminating choices. Wherever a choice exists, two different implementation approaches are bound to emerge.

## 4.1 Five Design Decisions

### No metadata in the data stream

```
- Field name    - Type info    - Tag ID
- Object header - Padding      - Alignment
```

The byte stream is not self-describing; it consists of raw data. Both the encoder and decoder already know the schema beforehand.

### Position serves as the unique identifier

There are no field IDs. The decoder identifies fields based on order. This refers to the declaration order, not the memory layout.

### Fixed size; no varints

A `UInt32` always occupies 4 bytes, even if the value is 0. The trade-off here is that a value corresponds exactly to a single representation; there is no concept of "shorter encoding."

### No optional fields or default values

Every field must have a value. No fields are missing, so the issue of "how to encode the absence of data" never arises.

### The schema is the single source of truth, agreed upon out-of-band

The byte stream does not carry the schema with it. Therefore, the schema must be identical at both ends and finalized before data exchange begins - via any method, provided it is not transmitted alongside the actual data.

This is a direct consequence of having "no metadata in the transmission stream," rather than an independent requirement.

## 4.2 The Cost - Plain and Simple

Each of the decisions above comes with a cost:

| Benefit | Trade-off |
|------|-----| 
| Deterministic (consistent) byte representation | Schema evolution is limited to adding/removing fields at the end of the Model (RFC-0002 §9.1) |
| Lightweight transport format, fast decoding | Inserting/deleting fields in the middle, changing field order, or altering an existing field's data type = breaking change |
| No metadata parsing required | Byte stream is not self-describing; schema mismatch → silent data corruption (no error reported) |
| No ambiguity | No Optional / Nullable / default values ​​|
| Schema fixed upfront, known to both parties | Modifying a field in the middle of the Model structure still requires synchronized deployment on both sides; only adding or removing fields at the end allows the system to tolerate temporary version mismatches |

Cyclone does not attempt to hide these trade-offs. If they do not suit your use case, section §5.3 outlines scenarios where Cyclone should not be used.

# 5. Why Choose Cyclone

## 5.1 When determinism is a hard requirement, not just a "nice-to-have"

There is a class of problems where the rule "identical data → identical byte sequence" is not merely an optimization, but a pass/fail condition:

| Use Case | Reason for requiring deterministic byte sequences |
|----------|------------------------------------|
| Payload signing/hashing | Signatures are applied to the byte sequence. If the byte sequence changes, the signature becomes invalid, even if the logical data remains unchanged. |
| Replay / Lockstep | Two computers must reach the same system state from the same input data sequence. |
| Content-addressed / Deduplication | Identical content must produce the same hash; otherwise, caching and deduplication become meaningless. |
| Cross-SDK testing | Comparing byte sequences is the only way to verify if two SDKs are truly compatible with each other. |
| Binary audit logs | Records must be capable of being reproduced with absolute precision. |

For these use cases, a format that decodes correctly but encodes non-deterministically is unusable.

It is important to distinguish between two types of "equivalence":

```
Data equivalence      decode(bytes_A) == decode(bytes_B)     ← sufficient for most applications
Byte equivalence      bytes_A == bytes_B                     ← §5.1 requires this
```

Most formats only guarantee the former. They allow multiple valid byte sequences to represent the same value (§3.3); consequently, two encoding operations often produce identical byte sequences - until a library version changes, the programming language changes, or a `HashMap` iterates over elements in a different order.

It is precisely that word "often" where the problem arises. Because:

```
Standard application      Byte alignment mismatch → undetected, as decoding still yields correct data
§5.1 Issue                Byte alignment mismatch → invalid signature, hash cache-miss, replay attack causing world-state inconsistency
```

This means the bug does not appear during testing; it only surfaces when two endpoints run different versions in a production environment. A format that is correct in 99.9% of cases is not "good enough" here - it is essentially a flawed format, just one where the flaw is harder to detect.

## 5.2 When bandwidth and CPU are constrained

```
Game networking      IoT / embedded      Real-time streaming
```

No metadata, no tags, no varint decoding. The transport format is extremely lightweight, and the byte structure is simple enough that implementations can map bytes directly to the data model without runtime lookups.

## 5.3 When NOT to choose Cyclone

This is just as important as the previous point:

| Scenario | Reason for unsuitability |
|-----------|------------------|
| Public API allowing independent third-party development | Version v1.1 only supports adding/removing fields at the end of the Model (RFC-0002 §9.1). Third-party operations - such as inserting a field in the middle, reordering fields, or changing an existing field's data type - remain breaking changes that Cyclone cannot handle. |
| Long-term parallel maintenance of the old client and new server is required when mid-model changes occur. | The version mismatch handling mechanism (RFC-0002 §9.1) covers only adding or removing fields at the end; there is no "unknown-field skipping" mechanism for fields inserted in the middle, nor is there support for default values. |
| The model contains many "optional" fields. | Version v1.1 lacks support for `Optional` / `Nullable` types. |
| The schema changes frequently (e.g., weekly), and not just at the end of the model. | Every change requires a synchronized deployment on both sides. |

If you encounter these scenarios, a format utilizing tag IDs and optional fields would be more suitable. That is the correct choice, not a weakness of Cyclone.

# 6. The Power of Cyclone

This section covers two types of capabilities; pay close attention to the classification labels:

```
§6.1  §6.2  §6.5      Part of the Specification – present in all compliant implementations
§6.3  §6.4  §6.6      Part of the Reference Implementation – permitted by the wire format, but not mandatory
```

## 6.1 Byte-level determinism

```
Go SDK      encodes Player{hp=100, name="Alice"}  →  byte sequence A
C# SDK      encodes Player{hp=100, name="Alice"}  →  byte sequence A
Rust SDK    encodes Player{hp=100, name="Alice"}  →  byte sequence A
```

They are identical, down to the very last byte. Any discrepancy indicates an implementation bug rather than a protocol feature - and such a bug can be detected through a simple byte array comparison.

This is the key that unlocks everything in section §5.1: hashing, signatures, replay protection, deduplication, and compliance testing.

## 6.2 Compact wire format

A full `Player` object (including nested Models, Strings, Enums, bools, and Arrays of Models):

```
Cyclone   49 bytes
JSON      ~140 bytes for the same data
```

A nearly threefold difference. This gap arises not from compression algorithms, but from the elimination of non-data elements: there are no field names, brackets, commas, or tags.

It is also predictable: the size is calculated via addition and does not depend on the actual content. ## 6.3 Enabling implementations without reflection

This is not a mandatory requirement of the Specification - the specification does not mandate a specific implementation mechanism (§6.5). However, since the transport format contains no metadata, tags, or variable-length indicators, all encoding/decoding decisions can be determined directly from the schema. There is no ambiguity at runtime.

Consequently, an implementation may adopt the following approach:

```
Compile time                Runtime
────────────                ───────
Read schema                 Write bytes
Generate codec code         Read bytes
Validate                    (complete)
```

The Reference Implementation (RI) follows this exact process and achieves the following benefits:

- Compatibility with AOT (Ahead-of-Time compilation) environments - IL2CPP, game consoles (Unity), mobile devices, and embedded systems.
- No memory allocation for runtime type analysis.
- No metadata table lookups on the hot path.
- No "slow start" issues caused by reflection initialization.

An implementation that uses reflection is still considered valid - it simply does not leverage the aforementioned benefits. The generated byte data must remain identical.

## 6.4 Error detection at build time

The distinction lies in the following aspect. The elements constituting an invalid schema - such as negative enum values, duplicate names, infinite recursion, or inconsistent constraints - are defined by the Specification. However, the point at which errors are detected is left to the discretion of each specific implementation. RI opts to reject violations at the schema definition stage, rather than deferring the check until execution time.

The least costly error is one that never makes it into the production environment.
## 6.5 Interchangeable Implementations

The specification describes only the byte layout structure. It does not mandate the use of a specific API, code generation mechanism, or annotations. Consequently, it can be implemented using:

```
Code-generating compiler    Reflection    Hand-coding
FPGA                        PLC           Assembly
```

The litmus test is: *Is it possible to write an encoder in assembly for an 8-bit microcontroller that complies with this specification?* If not, then that requirement should not be part of the specification.

The reference implementation is not the standard; the specification is. You can replace the entire implementation without altering the wire format.

## 6.6 Your Data Types Remain Your Own

Two concepts must be distinguished before reading this section:

```
Model (RFC-0002 §5)   A Cyclone type: an ordered list of fields
Your type             A class, struct, or record in your programming language
```

The Specification defines the former concept and makes no mention of the latter. From a byte stream, there is no way to tell whether the other party is using a class, struct, DTO, or a raw array of numbers - all that matters is that the ordered list of fields matches.

*The following section discusses the Reference Implementation (RI);* it describes how the RI chooses to extract data, rather than imposing a mandatory compliance requirement.

The RI does not force you to write a parallel DTO class for network transmission, nor does it require inheritance from a base class or the implementation of an interface. It constructs the Model from your existing data type, extracting only those fields marked as network fields. The remaining elements - such as logic, methods, and internal fields - are ignored by the RI.

The only condition imposed by the specification is that the order of network fields, when mapped to the Schema, must match the order of their declaration within that Schema (§4.1). How you extract those fields is entirely up to you.

# 7. Cyclone's Position

```
Application
(game logic, RPC, replication, prediction)
↑
┌─────────────┐
│   CYCLONE   │   Model ↔ Bytes
└─────────────┘
↑
Transport
(TCP / UDP / QUIC / serial / file)
```

Cyclone is independent of the layers above or below it. It sits precisely where data changes its form of representation.

# 8. Philosophy

Two sets of principles operate at two different layers. They must not be confused with one another.

## 8.1 Specification Principles

These are mandatory compliance requirements. Any violation means the system is not Cyclone.
```
Specification First               The specification is the single source of truth
Protocol over Framework           Define bytes, not APIs
Minimal Wire Format               Send only data, not data descriptions
Deterministic by Design           One piece of data = exactly one byte sequence
Language Neutral                  No single language is the primary language
Implementation Independent        No specific parser, macro, or code generator required
Implementation Replaceable        The reference implementation is not the mandatory standard
```

## 8.2 Reference Implementation Principles

These are design choices, not mandatory compliance requirements. Other implementations may choose different approaches, provided the byte output remains unchanged.

```
User Owns the Model          No need to rewrite the model
Compile-time over Runtime    If determinable at build time, do it at build time
Zero Runtime Reflection      Runtime only performs byte reading and writing
```

## 8.3 Decision-making Rules

For any future changes, ask the following two questions in order:

> **1.** Is this feature observable from the byte stream?
>
> No → it belongs to section §8.2; must not be included in the Specification.
>
> **2.** Does this change violate any principle in section §8.1?
>
> Yes → it is incompatible with Cyclone.

The specific test criterion for Question 1 remains the one from section §6.5: *Could an author writing an encoder in assembly language for an 8-bit microcontroller comply with this feature?*
