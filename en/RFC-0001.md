# RFC-0001 - What is Fomoxa?

## Status

Final

## Version

1.1.0

## Author

Ha Duy Thang

---

# 1. One-sentence summary

> Fomoxa is a binary wire format specification. It defines how data is represented as bytes. The same data always yields exactly one byte sequence, across every language, every runtime and every implementation.

Fomoxa defines a protocol, not an implementation.

---

# 2. What Fomoxa is not

Read this first to avoid misunderstandings:

```
- Networking Framework      - RPC Framework
- Game Engine               - Transport Protocol
- Serialization Library     - Proprietary SDK
```

Fomoxa does not handle:

```
- TCP / UDP / QUIC      - Retransmission     - Packet ordering
- Matchmaking           - Prediction         - Replication logic
- Encryption            - Compression        - Checksum
```

Those components sit on top of Fomoxa. Fomoxa answers exactly one question:

```
Which byte format must the data follow?
```

---

# 3. The problem Fomoxa solves

## 3.1 A real-world scenario

A real system usually contains:

```
server        Go
client        C# / Unity
Tool          Rust
Analytics     Python
Device        C on a microcontroller
```

All five components understand the same `Player`. Many situations demand more than that. They must produce identical bytes.

## 3.2 Why are "identical bytes" hard?

Every language has its own internal logic. That logic reaches straight into the data representation:

| Source of divergence | Example |
|----------------------|---------|
| Memory layout | The compiler reorders fields to reduce padding |
| Alignment | `struct { u8; u32; u8 }` occupies 12 bytes in RAM, not 6 |
| Endianness | Big-endian on some architectures |
| String length | C#/Java count characters; Go/Rust count bytes |
| Enum size | `int` is 4 bytes here, 8 bytes elsewhere |
| Float | `NaN` normalization, `-0.0` folded into `0.0` |

Each divergence produces a different byte stream. The largest risk:

```
A wrong schema usually raises NO error.

It silently produces wrong data.
```

## 3.3 Why common formats do not solve this

| Format | Problem against "same data → same bytes" |
|-----------|-----------------------------------------------------------|
| JSON | Text-based; key order undefined; float printing varies by implementation; large size |
| Protobuf | The official documentation states it plainly: serialization guarantees no canonical form. Map order, unknown fields and version differences all change the bytes |
| MessagePack | One integer has several valid encodings (`int8`, `int16`, `int32`...) → several byte streams for one value |
| Reflection-based (`BinaryFormatter`, `pickle`...) | Tied to runtime and version; does not cross language boundaries |

The common trait: they are designed for flexibility. Flexibility means several valid ways to encode the same data. For the problems in §5.1, "several valid ways" is the problem.

## 3.4 Problem statement

```
Given the same schema
and the same logical values,

Model  →  Encode  →  Bytes
Bytes  →  Decode  →  Model

must yield identical results
across every conforming implementation.
```

That is the whole guarantee. Nothing more.

# 4. How Fomoxa solves it

Fomoxa removes choices. Where a choice remains, two implementations will diverge.

## 4.1 Five design decisions

### No metadata on the wire

```
- Field name    - Type info    - Tag ID
- Object header - Padding      - Alignment
```

The byte stream is not self-describing. It is raw data. Encoder and decoder both know the schema in advance.

### Position is the only identifier

There are no field IDs. The decoder identifies fields by order. This is declaration order, not memory layout.

### Fixed size, no varint

A `UInt32` always occupies 4 bytes, even when the value is 0. The trade: one value maps to exactly one representation. There is no "shorter encoding".

### No Optional, no default values

Every field carries a value. No field is absent. The question "how do I encode absence" never arises.

### Schema is the single source of truth, agreed out-of-band

The byte stream does not carry the schema. The schema must be identical on both ends and fixed before data is exchanged. Agree on it by any means, as long as it does not travel with the data.

This follows directly from "no metadata on the wire". It is not a separate requirement.

## 4.2 The price

Every decision above has a cost:

| Benefit | Trade-off |
|------|-----|
| Deterministic bytes | The schema evolves only by adding or removing fields at the end of a Model (RFC-0002 §9.1) |
| Compact wire format, fast decode | Inserting or deleting a middle field, reordering fields, or changing the type of an existing field is a breaking change |
| No metadata parsing | The byte stream is not self-describing; a schema mismatch corrupts data silently |
| No ambiguity | No Optional, no Nullable, no default values |
| Schema fixed up front, known to both sides | Editing a middle field still forces a synchronized deploy on both sides. Only appends and truncations at the end tolerate a temporary version skew |

Fomoxa does not hide these trades. If they do not fit you, §5.3 states when to stay away.

# 5. Why choose Fomoxa

## 5.1 When determinism is mandatory, not "nice to have"

One class of problems treats "same data → same bytes" as a pass/fail condition:

| Use case | Why deterministic bytes are required |
|----------|------------------------------------|
| Payload signing / hashing | The signature binds to bytes. Different bytes void it, even when the logical data is unchanged |
| Replay / lockstep | Two machines must reach the same state from the same input sequence |
| Content-addressed / dedupe | Identical content must hash identically. Otherwise caching and dedupe are meaningless |
| Cross-SDK testing | Comparing bytes is the only way to know two SDKs actually agree |
| Binary audit logs | Records must be reproducible exactly |

For this class, a format that decodes correctly but encodes non-deterministically is unusable.

Separate two kinds of "sameness":

```
Data equivalence    decode(bytes_A) == decode(bytes_B)     ← enough for most applications
Byte equivalence    bytes_A == bytes_B                     ← §5.1 requires this
```

Most formats guarantee only the first. They allow several valid byte sequences for one value (§3.3). In practice two encodes *usually* produce the same bytes. Until a library version changes, a language changes, or a `HashMap` iterates in a different order.

That word "usually" is where it breaks:

```
Ordinary application     Byte skew → nobody notices, because decode still yields correct data
§5.1 problem             Byte skew → broken signatures, hash cache-miss, replay corrupting world-state
```

The bug does not surface during testing. It surfaces when two ends run two versions in production. A format that is right 99.9% of the time is not "good enough" here. It is a broken format that is merely harder to see.

## 5.2 When bandwidth and CPU are tight

```
Game networking      IoT / embedded      Real-time streaming
```

No metadata, no tags, no varint decoding. The wire format is very compact. The byte structure is simple enough to map straight into a model, with no runtime lookup.

## 5.3 When NOT to choose Fomoxa

This section matters as much as the one above:

| Situation | Why it does not fit |
|-----------|------------------|
| A public API for independent third-party development | v1.1 supports appending or truncating fields at the end of a Model only (RFC-0002 §9.1). A third party inserting a middle field, reordering fields or retyping an existing field creates a breaking change that Fomoxa cannot absorb |
| Old client must run alongside new server for a long period, with the change in the middle of a Model | The version-skew mechanism (RFC-0002 §9.1) covers appends and truncations at the end only. There is no unknown-field skipping for inserted fields, and no default values |
| A Model with many "optional" fields | v1.1 has no `Optional` and no `Nullable` |
| The schema changes weekly, not only at the end of a Model | Every change forces a synchronized deploy on both sides |

In these cases, choose a format with tag IDs and optional fields. That is the correct call, not a weakness of Fomoxa.

# 6. What Fomoxa gives you

This section covers two classes of capability. Watch the labels:

```
§6.1  §6.2  §6.5      Specification - present in every conforming implementation
§6.3  §6.4  §6.6      Reference Implementation - permitted by the wire format, not required
```

## 6.1 Byte-level determinism

```
Go SDK      encode Player{hp=100, name="Alice"}  →  byte sequence A
C# SDK      encode Player{hp=100, name="Alice"}  →  byte sequence A
Rust SDK    encode Player{hp=100, name="Alice"}  →  byte sequence A
```

Identical, down to the last byte. A discrepancy is an implementation bug, not a protocol feature. Catch it with one byte-array comparison.

This is the key to everything in §5.1: hashing, signatures, replay protection, dedupe and conformance testing.

## 6.2 Compact wire format

A full `Player` (nested Model, String, Enum, bool, Array of Model):

```
Fomoxa    49 bytes
JSON      ~140 bytes for the same data
```

Nearly a 3x gap. The gap does not come from compression. It comes from dropping everything that is not data: no field names, no brackets, no commas, no tags.

The size is also predictable. It is computed by addition and does not depend on content.

## 6.3 Reflection-free implementations are possible

This is not a Specification requirement. The Specification does not dictate implementation mechanics (§6.5). The wire format contains no metadata, no tags and no variable-length indicators. Every encode and decode decision is determined by the schema. No ambiguity remains at runtime.

An implementation may therefore take this route:

```
Build time                  Run time
──────────────────          ──────────────────
Read the schema             Write bytes
Generate the codec          Read bytes
Validate                    (done)
```

The Reference Implementation (RI) follows exactly this path and gains:

- Runs on AOT environments: IL2CPP, consoles (Unity), mobile, embedded.
- No allocation for runtime type analysis.
- No metadata table lookup on the hot path.
- No "slow start" from reflection warm-up.

A reflection-based implementation is still valid. It simply forfeits those benefits. Its bytes must still be identical.

## 6.4 Errors caught at build time

The difference sits here. What makes a schema invalid (negative enum values, duplicate names, infinite recursion, wrong constraints) is defined by the Specification. *When* the error is caught is decided by each implementation.

The RI rejects at schema definition time instead of deferring the check to runtime.

The cheapest bug is the one that never reaches production.

## 6.5 Implementations are replaceable

The Specification describes byte layout only. It mandates no API, no code-generation mechanism and no annotations. It can be implemented with:

```
Code-generating compiler    Reflection    Hand-written
FPGA                        PLC           Assembly
```

The decisive test: *Can an encoder written in assembly on an 8-bit microcontroller comply with this rule?* If not, the rule does not belong in the Specification.

The Reference Implementation is not the standard. The Specification is the standard. Replace the entire implementation and the wire format does not move.

## 6.6 Your types stay yours

Separate two concepts first:

```
Model (RFC-0002 §5)   a Fomoxa type: an ordered list of fields
Your type             a class / struct / record in your language
```

The Specification defines the first and says nothing about the second. Looking at a byte stream, there is no way to tell whether the other side uses a class, a struct, a DTO or a raw number array. Only the ordered field list has to match.

*The following describes the Reference Implementation (RI).* It states how the RI chooses to extract data. It is not a conformance requirement.

The RI does not force you to write a parallel DTO class for the wire. It requires no base class and no interface. It builds a Model from your existing type and extracts only the fields marked as network fields. The rest (logic, methods, internal fields) is ignored.

The Specification imposes one condition: the order of network fields, once mapped into the schema, must match the declaration order in that schema (§4.1). How you extract them is your business.

# 7. Where Fomoxa sits

```
        Application
        (game logic, RPC, replication, prediction)
              ↑
        ┌────────────┐
        │   FOMOXA   │   Model ↔ Bytes
        └────────────┘
              ↑
        Transport
        (TCP / UDP / QUIC / serial / file)
```

Fomoxa depends on neither the layer above nor the layer below. It sits exactly where data changes shape.

# 8. Philosophy

Two sets of principles operate at two different layers. Do not mix them.

## 8.1 Specification principles

These are conformance requirements. Violate any one and the system is not Fomoxa.

```
Specification First               The spec is the single source of truth
Protocol over Framework           Define bytes, not APIs
Minimal Wire Format               Send data only, never a description of data
Deterministic by Design           One value = exactly one byte sequence
Language Neutral                  No language is the primary language
Implementation Independent        No mandated parser, macro or generator
Implementation Replaceable        The Reference Implementation is not the standard
```

## 8.2 Reference Implementation principles

These are design choices, not conformance requirements. Other implementations may differ, as long as the output bytes do not.

```
User Owns the Model          Never force a model rewrite
Compile-time over Runtime    If it can be resolved at build time, resolve it at build time
Zero Runtime Reflection      At run time, read bytes and write bytes
```

## 8.3 Decision rules

For any future change, ask two questions in order:

> 1. Is this trait observable from the byte stream?
>
> No → it belongs to §8.2. Keep it out of the Specification.
>
> 2. Does this change violate any principle in §8.1?
>
> Yes → it does not belong in Fomoxa.

The concrete test for question 1 remains the test from §6.5: *Can someone writing an encoder in assembly on an 8-bit microcontroller comply with this trait?*
