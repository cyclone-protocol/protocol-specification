# 1. One Sentence

> Cyclone is a **binary wire format specification** that defines how data is represented as bytes, such that the same data always yields **exactly one** byte sequence - on every language, every runtime, every implementation.

Cyclone defines a **protocol**, not an **implementation**.

---

# 2. What Cyclone Is Not

Read this first, so you don't expect the wrong thing:

```
✗ Networking Framework      ✗ RPC Framework
✗ Game Engine               ✗ Transport Protocol
✗ Serialization Library     ✗ Proprietary SDK
```

Cyclone does not care about:

```
TCP / UDP / QUIC      Retransmission     Packet ordering
Matchmaking           Prediction         Replication logic
Encryption            Compression        Checksum
```

Those are built **on top of** Cyclone. Cyclone answers exactly one question:

```
What shape must the bytes have.
```

---

# 3. The Problem Cyclone Exists To Solve

## 3.1 The situation

A real system usually looks like:

```
Server        Go
Client        C# / Unity
Tool          Rust
Analytics     Python
Device        C on a microcontroller
```

All five must understand the same `Player`. And in many problems they don't just need to **understand it the same way** - they need to **produce byte-identical output**.

## 3.2 Why "byte-identical" is hard

Every language has its own way of thinking, and that thinking leaks into the data:

| Source of difference | Example |
|----------------------|---------|
| Memory layout | The compiler reorders fields to reduce padding |
| Alignment | `struct { u8; u32; u8 }` occupies 12 bytes in RAM, not 6 |
| Endianness | Big endian on some architectures |
| String length | C#/Java count characters, Go/Rust count bytes |
| Enum width | `int` is 4 bytes here, 8 bytes there |
| Map/set ordering | `HashMap` iterates in a different order on every run |
| Float | Normalizing `NaN`, collapsing `-0.0` into `0.0` |

Every difference above produces a different byte stream. And the most dangerous part:

```
A wrong schema usually raises NO error.

It silently produces wrong data.
```

## 3.3 Why the common formats don't solve this

| Format | Problem with "same data → same bytes" |
|--------|---------------------------------------|
| JSON | Text, key order unspecified, floats printed differently per implementation, large |
| Protobuf | The official documentation states plainly that serialization is **not guaranteed canonical**: map ordering, unknown fields, and version differences can all change the bytes |
| MessagePack | One integer has several valid representations (`int8`, `int16`, `int32`…) → many byte streams for one value |
| Reflection-based (`BinaryFormatter`, `pickle`…) | Runtime-dependent, version-dependent, not cross-language |

What they share: they were designed to be **flexible**. Flexible means more than one valid encoding exists for the same data. For the problems in §5.1, "more than one valid encoding" **is** the problem.

## 3.4 The problem, stated compactly

```
Given an identical schema
and an identical logical value

Model  →  Encode  →  Bytes
Bytes  →  Decode  →  Model

must produce identical results
on every conforming implementation.
```

That is the entirety of what Cyclone guarantees. Nothing more.

# 4. How Cyclone Solves It

Cyclone solves it by **removing every choice**. Wherever there is a choice, two implementations will eventually choose differently.

## 4.1 Five design decisions

### No metadata on the wire

```
✗ Field name    ✗ Type info    ✗ Tag ID
✗ Object header ✗ Padding      ✗ Alignment
```

The byte stream is **not self-describing**. It is data only. Encoder and decoder know the schema in advance.

### Position is the only identifier

There are no field IDs. The decoder knows which field it is reading from the **order**. That order is **declaration** order, not memory layout.

### Fixed size, no varint

`UInt32` is always 4 bytes, even when the value is 0. In exchange: one value → exactly one representation, with no "shorter encoding" available.

### No Optional, no default value

Every field carries a value. There is no absent field, so there is no question of "how do you encode absence".

### The schema is the single source of truth, agreed out of band

The byte stream does not carry the schema. So the schema must be identical on both ends and settled **before** any data is exchanged - by whatever route you like, as long as it is not on the wire.

This is a direct consequence of "no metadata on the wire", not an independent requirement.

## 4.2 The price - stated plainly

Each decision above has a cost:

| Gained | Lost |
|--------|------|
| Absolutely deterministic bytes | Schema evolution is limited to adding/removing fields at the **end** of the Model (RFC-0002 §9.1) |
| Small wire, fast decode | Inserting/removing a field in the middle, reordering fields, or changing an existing field's type = breaking change |
| No metadata to parse | Stream is not self-describing; wrong schema → silently wrong data |
| No ambiguity | No Optional / Nullable / default |
| Schema settled up front, known to both ends | Changing a field in the middle of the Model still requires deploying both sides together; only appending/removing a field at the end tolerates a temporary version gap |

Cyclone does **not** try to hide these trade-offs. If they are unacceptable for your problem, §5.3 says exactly when not to use it.

# 5. Why Choose Cyclone

## 5.1 When determinism is a requirement, not a nice-to-have

There is a class of problems where "same data → same bytes" is not an optimization but a **correctness condition**:

| Problem | Why deterministic bytes are required |
|---------|--------------------------------------|
| Signing / hashing a payload | A signature is computed over bytes. Bytes change → signature fails, even though the logical data did not change |
| Replay / lockstep | Two machines must reach the same world state from the same input sequence |
| Content-addressing / dedupe | The same content must produce the same hash, otherwise caching and deduplication are meaningless |
| Cross-SDK testing | Comparing bytes is the only way to prove two SDKs are genuinely compatible |
| Binary audit log | A record must be reproducible exactly |

For these problems, a format that **decodes correctly but encodes non-deterministically** is unusable.

Two different meanings of "identical" have to be kept apart:

```
Identical data     decode(bytes_A) == decode(bytes_B)     ← enough for most applications
Identical bytes    bytes_A == bytes_B                     ← §5.1 needs this one
```

Most formats promise only the first. They allow several valid byte sequences to represent one value (§3.3), so in practice two encodes **usually** produce the same bytes - right up until you change library version, change language, or a `HashMap` iterates in a different order.

"Usually" is what kills you. Because:

```
Ordinary application    bytes differ → nobody notices, decoding still yields the right data
§5.1 problem            bytes differ → signature fails, hash misses cache, replay diverges
```

Which means the bug does not show up in testing. It shows up when the two ends run different versions in production. A format that is right 99.9% of the time is not "close enough" here - it is a wrong format that is merely harder to catch.

## 5.2 When bandwidth and CPU are constrained

```
Game networking      IoT / embedded      Real-time streaming
```

No metadata, no tags, no varint decoding. The wire is small, and the shape of the bytes is simple enough that an implementation can go from bytes to model without looking anything up at runtime.

## 5.3 When NOT to choose Cyclone

Just as important as the section above:

| Situation | Why it doesn't fit |
|-----------|--------------------|
| A public API that third parties evolve however they like | v1 only allows adding/removing fields at the **end** of the Model (RFC-0002 §9.1). A third party inserting a field in the middle, reordering fields, or changing an existing field's type is still a breaking change Cyclone cannot control |
| Old clients and new servers must coexist long-term, with changes in the middle of the Model | Version skew (RFC-0002 §9.1) only covers appending/removing a field at the end; there is no unknown-field skipping for a field inserted in the middle, and no defaults |
| Humans need to read the data by eye | Cyclone is pure binary |
| The model has many "may not be present" fields | No Optional / Nullable in v1 |
| The schema changes weekly, not just at the end of the Model | Every change requires deploying both sides together |

If you are in these groups, a format with tag IDs and optional fields will serve you better. That is the right call, not a failure of Cyclone.

# 6. What Cyclone Gives You

This section covers two kinds of strength. Read the labels:

```
§6.1  §6.2  §6.5      Specification - every conforming implementation has these
§6.3  §6.4  §6.6      Reference Implementation - the wire format permits them, it does not require them
```

## 6.1 Byte-level determinism

```
Go SDK      encode Player{hp=100, name="Alice"}  →  bytes A
C# SDK      encode Player{hp=100, name="Alice"}  →  bytes A
Rust SDK    encode Player{hp=100, name="Alice"}  →  bytes A
```

Identical, byte for byte. If they differ, that is an **implementation bug**, not a property of the protocol - and that bug is caught by a single byte-array comparison.

This is what unlocks all of §5.1: hashing, signing, replay, dedupe, conformance testing.

## 6.2 Small wire

A complete `Player` (nested Model, String, Enum, bool, Array of Model):

```
Cyclone   49 bytes
JSON      ~140 bytes for the same data
```

Nearly **3×**. The difference does not come from a compression algorithm - it comes from **not sending anything that isn't data**: no field names, no braces, no commas, no tags.

And it is predictable: the size is a sum, independent of content.

## 6.3 It lets an implementation skip reflection

This is **not** a requirement of the Specification - the spec does not care what mechanism an implementation uses (§6.5). But because the wire format has no metadata, no tags, and no variable sizes, every encode/decode decision follows from the schema. Nothing is left to ask at runtime.

So an implementation **may** choose to work like this:

```
Compile time                Runtime
────────────                ───────
Read schema                 Write bytes
Generate codec              Read bytes
Validate                    (that's all)
```

The Reference Implementation takes exactly that route, and gets:

- Runs on AOT targets - IL2CPP, Unity consoles, mobile, embedded.
- No allocation for runtime type analysis.
- No metadata table lookups on the hot path.
- No "slow first call" from reflection warm-up.

An implementation built on reflection is still **conforming** - it simply forgoes the benefits above. The bytes it produces must still be identical.

## 6.4 Errors happen at build time

*The boundary here runs between two sentences.* **What** counts as an invalid schema - negative enums, duplicate names, infinite recursion, bad constraints - is set by the Specification. **When** it is detected is the implementation's call.

The Reference Implementation rejects it where the schema is defined, rather than deferring to runtime.

The cheapest bug is the one that never reaches production.

## 6.5 Implementations are replaceable

The specification describes only the shape of the bytes. It does not mandate an API, does not require code generation, does not require annotations. So it can be implemented with:

```
Code generator       Reflection    By hand
FPGA                 PLC           Assembly
```

The test: *could someone writing an encoder in assembly on an 8-bit microcontroller follow this statement?* If not - that statement does not belong in the Specification.

The Reference Implementation is **not** the standard. The Specification is. Replace the entire implementation and the wire format does not move.

## 6.6 Your type stays yours

Two meanings have to be kept apart before reading this section:

```
Model (RFC-0002 §5)   a Cyclone type: an ordered list of fields
Your type             the class / struct / record in your language
```

The Specification defines the first and says **nothing** about the second. From a byte sequence there is no way to tell whether the other end used a class, a struct, a DTO, or a raw array of numbers - only that the ordered field lists match.

*What follows is Reference Implementation*, i.e. **how the RI chooses to get at your data**, not a conformance condition.

The RI does not force you to write a parallel DTO layer for the network, does not require inheriting a base class, does not require implementing an interface. It builds the Model from **your existing type**, taking only the fields marked as network fields. The rest - logic, methods, internal fields - the RI never looks at.

The one condition the Specification does impose: once mapped to the Schema, the network fields must appear in the order the Schema declares (§4.1). Where you get those fields from is your business.

# 7. Where Cyclone Sits

```
        Application
        (game logic, RPC, replication, prediction)
              ↑
        ┌─────────────┐
        │   CYCLONE   │   Model ↔ Bytes
        └─────────────┘
              ↑
        Transport
        (TCP / UDP / QUIC / serial / file)
```

Cyclone knows nothing about the layer above or the layer below. It stands exactly where data changes shape.

# 8. Philosophy

Two groups of principles, at two different layers. Do not mix them.

## 8.1 Principles of the Specification

These are conformance conditions. Violating one means it is not Cyclone.

```
Specification First          The specification is the single source of truth
Protocol over Framework      Define bytes, not an API
Minimal Wire Format          Send the data, never a description of the data
Deterministic by Design      One value, exactly one byte sequence
Language Neutral             No language is the reference language
Implementation Independent   No mandated parser / macro / generator
Implementation Replaceable   The Reference Implementation is not the standard
```

## 8.2 Principles of the Reference Implementation

These are design choices, not conformance conditions. Another implementation may choose differently, as long as the bytes do not move.

```
User Owns the Model          Never force a rewrite of the model
Compile-time over Runtime    Decidable at build time → decided at build time
Zero Runtime Reflection      The runtime only reads and writes bytes
```

## 8.3 The decision rule

For every future change, two questions in order:

> **1.** Is this statement observable from the byte stream?
>
> No → it belongs in §8.2 and must not enter the Specification.
>
> **2.** Does this change violate any principle in §8.1?
>
> Yes → it is not part of Cyclone.

The concrete test for question 1 is still the one from §6.5: *could someone writing an encoder in assembly on an 8-bit microcontroller follow this statement?*
