# RFC-0002 - Wire Format Specification

## Status

Final

## Version

1.1.0

## Author

# 0. What this specification is

This specification answers exactly one question:

> How do I produce or read a Fomoxa byte array?

The specification describes:

```
The structure of the bytes.
```

The specification does NOT describe:

```
Which API produces those bytes.
The use of annotations.
Code-generation requirements.
```

The same specification can therefore be implemented with:

```
Code-generating compiler
Reflection
Hand-written code
FPGA
PLC
Microcontroller
Assembly
```

The only condition is that both conversions:

```
Logical data  →  Bytes
Bytes  →  Logical data
```

follow the rules below strictly.

---

# 1. The rules

```
Always little-endian.
UInt32 always occupies exactly 4 bytes.
Enums are always UInt32.
Floats are written as raw IEEE 754 bit patterns.
Models carry no metadata.
Fields are written in declaration order, not memory layout order.
No padding.
No alignment.
No tag IDs.
No object headers.
Same data → same bytes.
```

# 2. Primitives

## 2.1 UInt32

A `UInt32` occupies exactly 4 bytes, little-endian.

```
Value

100

↓

Bytes

64 00 00 00
```

## 2.2 Full table

| Type | Byte shape | Size |
|------|----------------|-----------|
| `bool` | `0x00` = false, `0x01` = true, anything else → invalid | 1 |
| `i8` / `u8` | 1 byte | 1 |
| `i16` / `u16` | 2 bytes little-endian | 2 |
| `i32` / `u32` | 4 bytes little-endian | 4 |
| `i64` / `u64` | 8 bytes little-endian | 8 |
| `f32` | IEEE 754 single, little-endian, no normalization | 4 |
| `f64` | IEEE 754 double, little-endian, no normalization | 8 |

No varints. No variable-length encoding.

## 2.3 Float - bit pattern

```
Floats are serialized by preserving the IEEE 754 bit pattern.

No normalization. No canonical form.
```

The encoder writes the exact bit pattern it holds and changes nothing:

```
Infinity   → bits written as-is
-0.0       → bits written as-is, distinct from 0.0
NaN        → bits written as-is
```

Understand this about `NaN`:

```
CPU A

NaN

↓

0x7FC00001

CPU B

NaN

↓

0x7FC01234
```

Two different bit patterns, both `NaN`. Two implementations that preserve the bits will emit different bytes.

This does not violate the protocol. The serialized value is the IEEE 754 bit pattern, not the abstract concept "NaN". The cross-SDK guarantee (§13) applies to the input bit pattern, not to a "NaN value".

Implementations MUST NOT replace `NaN` with a normalized bit pattern.

## 2.4 Bool

```
Encoders MUST emit 0x00 or 0x01 only.
```

Write no other value. This includes values the source language treats as true: `0xFF`, `0x02`, a non-null pointer.

If the decoder meets a byte other than `0x00` or `0x01`, the byte stream is invalid (§10). Never treat "non-zero as true".

---

# 3. String

A String is represented as:

```
UInt32 length

↓

UTF-8 bytes
```

`length` is the UTF-8 byte count, not the character count.

```
ABC

↓

03 00 00 00

41 42 43
```

The byte range MUST be valid UTF-8.

---

# 4. Bytes

```
UInt32 length

↓

Raw bytes
```

Same as String, without the UTF-8 constraint.

---

# 5. Model

A Model is a Fomoxa type consisting of an ordered list of fields. Each field holds a Fomoxa type.

That is the entire definition. Which concept a Model maps to in your language (`class`, `struct`, `record`, `data class`, `dict`, or a set of loose variables) falls outside the Specification. Two languages using two different concepts must still produce the same bytes. What is serialized is the ordered field list, not the language construct holding it.

A Model is represented by concatenating each field's bytes in definition order.

```
Player

Hp

↓

UInt32

Name

↓

String

↓

Bytes
```

No metadata, no field IDs, no padding between fields.

## 5.1 Field order

Fields MUST be serialized in declaration order.

Field order is part of the protocol. Reordering fields changes the entire byte sequence.

The key point: wire order is declaration order, not memory order. A compiler may reorder fields in RAM to reduce padding. That MUST NOT change a single output byte.

```
Declaration       Possible RAM layout       On the wire
───────────       ───────────────────       ─────────────────
a: u8             b (4 bytes)               a
b: u32            a (1 byte)                b
c: u8             c (1 byte)                c
                  + padding                 (no padding)
```

Any implementation that derives field order from memory layout, reflection order, or any source other than declaration order has an implementation bug.

---

# 6. Array

```
UInt32 Count

↓

Element 1

↓

Element 2

↓

...
```

`Count` is the element count, not the byte count. Each element is written in the byte format of type `T`.

---

# 7. Enum

```
UInt32 value
```

```
Enums are always UInt32.

This is a protocol decision,
not a storage optimization.
```

No `u8`, no `u16`, no `i32`, no scaling with member count. Every Enum, at every size, is exactly 4 bytes little-endian.

The reasons: a small specification, a simple compiler, fast decoding, no negotiation between the two sides.

A value outside the defined set → invalid byte stream. No graceful degradation, no skipping.

---

# 8. Encoder

To write a Model:

```
1. Write the first field.

2. Write the second field immediately after it.

3. Insert no other bytes.

4. The final byte is the last byte of the last field.
```

---

# 9. Decoder

To read a Model:

```
1. Read the first field.
2. Advance the cursor by exactly the bytes that field consumed.
3. Move to the next field.
4. Repeat until the Model ends.
```

If the remaining bytes are fewer than the field requires, distinguish the cursor position:

```
The cursor sits inside a field (partially read) and bytes run out before the field completes
→ Invalid byte stream (unexpected EOF, §10)

The previous field completed, the cursor sits on a field boundary, and bytes run out before the next field reads anything
→ Not an error. See version skew (§9.1)
```

If every field of the Model has been read and bytes remain in the stream, the surplus is not an error either. See §9.1.

## 9.1 Version skew

A Model is user-defined, and its definition changes over time. At any moment, the Model used by the writer and the Model used by the reader may differ. Call that version skew.

### Two Models, equal standing

Fomoxa embeds no version information in the byte stream (§11). "Older" and "newer" are not properties readable from the bytes. For any pair of Models, saying one side appended a field is as accurate as saying the other side dropped a trailing field. Both descriptions map to the same byte sequence and the same decode behaviour. No test distinguishes them.

The word "version" here means only that two different Models exist. It implies no chronology. Every rule in this section is therefore built on the pair (writer Model, reader Model), not on time order.

### Validity conditions

Version skew is valid if and only if:

```
The type sequence of the shorter Model is an exact prefix
of the type sequence of the longer Model.

Let n be the field count of the shorter Model.
At every index from 0 to n-1, both Models carry the same Fomoxa types,
in the same declaration order (§5.1).
Extra fields appear only at the tail of the longer Model.
```

Those are the only criteria. Which Model is longer does not affect the conclusion.

### Two manifestations on the byte stream

```
Missing trailing bytes
──────────────────
The writer Model has fewer fields than the reader Model.
The stream ends exactly on a field boundary
→ the reader's remaining fields have no data.
```

```
Surplus trailing bytes
────────────────
The writer Model has more fields than the reader Model.
After reading every field the reader knows, bytes remain
→ the surplus belongs to fields the reader does not have.
```

In both cases the decoder MUST treat the byte stream as valid.

Stop rules:

```
1. Bytes missing at a field boundary
→ stop reading the Model there; treat the remaining fields as absent.

2. Bytes remaining after the last field the Model knows
→ ignore the surplus and read no further.
```

How an implementation represents "a missing field" (default values, `Option<T>`, an application-level exception) falls outside the Specification, the same way error reporting does in §10.

A Model nested in another Model's field applies this rule at its own level. A nested Model missing bytes or carrying surplus bytes at its own field boundary is also version skew, not an error.

### When it is NOT version skew

If two schemas diverge at a specific index, the prefix condition fails:

```
Two schemas diverge at one index
→ the field at that index differs, violating the field-order rule in §5.1
→ this is a protocol change, not version skew,
and it falls outside this section.
```

Example with `Item { id: u32, name: String, hp: u16 }`:

| Writer Model | Reader Model | Prefix? | Conclusion |
|---|---|---|---|
| `{ id, name }` | `{ id, name, hp }` | yes | version skew, valid |
| `{ id, name, hp }` | `{ id, name }` | yes | version skew, valid |
| `{ id, name, hp }` | `{ id, hp }` - middle `name` dropped | no, diverges at index 1 (`String` ↔ `u16`) | protocol change |
| `{ id, name, hp }` | `{ id, lvl: u8, name, hp }` - middle insert | no, diverges at index 1 (`String` ↔ `u8`) | protocol change |
| `{ id, name, hp }` | `{ name, id, hp }` - reordered | no, diverges at index 0 (`u32` ↔ `String`) | protocol change |

The first two rows form a bidirectional read/write pair and reach the same conclusion. It confirms the earlier statement: the direction of change is irrelevant to the wire representation.

### Scope of this section

This description covers order and types only. No field names and no field IDs appear on the wire (§11). Position is the sole identifier. Two Models with the same type sequence but different field meanings produce the same byte layout, and §9.1 cannot tell them apart. Detecting and blocking such cases belongs to a higher schema layer, where field names and full declarations are available for comparison. It falls outside the Specification.

# 10. Invalid byte streams

| Error | Condition on the byte stream |
|-----|---------------------------|
| Unexpected EOF | Fewer bytes remain than the field requires, and the cursor has already read part of that field (bytes missing at a field boundary are not an error, see §9.1) |
| Invalid bool | The byte of a `bool` is neither `0x00` nor `0x01` |
| Invalid enum | A `u32` value outside the defined set |
| Invalid UTF-8 | The byte range of a `String` is not valid UTF-8 |
| Length overflow | A length or count field exceeds the remaining bytes, or exceeds a configured limit (§12) |

How an implementation reports an error (throwing an exception, returning an error, setting a flag, driving GPIO pins) falls outside the Specification.

## 10.1 Length overflow

```
Implementations MUST reject a length value that exceeds the remaining bytes.
```

This check MUST run before allocation.

```
Length = 100

5 bytes remain

↓

Error
```

This constraint is normative, independent of configuration and independent of implementation. A length the byte stream itself cannot satisfy is always an invalid byte stream.

The error name matches, but the nature differs from the configured limit in §12:

| Source | Condition | Property |
|-------|-----------|-----------|
| Byte stream | `length > remaining bytes` | Normative. Every implementation MUST reject |
| Configuration | `length > MaxStringLength…` | Non-normative. Set per endpoint |

Apply both at once:

```
effective limit = min(remaining bytes, configured limit)
```

---

# 11. Not present on the wire

```
- Padding             - Alignment        - Nullable / Option<T>
- Version field/tag   - Compression      - Checksum
- Field ID / tag      - Object header    - Default value
```

No version field and no version tag is written into the bytes. This is a statement about byte shape, not a statement about compatibility between two Model versions. How the decoder handles a mismatch between writer Model and reader Model is covered in §9.1. It does not contradict the table above.

---

# 12. Limits - non-normative

A `u32` length or count permits up to 4GB. An implementation that allocates by length without checking is exposed to DoS.

Implementations SHOULD therefore expose configurable limits: `MaxStringLength`, `MaxBytesLength`, `MaxArrayCount`, `MaxPacketSize`.

These limits are not part of the protocol. Two endpoints with different configurations MAY disagree on whether to accept a byte stream.

Configured limits are additive. They do not replace the normative check in §10.1. No configuration permits accepting a length greater than the remaining bytes.

---

# 13. Cross-SDK guarantee

```
Every v1.1 implementation MUST produce identical bytes for the same input data.
```

For floats, "the same input data" means the same IEEE 754 bit pattern (§2.3), not the same mathematical value.

A discrepancy is an implementation bug, not a protocol bug.

---

# 14. Test vectors

A test vector is a pair (value, bytes).

```
u32   100          → [64 00 00 00]
String "abc"       → [03 00 00 00 61 62 63]
Array<u32> [1,2,3] → [03 00 00 00 01 00 00 00 02 00 00 00 03 00 00 00]
bool  false / true → [00] / [01]
bool  [02]         → invalid
f32   3.14         → [C3 F5 48 40]
f32   Infinity     → [00 00 80 7F]
f32   -0.0         → [00 00 00 80]
enum  Status::OK   → [00 00 00 00]
enum  [63 00 00 00] where value set = {0,1} → invalid
String len=2 data=[FF FE] → invalid (UTF-8)
String len=[64 00 00 00] with 5 bytes left → invalid (length overflow)

model Item { id: u32; name: String }
Item{ id=42, name="Sword" } → [2A 00 00 00 05 00 00 00 53 77 6F 72 64]

model ItemV1 { id: u32 }
model ItemV2 { id: u32; name: String }

Written by ItemV1, read by ItemV2:
[2A 00 00 00] → id=42, bytes end on the boundary before name → valid, version skew (§9.1); name has no data

Written by ItemV2, read by ItemV1:
[2A 00 00 00 05 00 00 00 53 77 6F 72 64] → id=42, 9 surplus bytes after field id → valid, version skew (§9.1); the surplus is ignored

Written by ItemV2, read by ItemV2, bytes truncated inside field name:
[2A 00 00 00 05 00 00 00 53 77] → length=5 but only 2 data bytes remain → invalid (unexpected EOF). NOT version skew, because bytes ran out inside a field rather than on a boundary
```

Float test vectors MUST be written as bit patterns, never as value names:

```
f32 bit pattern 0x7FC00000 → [00 00 C0 7F]
f32 bit pattern 0x7FC00001 → [01 00 C0 7F]
```

Both are `NaN`. Writing `f32 NaN → [00 00 C0 7F]` is wrong. It implies a canonical NaN that §2.3 does not define. A conformance suite comparing by "NaN value" will report false failures on platforms that produce different bit patterns.

---

# 15. Full example

```
model Vector3 { x: f32; y: f32; z: f32 }

model GameMessage {
    playerId:   u32
    playerName: String
    position:   Vector3
    health:     u32
    isAlive:    bool
}
```

Values:

```
    playerId   = 42
    playerName = "Knight"
    position   = Vector3 { x = 10.5, y = 20.3, z = -5.1 }
    health     = 100
    isAlive    = true
```

Bytes:

```
    playerId   → [2A 00 00 00]
    playerName → [06 00 00 00] [4B 6E 69 67 68 74]
    position   → [00 00 28 41] [66 66 A2 41] [33 33 A3 C0]
    health     → [64 00 00 00]
    isAlive    → [01]

    [2A 00 00 00 06 00 00 00 4B 6E 69 67 68 74
    00 00 28 41 66 66 A2 41 33 33 A3 C0
    64 00 00 00 01]
```

Reading back: read 4 bytes → `playerId = 42`. Read 4 bytes (length = 6), advance the cursor past 6 bytes → `playerName = "Knight"`. Read 3 × 4 bytes → `position`. Read 4 bytes → `health = 100`. Read 1 byte → `isAlive = true`. The cursor stops exactly at the end of the stream.
