# 0. What is this specification?

This specification answers only one question:

> How do you create or read a Cyclone byte array?

The specification describes:

```
What the byte structure must look like.
```

The specification does NOT describe:

```
The API used to generate those bytes.
The use of annotations.
Code generation requirements.
```

Therefore, the same specification can be implemented using:

```
Code-generating compilers
Reflection
Hand-coding
FPGAs
PLCs
Microcontrollers
Assembly
```

As long as the final conversion processes:

```
Logical data → Bytes
Bytes → Logical data
```

strictly adhere to the rules of the specification.

---

# 1. Rules

```
Always use Little Endian format.
UInt32 always occupies exactly 4 bytes.
Enum types are always UInt32.
Floating-point numbers (floats) are written as raw IEEE 754 bit patterns.
Models contain no metadata.
Fields are written in the order of declaration, not memory layout.
No padding bytes.
No memory alignment.
No tag IDs.
No object headers.
Identical data → identical byte sequence.
```

# 2. Primitives

## 2.1 UInt32

A `UInt32` value is represented by exactly 4 bytes in Little Endian format. 
```
Value

100

↓

Bytes

64 00 00 00
```

## 2.2 Full table

| Type | Byte representation | Size |
|------|---------------------|------|
| `bool` | `0x00` = false, `0x01` = true, other → invalid | 1 |
| `i8` / `u8` | 1 byte | 1 |
| `i16` / `u16` | 2 bytes Little Endian | 2 |
| `i32` / `u32` | 4 bytes Little Endian | 4 |
| `i64` / `u64` | 8 bytes Little Endian | 8 |
| `f32` | IEEE 754 single, Little Endian, non-normalized | 4 |
| `f64` | IEEE 754 double, Little Endian, non-normalized | 8 |

No varints; no variable-length encoding.

## 2.3 Float - Bit Pattern

```
Floating-point values ​​are serialized by preserving the exact IEEE 754 bit representation.

No normalization or conversion to a canonical form is performed.
```

This means the encoder records the existing bit pattern exactly as is, without modification:

```
Infinity   → write bits as-is
-0.0       → write bits as-is; distinguished from 0.0
NaN        → write bits as-is
```

A key point regarding `NaN`:

```
CPU A

NaN

↓

0x7FC00001

CPU B

NaN

↓

0x7FC01234
```

There are two distinct bit patterns, both representing `NaN`. If two implementations preserve these bits exactly, the resulting bytes will differ.

This does not violate the protocol. The serialized value is the IEEE 754 bit pattern, not the abstract concept of "NaN". The compatibility guarantee between SDKs (section §13) applies to the input bit pattern, not to the "NaN value" itself.

Implementations MUST NOT replace `NaN` with a normalized bit pattern.

## 2.4 Bool Type

```
The encoder is permitted to emit ONLY 0x00 or 0x01.

```

No other values ​​may be written - including those the source language considers "true" (e.g., `0xFF`, `0x02`, or a non-null pointer).

If the decoder encounters a byte other than `0x00` or `0x01`, the byte stream is invalid (§10). "Non-zero is true" semantics must not be applied. ---
# 3. String

A character string is represented as follows:

```
Length (UInt32)

↓

UTF-8 bytes
```

`Length` is the **number of UTF-8 bytes**, not the number of characters.

```
ABC

↓

03 00 00 00

41 42 43
```

The byte sequence must be valid according to the UTF-8 standard.

# 4. Byte

```
Length (UInt32)

↓

Raw bytes
```

Similar to `String` but not constrained by UTF-8.

# 5. Model

A Model is a type of Cyclone consisting of an ordered list of fields, where each field contains a Cyclone type.

That is the complete definition. Which concept in your language a Model corresponds to - whether a `class`, `struct`, `record`, `data class`, `dict`, or a group of individual variables - is outside the scope of the Specification. Two languages ​​using different concepts must still produce the exact same byte sequence, because what is serialized is the ordered list of fields, not the language construct containing them.

A Model is represented by concatenating the bytes of each field in their defined order.

```
Player

Hp

↓

UInt32

Name

↓

String

↓

Bytes
```

There is no metadata, no field ID, and no padding between fields.

## 5.1 Field order

Fields MUST be serialized in the order of their declaration.

Field order is part of the protocol. Changing the field order alters the entire byte sequence.

Key point: the order during transmission (on the wire) is the declaration order, not the memory layout order. Compilers are permitted to rearrange fields in RAM to minimize padding; this MUST NOT alter even a single byte of the output data.

```
Declaration       Possible RAM layout       On the wire
───────────       ───────────────────       ─────────────────
a: u8             b (4 bytes)               a
b: u32            a (1 byte)                b
c: u8             c (1 byte)                c
+ padding                 (no padding)
```

Any implementation that determines field order based on memory layout, reflection order, or any source other than the declaration order is an implementation error. ---

# 6. Array

```
UInt32 Count

↓

Element 1

↓

Element 2

↓

...
```
`Count` is the **number of elements**, not the number of bytes. Each element is written according to the specific byte format of type `T`.

---

# 7. Enum

```
UInt32 value
```

```
Enums are always represented as UInt32.

This is a protocol design decision,
not a storage optimization.

```

No `u8`, no `u16`, no `i32`, and no variation based on the number of members. Every Enum - regardless of size - is exactly 4 bytes in Little Endian format.

Rationale: compact specification, simple compiler implementation, fast decoding, and no need for negotiation between parties.

A value outside the defined set → invalid byte stream. No graceful degradation, no skipping.

---

# 8. Encoder

To create a Model:

```
1. Write the first field.

2. Write the second field immediately after.

3. Do not insert any additional bytes.

4. The final byte is the last byte of the last field.

```

---
# 9. Decoder

When reading a Model:

```
1. Read the first field.

2. Advance the pointer by the exact number of bytes used by that field.

3. Proceed to the next field.

4. Repeat until the end of the Model.

```

If the number of remaining bytes is less than the number required for the field, the pointer position must be distinguished:

```
The pointer is in the middle of a field (partially read) and bytes run out before the field is fully read
→ Invalid byte stream (unexpected EOF, §10)

The previous field was fully read, the pointer is at the boundary between two fields, and bytes run out before the next field reads any bytes
→ Not an error; see Version Differences (§9.1)

```
If all fields of the Model have been read and bytes still remain in the byte stream - those remaining bytes do not constitute an error either; see §9.1.

## 9.1 Version Differences

A Model is a user-defined object, and that definition changes over time: a new field is added to the end of the Model. At any given time, the writer and the reader may be running two different versions of the Model - this is known as a version difference.

```
Missing bytes at the end
────────────────────────
The writer uses an older Model (fewer fields).
The reader uses a newer Model (more fields).
The data stream ends exactly at a field boundary
→ The reader's remaining fields have no data.
```

```
Trailing bytes
────────────────
The writer uses a newer Model (more fields).
The reader uses an older Model (fewer fields).
After reading all fields known to the reader, bytes remain in the stream
→ the extra bytes belong to fields unknown to the reader.

```

In both cases, the decoder MUST treat this as a valid stream byte.

Rules for stopping reading:

```
1. Missing bytes at a field boundary
→ stop reading the Model there; remaining fields are considered absent.

2. Extra bytes after the last field known to the Model
→ ignore the extra bytes; do not continue reading.

```

Version differences are valid only when new fields are always appended to the end of the Model:

```
Inserting a field in the middle, removing an existing field, or changing the field order violates the field ordering in §5.1 and falls outside the scope of this section - this constitutes a protocol change, not a version difference.

```

How an implementation represents "missing fields" (default values, `Option<T>`, application-level exceptions, etc.) is outside the scope of the Specification, similar to error reporting in §10.

A model nested within the field of another model applies this rule at its own level: a missing sub-model or extra bytes at its own field boundary also constitute a version difference, not an error.

# 10. Invalid byte stream

| Error | Byte stream condition |
|-----|---------------------------|
| Unexpected EOF | Remaining bytes are fewer than the field's required bytes, and the pointer has partially read that field (missing bytes at a field boundary do not constitute an error – see §9.1) |
| Invalid Boolean | The byte for a `bool` is neither `0x00` nor `0x01` |
| Invalid Enum | The `u32` value is not within the defined set of values ​​|
| Invalid UTF-8 | The byte range of a `String` is not a valid UTF-8 string |
| Length overflow | The length/count field exceeds the remaining bytes or exceeds a configuration limit (§12) |

How an implementation reports an error - throwing an exception, returning an error, setting a flag, toggling GPIO pins - is outside the scope of the Specification.

## 10.1 Length overflow error

```
Implementations MUST reject length values ​​that exceed the available remaining bytes.

```
This check must occur prior to memory allocation.

```
Length = 100

5 bytes remaining in data packet

↓

Error
```

This is a mandatory constraint: independent of configuration and independent of implementation. A length that the byte stream itself cannot satisfy always constitutes an invalid byte stream.

The error name is the same, but the nature differs from the configuration limits in §12:

| Source | Condition | Attribute |
|-------|-----------|-----------|
| Byte stream | `length > remaining bytes` | Mandatory – any implementation MUST reject |
| Configuration | `length > MaxStringLength…` | Non-mandatory – depends on each party's configuration | Applying both simultaneously:

```
effective limit = min(remaining bytes, configured limit)
```

---

# 11. Not present on the wire

```
- Padding             - Alignment        - Nullable / Option<T>
- Version field/tag   - Compression      - Checksum
- Field ID / tag      - Object header    - Default value
```

No version field/tag is written to the byte stream - this is a statement regarding the byte layout, not a statement regarding compatibility between two Model versions. How the decoder handles differences between the writing Model and the reading Model is described in §9.1 (Version differences); this does not contradict the table above.

---

# 12. Limits – Non-normative

A `u32` for length/count allows for up to 4GB. An implementation that allocates based on length without validation is vulnerable to a denial-of-service (DoS) attack.

Therefore, implementations SHOULD have configurable limits (`MaxStringLength`, `MaxBytesLength`, `MaxArrayCount`, `MaxPacketSize`).

These limits are not part of the protocol. Two endpoints with different configurations MAY disagree on whether to accept a byte stream.

Configurable limits are supplementary to, not a replacement for, the normative checks in §10.1. No configuration allows accepting a length greater than the number of remaining bytes.

---

# 13. Ensuring multi-SDK compatibility

Every v1.1 implementation MUST produce identical byte sequences for the same input data.

For floating-point numbers, "same input data" means the same IEEE 754 bit pattern (§2.3), not the same mathematical value.

Otherwise, it is an error in the implementation, not in the protocol.**

# 14. Test Vector

A test vector is a **(value, byte)** pair.

```
u32   100          → [64 00 00 00]
String "abc"       → [03 00 00 00 61 62 63]
Array<u32> [1,2,3] → [03 00 00 00 01 00 00 00 02 00 00 00 03 00 00 00]
bool  false / true → [00] / [01]
bool  [02]         → invalid
f32   3.14         → [C3 F5 48 40]
f32   Infinity     → [00 00 80 7F]
f32   -0.0         → [00 00 00 80]
enum  Status::OK   → [00 00 00 00]
enum  [63 00 00 00] with value set = {0,1} → invalid
String len=2 data=[FF FE] → invalid (UTF-8)
String len=[64 00 00 00] but only 5 bytes remain → invalid (Length Overflow)

model Item { id: u32; name: String }
Item{ id=42, name="Sword" } → [2A 00 00 00 05 00 00 00 53 77 6F 72 64]

model ItemV1 { id: u32 }
model ItemV2 { id: u32; name: String }

Written by ItemV1, read by ItemV2:
[2A 00 00 00] → id=42, bytes run out right before the `name` field → valid, version mismatch (§9.1);
``` `name` has no data

Written by ItemV2, read by ItemV1:
[2A 00 00 00 05 00 00 00 53 77 6F 72 64] → id=42, 9 bytes remaining after the `id` field → valid, version mismatch (§9.1); extra data is ignored

Written by ItemV2, read by ItemV2, but bytes are truncated midway through the `name` field:
[2A 00 00 00 05 00 00 00 53 77] → length=5 but only 2 bytes of data remain → invalid (Unexpected EOF); ​​NOT a version mismatch because the byte data runs out midway through a field, rather than at a field boundary
```

Test vectors for the `float` type MUST be written using bit patterns, not value names:

```
f32 bit pattern 0x7FC00000 → [00 00 C0 7F]
f32 bit pattern 0x7FC00001 → [01 00 C0 7F]
```

Both are `NaN`. Writing `f32 NaN → [00 00 C0 7F]` is incorrect because it implies a canonical NaN value, which section §2.3 does not specify. A conformance test suite relying on "NaN value" comparisons would report false errors on platforms that generate different bit patterns.

# 15. Complete example

```
model Vector3 { x: f32; y: f32; z: f32 }

model GameMessage {
playerId:   u32
playerName: String
position:   Vector3
health:     u32
isAlive:    bool
}
```

Values:

```
playerId   = 42
playerName = "Knight"
position   = Vector3 { x = 10.5, y = 20.3, z = -5.1 }
health     = 100
isAlive    = true
```

Byte data:

```
playerId   → [2A 00 00 00]
playerName → [06 00 00 00] [4B 6E 69 67 68 74]
position   → [00 00 28 41] [66 66 A2 41] [33 33 A3 C0]
health     → [64 00 00 00]
isAlive    → [01]

[2A 00 00 00 06 00 00 00 4B 6E 69 67 68 74
00 00 28 41 66 66 A2 41 33 33 A3 C0
64 00 00 00 01]
```

Reading back: read 4 bytes → `playerId = 42`; read 4 bytes (length = 6), advance pointer by 6 bytes → `playerName = "Knight"`; read 3 × 4 bytes → `position`; read 4 bytes → `health = 100`; Read 1 byte → `isAlive = true`; the pointer stops exactly at the end of the data stream.
