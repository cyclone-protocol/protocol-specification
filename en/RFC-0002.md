# 0. What a Specification Is

The Specification answers exactly one question:

> If I want to **produce** or **read** a Cyclone byte array, what must I do?

The Specification describes:

```
What shape the bytes must have.
```

The Specification does NOT describe:

```
Which API you must use to produce bytes.
That you must use annotations.
That you must generate code.
```

So the same Specification can be implemented with:

```
Code generator
Reflection
By hand
FPGA
PLC
Microcontroller
Assembly
```

As long as, in the end:

```
Logical Data  →  Bytes
Bytes  →  Logical Data
```

both follow the rules of the Specification exactly.

---

# 1. Rules

```
Little Endian is always used.
UInt32 always occupies exactly 4 bytes.
Enum is always UInt32.
Float is written as its raw IEEE 754 bit pattern.
Models contain no metadata.
Fields are written in declaration order, not memory layout order.
No padding.
No alignment.
No tag id.
No object header.
Same data → same byte sequence.
```

---

# 2. Primitives

## 2.1 UInt32

A `UInt32` value is represented by exactly 4 bytes, Little Endian.

```
Value

100

↓

Bytes

64 00 00 00
```

## 2.2 Full table

| Type | Byte shape | Size |
|------|------------|------|
| `bool` | `0x00` = false, `0x01` = true, anything else → invalid | 1 |
| `i8` / `u8` | 1 byte | 1 |
| `i16` / `u16` | 2 bytes Little Endian | 2 |
| `i32` / `u32` | 4 bytes Little Endian | 4 |
| `i64` / `u64` | 8 bytes Little Endian | 8 |
| `f32` | IEEE 754 single, Little Endian, no normalization | 4 |
| `f64` | IEEE 754 double, Little Endian, no normalization | 8 |

No varint, no variable-length encoding.

## 2.3 Float - Bit Pattern

```
Floating-point values are serialized by preserving
their IEEE 754 bit representation exactly.

No normalization or canonicalization is performed.
```

Meaning the encoder writes the **exact bit pattern** it holds, unmodified:

```
Infinity   → raw bits
-0.0       → raw bits, distinct from 0.0
NaN        → raw bits
```

What must be understood about `NaN`:

```
CPU A

NaN

↓

0x7FC00001

CPU B

NaN

↓

0x7FC01234
```

Two different bit patterns, both `NaN`. If two implementations both "preserve the bits", the bytes they produce will differ.

This does **not** violate the protocol. What is serialized is the **IEEE 754 bit pattern**, not the logical notion "NaN". The Cross-SDK Guarantee (§13) is stated over the same input bit pattern, not over the same "NaN value".

An implementation MUST NOT replace `NaN` with any canonical bit pattern.

## 2.4 Bool

```
Encoder MUST only emit 0x00 or 0x01.
```

No other value may be written - including values the source language considers truthy (`0xFF`, `0x02`, a non-null pointer).

A decoder that encounters a byte other than `0x00` / `0x01` has an invalid byte stream (§10). It must not treat "non-zero means true".

# 3. String

A string is represented by:

```
UInt32 Length

↓

UTF-8 Bytes
```

`Length` is the **number of UTF-8 bytes**, not the number of characters.

```
ABC

↓

03 00 00 00

41 42 43
```

The byte region must be valid UTF-8.

---

# 4. Bytes

```
UInt32 Length

↓

Raw Bytes
```

Same as `String` but with no UTF-8 constraint.

---

# 5. Model

A **Model** is a Cyclone type consisting of an **ordered list of fields**, each field carrying a Cyclone type.

That is the whole definition. Which concept in your language a Model maps to - `class`, `struct`, `record`, `data class`, `dict`, or a handful of loose variables - is **outside** the Specification. Two languages using two different concepts must still produce the same byte sequence, because what gets serialized is the ordered list of fields, not the language construct holding it.

A Model is represented by concatenating the bytes of each field in definition order.

```
Player

Hp

↓

UInt32

Name

↓

String

↓

Bytes
```

No metadata, no field ID, no padding between fields.

## 5.1 Field Ordering

```
Fields MUST be serialized in declaration order.

Memory layout,
compiler optimization,
padding,
alignment,
or runtime object layout
MUST NOT affect serialization order.
```

Field order is part of the protocol. Reordering fields changes the entire byte sequence.

The consequence to internalize: the order on the wire is **declaration** order, not memory order. A compiler may reorder fields in RAM to reduce padding; that MUST NOT change a single byte of the output.

```
Declaration       Possible RAM layout       Wire
───────────       ───────────────────       ────
a: u8             b (4 bytes)               a
b: u32            a (1 byte)                b
c: u8             c (1 byte)                c
                  + padding                 (no padding)
```

An implementation that takes field order from memory layout, from reflection order, or from any source other than declaration order has an **implementation bug**.

---

# 6. Array

```
UInt32 Count

↓

Element 1

↓

Element 2

↓

...
```

`Count` is the **number of elements**, not the number of bytes. Each element is written in the exact byte shape of type `T`.

---

# 7. Enum

```
UInt32 Value
```

```
Enums are always represented as UInt32.

This is a protocol design decision
rather than a storage optimization.
```

No `u8`, no `u16`, no `i32`, no variant sized by member count. Every enum, at every size, is exactly 4 bytes Little Endian.

The reason: a small spec, a simple compiler, fast decoding, and nothing for two peers to negotiate.

A value outside the defined set makes the byte stream invalid. No graceful degradation, no skipping.

---

# 8. Encoder

To produce a Model:

```
1. Write the first field.
2. Write the second field immediately after it.
3. Insert no other bytes whatsoever.
4. The final byte is the last byte of the last field.
```

---

# 9. Decoder

To read a Model:

```
1. Read the first field.
2. Advance the read cursor by exactly the bytes that field used.
3. Continue with the next field.
4. Repeat until the Model ends.
```

If fewer bytes remain than the field requires, the cursor position matters:

```
The cursor is inside a field (part of that field
has already been read) and bytes run out before
the field finishes reading
  → the byte stream is invalid (Unexpected EOF, §10)

The previous field finished reading in full, the
cursor sits exactly on the boundary between two
fields, and bytes run out before the next field
reads any byte at all
  → not an error, see Version Skew (§9.1)
```

Reading every field of the Model while bytes still remain in the stream is likewise not an error - see §9.1.

## 9.1 Version Skew

A Model is a user-defined artifact, and that definition changes over time: a new field gets added to the end of a Model. At any given moment the writer and the reader MAY be running two different versions of that Model - this is called **version skew**.

```
Missing bytes at the end
─────────────────────────
The writer uses an older Model (fewer fields).
The reader uses a newer Model (more fields).
The stream ends exactly on a field boundary
  → the reader's remaining fields have no data.
```

```
Extra bytes at the end
───────────────────────
The writer uses a newer Model (more fields).
The reader uses an older Model (fewer fields).
Every field the reader knows about is read, bytes remain
  → the leftover bytes belong to a field the reader
    does not know about.
```

In both cases the decoder MUST treat this as a valid byte stream.

Stopping rule:

```
1. Bytes run out exactly on a field boundary
     → stop reading the Model there; the remaining
       fields are treated as absent.
2. Bytes remain after the last field the Model knows
     → discard the leftover bytes, read no further.
```

Version skew is only valid when new fields are always appended to the **end** of the Model:

```
Inserting a field in the middle, removing an existing
field, or reordering fields breaks the field ordering
in §5.1 and is outside the compatibility this section
covers - that is a protocol change, not version skew.
```

How an implementation represents an "absent field" (a default value, `Option<T>`, an application-level exception...) is outside the Specification, the same way error reporting is outside it in §10.

A Model nested inside a field of another Model follows this same rule at its own level: a nested Model with missing or extra bytes at its own field boundary is also version skew, not an error.

# 10. Invalid Byte Streams

| Error | Condition on the byte stream |
|-------|------------------------------|
| Unexpected EOF | Remaining bytes fewer than the field requires, and the cursor has already read part of that field (bytes missing exactly on a field boundary is not an error - see §9.1) |
| Invalid Bool | A `bool` byte that is neither `0x00` nor `0x01` |
| Invalid Enum | A `u32` value outside the defined value set |
| Invalid UTF-8 | A `String` byte region that is not valid UTF-8 |
| Length Overflow | A length/count field larger than the remaining bytes, or beyond a configured limit (§12) |

How an implementation reports the error - throw, return an error, set a flag, pull a GPIO pin - is outside the Specification.

## 10.1 Length Overflow

```
Implementation MUST reject
length values that exceed
available remaining bytes.
```

This check must happen **before allocating memory**.

```
Length = 100

5 bytes left in the packet

↓

Error
```

This is a **normative** constraint: independent of configuration, independent of implementation. A length that the byte stream itself cannot satisfy makes the byte stream invalid, always.

Same error name, different nature from the configured limits in §12:

| Source | Condition | Nature |
|--------|-----------|--------|
| Byte stream | `length > remaining bytes` | **Normative** - every implementation MUST reject |
| Configuration | `length > MaxStringLength…` | Non-normative - per-peer configuration |

Both apply simultaneously:

```
effective_limit = min(remaining_bytes, configured_limit)
```

---

# 11. Does Not Exist On The Wire

```
✗ Padding             ✗ Alignment        ✗ Nullable / Option<T>
✗ Version field/tag   ✗ Compression      ✗ Checksum
✗ Field ID / tag      ✗ Object header    ✗ Default value
```

No version field or tag is written into the bytes - this is a statement about **byte shape**, not a statement about compatibility between two Model versions. How a decoder handles a mismatch between the writer's and the reader's Model is described in §9.1 (Version Skew), and does not contradict the table above.

---

# 12. Limits - Non-normative

A `u32` length/count allows up to 4GB. An implementation that allocates from an unchecked length is a DoS target.

Therefore implementations SHOULD have configurable limits (`MaxStringLength`, `MaxBytesLength`, `MaxArrayCount`, `MaxPacketSize`).

These limits are **not part of the protocol**. Two peers with different configurations MAY disagree on whether a byte stream is acceptable.

Configured limits are **additive**, not a replacement for the normative check in §10.1. No configuration may permit accepting a `length` larger than the remaining bytes.

---

# 13. Cross-SDK Guarantee

```
Every v1 implementation MUST produce identical byte sequences
for the same input data.
```

For floats, "the same input data" means **the same IEEE 754 bit pattern** (§2.3), not the same mathematical value.

If it does not, that is an implementation bug, not a protocol one.

---

# 14. Test Vectors

A test vector is a pair of **(value, bytes)**.

```
u32   100          → [64 00 00 00]
String "abc"       → [03 00 00 00 61 62 63]
Array<u32> [1,2,3] → [03 00 00 00 01 00 00 00 02 00 00 00 03 00 00 00]
bool  false / true → [00] / [01]
bool  [02]         → invalid
f32   3.14         → [C3 F5 48 40]
f32   Infinity     → [00 00 80 7F]
f32   -0.0         → [00 00 00 80]
enum  Status::OK   → [00 00 00 00]
enum  [63 00 00 00] where value set = {0,1} → invalid
String len=2 data=[FF FE] → invalid (UTF-8)
String len=[64 00 00 00] but 5 bytes remain → invalid (Length Overflow)

model Item { id: u32; name: String }
Item{ id=42, name="Sword" } → [2A 00 00 00 05 00 00 00 53 77 6F 72 64]

model ItemV1 { id: u32 }
model ItemV2 { id: u32; name: String }

Written by ItemV1, read by ItemV2:
[2A 00 00 00] → id=42, bytes run out exactly on the boundary before name → valid, version skew (§9.1); name has no data

Written by ItemV2, read by ItemV1:
[2A 00 00 00 05 00 00 00 53 77 6F 72 64] → id=42, 9 bytes remain after the id field → valid, version skew (§9.1); the leftover is discarded

Written by ItemV2, read by ItemV2, but the bytes are truncated in the middle of the name field:
[2A 00 00 00 05 00 00 00 53 77] → length=5 but only 2 bytes of data remain → invalid (Unexpected EOF), NOT version skew, because the bytes run out in the middle of a field, not on a boundary
```

Float test vectors MUST be written as **bit patterns**, not as value names:

```
f32 bit pattern 0x7FC00000 → [00 00 C0 7F]
f32 bit pattern 0x7FC00001 → [01 00 C0 7F]
```

Both are `NaN`. Writing `f32 NaN → [00 00 C0 7F]` is **wrong** because it implies a canonical NaN that §2.3 never specifies. A conformance suite comparing on "the NaN value" will fail incorrectly on platforms that produce a different bit pattern.

# 15. Complete Example

```
model Vector3 { x: f32; y: f32; z: f32 }

model GameMessage {
  playerId:   u32
  playerName: String
  position:   Vector3
  health:     u32
  isAlive:    bool
}
```

Values:

```
playerId   = 42
playerName = "Knight"
position   = Vector3 { x = 10.5, y = 20.3, z = -5.1 }
health     = 100
isAlive    = true
```

Bytes:

```
playerId   → [2A 00 00 00]
playerName → [06 00 00 00] [4B 6E 69 67 68 74]
position   → [00 00 28 41] [66 66 A2 41] [33 33 A3 C0]
health     → [64 00 00 00]
isAlive    → [01]

[2A 00 00 00 06 00 00 00 4B 6E 69 67 68 74
 00 00 28 41 66 66 A2 41 33 33 A3 C0
 64 00 00 00 01]
```

Reading it back: read 4 bytes → `playerId = 42`; read 4 bytes of length = 6, advance the cursor 6 bytes → `playerName = "Knight"`; read 3 × 4 bytes → `position`; read 4 bytes → `health = 100`; read 1 byte → `isAlive = true`; the cursor stops exactly at the end of the stream.
