# RFC-0003 - Conformance

## Trạng thái

Final

## Phiên bản

1.1.0

## Tác giả

Hà Duy Thắng

---

# 0. Mục tiêu

Tài liệu này trả lời một câu hỏi:

> Làm sao biết một implementation có đúng hay không?

Câu trả lời:

```
Chạy test vector

↓

100%

↓

Fomoxa Compatible
```

Việc đánh giá không dựa vào phỏng vấn, code review hay lời cam kết của tác giả, mà chỉ dựa vào kết quả chạy test vector và so byte.

---

# 1. Định nghĩa

## 1.1 Fomoxa Compatible

```
Một implementation là Fomoxa Compatible
khi và chỉ khi nó vượt qua 100% test vector trong tài liệu này.
```

Không có mức "tương thích một phần" như 98%. Một vector trượt nghĩa là tồn tại dữ liệu mà implementation này và implementation khác cho kết quả khác nhau, và khác biệt đó xảy ra âm thầm trên production.

## 1.2 Test vector là gì?

Test vector là một cặp:

```
(giá trị logic, chuỗi byte)
```

Nó không phải cặp (lời gọi hàm, giá trị trả về). Giống RFC-0002, vector không nhắc tới tên phương thức, ngôn ngữ hay API.

## 1.3 Năm phép kiểm tra

Mỗi vector dùng cho tối đa năm phép kiểm tra:

| Kiểm tra | Nội dung | Kết quả mong đợi |
|-----------|----------|------------------|
| Encode | giá trị → byte | Byte giống hệt vector |
| Decode | byte → giá trị | Giá trị bằng vector |
| Round-trip | giá trị → byte → giá trị | Bằng giá trị ban đầu |
| Reject | byte không hợp lệ → decode | BẮT BUỘC bị từ chối |
| Compat | byte đọc bởi Model phiên bản khác (RFC-0002 §9.1) → decode | KHÔNG ĐƯỢC từ chối |

Vector ở §3–§8.5 dùng cho ba phép đầu. Vector ở §8.6 chỉ dùng cho Compat. Vector ở §9 chỉ dùng cho Reject.

---

# 2. Quy tắc chạy

```
1. Mọi vector PHẢI pass. Không ngoại lệ, không skip.
2. So sánh là so byte, không so chuỗi.
3. Vector Reject BẮT BUỘC bị từ chối; đây không phải khuyến nghị.
4. Giá trị trả về PHẢI bằng giá trị gốc, không phải "xấp xỉ".
```

Không được làm những việc sau để pass:

```
- Chuẩn hoá mẫu bit NaN
- Sắp xếp lại field
- Bỏ qua enum không xác định
- Coi "khác 0 là đúng"
```

Mỗi việc trên làm test pass ở implementation này nhưng fail khi kiểm tra chéo với implementation khác.

# 4. Float

Float được kiểm tra bằng mẫu bit, không bằng tên giá trị (RFC-0002 §2.3).

## 4.1 f32

| ID | Mẫu bit | Giá trị | Byte |
|----|-------------|---------|------|
| F-001 | `0x00000000` | `0.0` | `[00 00 00 00]` |
| F-002 | `0x80000000` | `-0.0` | `[00 00 00 80]` |
| F-003 | `0x3F800000` | `1.0` | `[00 00 80 3F]` |
| F-004 | `0x3FC00000` | `1.5` | `[00 00 C0 3F]` |
| F-005 | `0x4048F5C3` | `3.14` | `[C3 F5 48 40]` |
| F-006 | `0x7F800000` | `+Infinity` | `[00 00 80 7F]` |
| F-007 | `0xFF800000` | `-Infinity` | `[00 00 80 FF]` |

## 4.2 f64

| ID | Mẫu bit | Giá trị | Byte |
|----|-------------|---------|------|
| F-020 | `0x0000000000000000` | `0.0` | `[00 00 00 00 00 00 00 00]` |
| F-021 | `0x8000000000000000` | `-0.0` | `[00 00 00 00 00 00 00 80]` |
| F-022 | `0x3FF0000000000000` | `1.0` | `[00 00 00 00 00 00 F0 3F]` |
| F-023 | `0x7FF0000000000000` | `+Infinity` | `[00 00 00 00 00 00 F0 7F]` |

## 4.3 NaN: giữ nguyên mẫu bit

| ID | Mẫu bit vào | Byte | Mẫu bit ra |
|----|-----------------|------|----------------|
| F-030 | `0x7FC00000` | `[00 00 C0 7F]` | `0x7FC00000` |
| F-031 | `0x7FC00001` | `[01 00 C0 7F]` | `0x7FC00001` |
| F-032 | `0xFFC00000` | `[00 00 C0 FF]` | `0xFFC00000` |

Cả ba đều là `NaN`. Nhóm vector này bắt lỗi chuẩn hoá NaN: F-031 xuất ra `[00 00 C0 7F]` nghĩa là implementation đã sửa dữ liệu người dùng.

Round-trip NaN PHẢI so mẫu bit, không dùng toán tử `==` của ngôn ngữ. Ở hầu hết ngôn ngữ, `NaN == NaN` trả về `false`, nên phép so sánh bằng `==` luôn trượt.

## 4.4 Không normalize

| ID | Kiểm tra | Kỳ vọng |
|----|----------|---------|
| F-040 | `0.0` và `-0.0` | Byte khác nhau (F-001 ≠ F-002) |
| F-041 | Round-trip `-0.0` | Vẫn là `-0.0`, không thành `0.0` |

# 5. String

`Length` là số byte UTF-8, không phải số ký tự.

| ID | Giá trị | Byte |
|----|---------|------|
| S-001 | `""` | `[00 00 00 00]` |
| S-002 | `"abc"` | `[03 00 00 00 61 62 63]` |
| S-003 | `"Alice"` | `[05 00 00 00 41 6C 69 63 65]` |
| S-004 | `"中"` | `[03 00 00 00 E4 B8 AD]` |
| S-005 | `"Xin chào"` | `[09 00 00 00 58 69 6E 20 63 68 C3 A0 6F]` |

S-004 và S-005 kiểm tra việc đếm byte thay vì đếm ký tự.

```
"中"

1 ký tự
3 byte

↓

Length MUST = 3
```

```
"Xin chào"

8 ký tự
9 byte   (à = C3 A0, 2 byte)

↓

Length MUST = 9
```

Implementation nào ghi `Length = 1` cho S-004 hoặc `Length = 8` cho S-005 là đang đếm ký tự, lỗi thường gặp nhất ở C#, Java và JavaScript.

# 6. Bytes

| ID | Giá trị | Byte |
|----|---------|------|
| B-001 | `[]` | `[00 00 00 00]` |
| B-002 | `[FF FE]` | `[02 00 00 00 FF FE]` |
| B-003 | `[00 00]` | `[02 00 00 00 00 00]` |

B-002 chính là chuỗi byte mà `String` phải từ chối (N-020). Cùng chuỗi byte cho kết quả khác nhau tùy kiểu. Kiểu được quyết định ở tầng schema; decoder không suy luận từ nội dung.

# 7. Array

`Count` là số phần tử, không phải số byte.

| ID | Kiểu | Giá trị | Byte |
|----|------|---------|------|
| A-001 | `Array<u32>` | `[]` | `[00 00 00 00]` |
| A-002 | `Array<u32>` | `[1,2,3]` | `[03 00 00 00 01 00 00 00 02 00 00 00 03 00 00 00]` |
| A-003 | `Array<String>` | `["a","bc"]` | `[02 00 00 00 01 00 00 00 61 02 00 00 00 62 63]` |
| A-004 | `Array<Array<u8>>` | `[[1,2],[]]` | `[02 00 00 00 02 00 00 00 01 02 00 00 00 00]` |
| A-005 | `Array<bool>` | `[true,false,true]` | `[03 00 00 00 01 00 01]` |

A-002 bắt lỗi nhầm số phần tử với số byte. Giá trị đúng là `3`, không phải `12`.

A-004 bắt lỗi Array lồng nhau: `count = 2`, phần tử đầu `count = 2` + `[01 02]`, phần tử thứ hai `count = 0` và không byte thừa.

# 8. Model & Enum

## 8.1 Model cơ bản

```
model Item { id: u32; name: String }
```

| ID | Giá trị | Byte |
|----|---------|------|
| T-001 | `Item{ id=42, name="Sword" }` | `[2A 00 00 00 05 00 00 00 53 77 6F 72 64]` |

## 8.2 Model rỗng

```
model Empty { }
```

| ID | Giá trị | Byte |
|----|---------|------|
| T-002 | `Empty{}` | `[]` - 0 byte |

## 8.3 Model lồng nhau

```
model Vector3 { x: f32; y: f32; z: f32 }
model Body    { pos: Vector3; hp: u32 }
```

| ID | Giá trị | Byte |
|----|---------|------|
| T-003 | `Vector3{1.5, 2.5, 3.5}` | `[00 00 C0 3F 00 00 20 40 00 00 60 40]` |
| T-004 | `Body{ pos=Vector3{1.5,2.5,3.5}, hp=100 }` | `[00 00 C0 3F 00 00 20 40 00 00 60 40 64 00 00 00]` |

Model lồng nhau được ghi nội tuyến: không tiền tố độ dài, không dấu phân cách, không header.

## 8.4 Thứ tự field

```
model Mixed { a: u8; b: u32; c: u8 }
```

| ID | Giá trị | Byte | Tổng |
|----|---------|------|------|
| T-010 | `Mixed{ a=1, b=2, c=3 }` | `[01 02 00 00 00 03]` | 6 byte |

Vector này bắt hai lỗi cùng lúc:

```
12 byte → implementation đang chép bố cục bộ nhớ (có padding/alignment)

[02 00 00 00 01 03] → implementation đã sắp xếp lại field
```

Thứ tự trên wire luôn là thứ tự khai báo (RFC-0002 §5.1).

```
model Order { z: u8; a: u8 }
```

| ID | Giá trị | Byte |
|----|---------|------|
| T-011 | `Order{ z=1, a=2 }` | `[01 02]` |

Kết quả `[02 01]` nghĩa là implementation đang sắp field theo bảng chữ cái. Lỗi này thường gặp khi lấy field bằng reflection rồi sắp xếp để có thứ tự "ổn định".

## 8.5 Enum

```
enum PlayerState { Idle=0, Walk=1, Run=2, Jump=3 }
```

| ID | Giá trị | Byte |
|----|---------|------|
| E-001 | `Idle` | `[00 00 00 00]` |
| E-002 | `Walk` | `[01 00 00 00]` |
| E-003 | `Jump` | `[03 00 00 00]` |

| ID | Kiểm tra | Kỳ vọng |
|----|----------|---------|
| E-010 | Kích thước encode của mọi enum | Luôn 4 byte, bất kể số thành viên |

E-010 bắt lỗi implementation "tối ưu" một enum 4 thành viên xuống 1 byte. Enum luôn là `UInt32` theo quyết định giao thức ở RFC-0002 §7.

## 8.6 Chênh lệch phiên bản

```
model ItemV1 { id: u32 }
model ItemV2 { id: u32; name: String }
```

| ID | Model bên ghi | Model bên đọc | Byte | Kỳ vọng |
|----|-----------|-----------|------|---------|
| V-001 | ItemV1 | ItemV2 | `[2A 00 00 00]` | KHÔNG ĐƯỢC từ chối; `id=42`, `name` không có dữ liệu |
| V-002 | ItemV2 | ItemV1 | `[2A 00 00 00 05 00 00 00 53 77 6F 72 64]` | KHÔNG ĐƯỢC từ chối; `id=42`, 9 byte thừa bị bỏ qua |

V-001 và V-002 là vector Compat (§1.3). Chúng chỉ hợp lệ khi byte thiếu hoặc thừa nằm đúng tại ranh giới field, không phải giữa field.

So với N-022: cả hai đều là "thiếu byte", nhưng N-022 thiếu byte giữa field `String` (đã đọc độ dài, dữ liệu chưa đủ), nên nó PHẢI bị từ chối. Nhầm hai trường hợp này là lỗi conformance thường gặp nhất khi thêm hỗ trợ chênh lệch phiên bản (RFC-0002 §9.1).

# 9. Reject vector

Các luồng byte dưới đây PHẢI bị từ chối. Implementation thường bỏ sót nhóm này, và đây cũng là nhóm phát hiện được nhiều lỗi nhất.

| ID | Kiểu | Byte đầu vào | Lý do không hợp lệ |
|----|----------|----------|-----------|
| N-001 | `bool` | `[02]` | Không phải `00`/`01` |
| N-002 | `bool` | `[FF]` | Không phải `00`/`01` |
| N-010 | `u32` | `[00 00 00]` | Thiếu byte |
| N-011 | `u64` | `[01 02 03 04]` | Thiếu byte |
| N-020 | `String` | `[02 00 00 00 FF FE]` | Không phải UTF-8 hợp lệ |
| N-021 | `String` | `[03 00 00 00 ED A0 80]` | Surrogate UTF-8 → không hợp lệ |
| N-022 | `String` | `[05 00 00 00 41 6C 69]` | `Length = 5` nhưng chỉ còn 3 byte |
| N-023 | `String` | `[64 00 00 00 41 6C 69 63 65]` | `Length = 100` nhưng chỉ còn 5 byte |
| N-030 | `Array<u32>` | `[03 00 00 00 01 00 00 00]` | `Count = 3` nhưng chỉ còn 1 phần tử |
| N-031 | `Array<u32>` | `[FF FF FF FF]` | `Count = 4294967295` nhưng không còn byte nào |
| N-040 | `enum{0,1}` | `[63 00 00 00]` | Giá trị 99 nằm ngoài tập định nghĩa |
| N-041 | `enum{0,1}` | `[02 00 00 00]` | Giá trị 2 nằm ngoài tập định nghĩa |

## 9.1 Quy tắc cho reject vector

```
Việc từ chối là BẮT BUỘC.
```

Implementation PHẢI từ chối. Phân loại lỗi (EOF không mong đợi / bool không hợp lệ / enum không hợp lệ / UTF-8 không hợp lệ / tràn độ dài) NÊN theo RFC-0002 §10. Conformance không kiểm tra chuỗi thông báo lỗi, vì cách báo lỗi nằm ngoài Specification.

## 9.2 N-023 và N-031: kiểm tra trước khi cấp phát

Hai vector này kiểm tra xem implementation có kiểm tra độ dài trước khi cấp phát không.

```
Count = 4294967295

↓

Nếu implementation cấp phát trước rồi mới đọc

↓

Nó cố cấp phát 16 GB

↓

Hết bộ nhớ / sập chương trình
```

Để chương trình sập rồi bắt ngoại lệ không được tính là pass N-031; luồng byte phải bị từ chối trước khi cấp phát.

# 10. Round-trip

| ID | Kiểm tra |
|----|----------|
| R-001 | Mỗi vector ở §3–§8: `giá trị → byte → giá trị` bằng giá trị gốc |
| R-002 | Mỗi vector ở §3–§8: `byte → giá trị → byte` bằng byte gốc |
| R-003 | Model lồng 3 lớp round-trip chính xác |
| R-004 | `Array` rỗng vẫn là `Array` rỗng sau round-trip, không thành `null` |
| R-005 | `String` rỗng vẫn là `""` sau round-trip, không thành `null` |
| R-006 | `-0.0` vẫn là `-0.0` sau round-trip |
| R-007 | `NaN` giữ nguyên mẫu bit sau round-trip |

R-004 và R-005 bắt lỗi ngôn ngữ chuyển giá trị rỗng thành null hoặc ngược lại. Fomoxa không có `null`. Rỗng và không tồn tại là hai khái niệm khác nhau, và khái niệm sau không có trong v1.1.

# 11. Kiểm thử chéo

Hai implementation cùng pass §3–§10 vẫn phải kiểm tra chéo:

| ID | Kiểm tra |
|----|----------|
| X-001 | A encode → B decode → giá trị đúng |
| X-002 | B encode → A decode → giá trị đúng |
| X-003 | A encode và B encode cùng một dữ liệu → byte giống hệt nhau |

X-003 là phép kiểm tra chặt nhất trong tài liệu và không phụ thuộc vào ngôn ngữ của A và B.

Ma trận kết quả:

| --- | Go | C# | Rust | C |
|----|----|----|----|----|
| Go | - | ✅ | ✅ | ✅ |
| C# | ✅ | - | ✅ | ✅ |
| Rust | ✅ | ✅ | - | ✅ |
| C | ✅ | ✅ | ✅ | - |

# 12. Báo cáo tuân thủ

Implementation công bố kết quả theo dạng:

```
Implementation: fomoxa-go
Phiên bản: 0.3.1
Spec: RFC-0002 v1.1

§3  Primitive        ✅  27/27
§4  Float            ✅  16/16
§5  String           ✅   5/5
§6  Bytes            ✅   3/3
§7  Array            ✅   5/5
§8  Model & Enum     ✅  12/12
§9  Reject           ✅  12/12
§10 Round-trip       ✅   7/7
§11 Cross-impl       ⚠️  chưa kiểm với implementation khác

Kết luận: Fomoxa Compatible
```

Nếu có bất kỳ dòng ❌ nào trong §3–§10:

```
Kết luận: KHÔNG tương thích Fomoxa
```

Không có trạng thái trung gian.

# 13. Những gì KHÔNG thuộc phạm vi conformance

Conformance chỉ xét biểu diễn byte. Các khía cạnh sau không được kiểm tra và không dùng để đánh giá:

| Không kiểm tra | Lý do |
|-----------|--------|
| Hình dạng API (`Encode()`, `WriteU32`…) | Specification không ép một API cụ thể |
| Mã nguồn sinh tự động hay không | Mã viết tay vẫn hợp lệ |
| Việc dùng annotation | Cách thể hiện schema là tự do |
| Nội dung thông báo lỗi | Cơ chế báo lỗi nằm ngoài Specification |
| Hiệu năng, cấp phát, thông lượng | Chúng không làm đổi biểu diễn byte |
| Giá trị mặc định của `MaxStringLength` | Giới hạn cấu hình không thuộc giao thức |

Một implementation chậm hơn 10 lần nhưng pass 100% test vector vẫn là Fomoxa Compatible. Một implementation nhanh hơn mà trượt một vector thì không.
