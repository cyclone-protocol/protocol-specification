# RFC-0002 — Wire Format Specification

## Status

Draft

## Version

1.0.0

## Author

Ha Duy Thang

# 0. Specification là gì

Specification chỉ trả lời một câu hỏi:

> Nếu tôi muốn **tạo** hoặc **đọc** một mảng byte Cyclone thì tôi phải làm như thế nào?

Specification mô tả:

```
Byte phải có hình dạng như thế nào.
```

Specification KHÔNG mô tả:

```
Bạn phải dùng API nào để tạo byte.
Bạn phải dùng annotation.
Bạn phải generate code.
```

Vì vậy cùng một Specification triển khai được bằng:

```
Compiler sinh code
Reflection
Viết tay
FPGA
PLC
Vi điều khiển
Assembly
```

Miễn là cuối cùng:

```
Logical Data  →  Bytes
Bytes  →  Logical Data
```

đều tuân theo đúng các rule của Specification.

---

# 1. Rule

```
Little Endian luôn được sử dụng.
UInt32 luôn chiếm đúng 4 byte.
Enum luôn là UInt32.
Float được ghi nguyên bit pattern IEEE 754.
Struct không chứa metadata.
Các field được ghi đúng theo thứ tự khai báo, không phải layout bộ nhớ.
Không có padding.
Không có alignment.
Không có tag id.
Không có object header.
Cùng dữ liệu → cùng byte sequence.
```

---

# 2. Primitive

## 2.1 UInt32

Một giá trị `UInt32` được biểu diễn bằng đúng 4 byte theo chuẩn Little Endian.

```
Value

100

↓

Bytes

64 00 00 00
```

## 2.2 Bảng đầy đủ

| Kiểu | Hình dạng byte | Kích thước |
|------|----------------|-----------|
| `bool` | `0x00` = false, `0x01` = true, khác → không hợp lệ | 1 |
| `i8` / `u8` | 1 byte | 1 |
| `i16` / `u16` | 2 byte Little Endian | 2 |
| `i32` / `u32` | 4 byte Little Endian | 4 |
| `i64` / `u64` | 8 byte Little Endian | 8 |
| `f32` | IEEE 754 single, Little Endian, không normalize | 4 |
| `f64` | IEEE 754 double, Little Endian, không normalize | 8 |

Không dùng varint, không dùng variable-length encoding.

## 2.3 Float — Bit Pattern

```
Floating-point values are serialized by preserving
their IEEE 754 bit representation exactly.

No normalization or canonicalization is performed.
```

Nghĩa là encoder ghi **đúng bit pattern** đang có, không sửa gì:

```
Infinity   → ghi nguyên bit
-0.0       → ghi nguyên bit, phân biệt với 0.0
NaN        → ghi nguyên bit
```

Điểm cần hiểu rõ về `NaN`:

```
CPU A

NaN

↓

0x7FC00001

CPU B

NaN

↓

0x7FC01234
```

Hai bit pattern khác nhau, cả hai đều là `NaN`. Nếu hai implementation cùng "giữ nguyên bit" thì byte sinh ra sẽ khác nhau.

Điều này **không vi phạm** protocol. Giá trị được serialize là **bit pattern IEEE 754**, không phải khái niệm logic "NaN". Cross-SDK Guarantee (§13) phát biểu trên cùng một bit pattern đầu vào, không phải trên cùng một "giá trị NaN".

Implementation MUST NOT thay `NaN` bằng một bit pattern canonical nào đó.

## 2.4 Bool

```
Encoder MUST only emit 0x00 or 0x01.
```

Không được ghi giá trị khác — kể cả những giá trị mà ngôn ngữ nguồn coi là truthy (`0xFF`, `0x02`, con trỏ khác null).

Decoder gặp byte khác `0x00` / `0x01` → byte stream không hợp lệ (§10). Không được coi "khác 0 nghĩa là true".

# 3. String

Một chuỗi được biểu diễn bằng:

```
UInt32 Length

↓

UTF-8 Bytes
```

`Length` là **số byte UTF-8**, không phải số ký tự.

```
ABC

↓

03 00 00 00

41 42 43
```

Vùng byte phải là UTF-8 hợp lệ.

---

# 4. Bytes

```
UInt32 Length

↓

Raw Bytes
```

Giống `String` nhưng không ràng buộc UTF-8.

---

# 5. Struct

Một Struct được biểu diễn bằng cách nối liên tiếp byte của từng field theo đúng thứ tự định nghĩa.

```
Player

Hp

↓

UInt32

Name

↓

String

↓

Bytes
```

Không metadata, không field ID, không padding giữa các field.

## 5.1 Field Ordering

```
Fields MUST be serialized in declaration order.

Memory layout,
compiler optimization,
padding,
alignment,
or runtime object layout
MUST NOT affect serialization order.
```

Thứ tự field là part của protocol. Đổi thứ tự field → đổi toàn bộ byte sequence.

Hệ quả cần nắm: thứ tự trên wire là thứ tự **khai báo**, không phải thứ tự trong bộ nhớ. Compiler được phép sắp xếp lại field trong RAM để giảm padding; điều đó MUST NOT làm đổi một byte nào của output.

```
Khai báo          Có thể nằm trong RAM      Wire
────────          ────────────────────      ────
a: u8             b (4 byte)                a
b: u32            a (1 byte)                b
c: u8             c (1 byte)                c
                  + padding                 (không padding)
```

Một implementation lấy thứ tự field từ layout bộ nhớ, từ thứ tự reflection, hay từ bất kỳ nguồn nào không phải thứ tự khai báo → là **bug của implementation**.

---

# 6. Array

```
UInt32 Count

↓

Element 1

↓

Element 2

↓

...
```

`Count` là **số phần tử**, không phải số byte. Mỗi phần tử được ghi theo đúng hình dạng byte của kiểu `T`.

---

# 7. Enum

```
UInt32 Value
```

```
Enums are always represented as UInt32.

This is a protocol design decision
rather than a storage optimization.
```

Không có `u8`, không có `u16`, không có `i32`, không có biến thể theo số lượng member. Mọi Enum, mọi kích thước, đều là đúng 4 byte Little Endian.

Lý do: spec nhỏ, compiler đơn giản, decode nhanh, không có gì để thương lượng giữa hai bên.

Giá trị không nằm trong tập đã định nghĩa → byte stream không hợp lệ. Không graceful degradation, không skip.

---

# 8. Encoder

Để tạo một Struct:

```
1. Ghi field thứ nhất.
2. Ghi field thứ hai ngay sau đó.
3. Không được chèn bất kỳ byte nào khác.
4. Byte cuối cùng chính là byte cuối của field cuối.
```

---

# 9. Decoder

Khi đọc một Struct:

```
1. Đọc field thứ nhất.
2. Di chuyển con trỏ đọc đúng số byte field đó sử dụng.
3. Tiếp tục field kế tiếp.
4. Lặp cho đến hết Struct.
```

Nếu số byte còn lại ít hơn số byte mà field yêu cầu, byte stream là không hợp lệ.

---

# 10. Byte Stream Không Hợp Lệ

| Lỗi | Điều kiện trên byte stream |
|-----|---------------------------|
| Unexpected EOF | Số byte còn lại nhỏ hơn số byte field yêu cầu |
| Invalid Bool | Byte của một `bool` không phải `0x00` hoặc `0x01` |
| Invalid Enum | Giá trị `u32` không nằm trong tập value đã định nghĩa |
| Invalid UTF-8 | Vùng byte của `String` không phải chuỗi UTF-8 hợp lệ |
| Length Overflow | Trường length/count lớn hơn số byte còn lại, hoặc vượt giới hạn cấu hình (§12) |

Cách một implementation báo lỗi — throw, return error, set flag, kéo chân GPIO — nằm ngoài Specification.

## 10.1 Length Overflow

```
Implementation MUST reject
length values that exceed
available remaining bytes.
```

Kiểm tra này phải xảy ra **trước khi cấp phát bộ nhớ**.

```
Length = 100

Packet còn 5 byte

↓

Error
```

Đây là ràng buộc **normative**: không phụ thuộc cấu hình, không phụ thuộc implementation. Một length không thể thoả mãn được bởi chính byte stream là byte stream không hợp lệ, luôn luôn.

Cùng tên lỗi nhưng khác bản chất với giới hạn cấu hình ở §12:

| Nguồn | Điều kiện | Tính chất |
|-------|-----------|-----------|
| Byte stream | `length > số byte còn lại` | **Normative** — mọi implementation MUST từ chối |
| Cấu hình | `length > MaxStringLength…` | Non-normative — tuỳ cấu hình từng bên |

Áp dụng đồng thời cả hai:

```
effective_limit = min(remaining_bytes, configured_limit)
```

# 11. Không Tồn Tại Trong Wire

```
✗ Padding          ✗ Alignment        ✗ Nullable / Option<T>
✗ Versioning       ✗ Compression      ✗ Checksum
✗ Field ID / tag   ✗ Object header    ✗ Default value
```

---

# 12. Giới Hạn — Non-normative

`u32` cho length/count cho phép tới 4GB. Một implementation cấp phát theo length chưa kiểm tra sẽ bị DoS.

Vì vậy implementation SHOULD có giới hạn cấu hình được (`MaxStringLength`, `MaxBytesLength`, `MaxArrayCount`, `MaxPacketSize`).

Giới hạn này **không phải part của protocol**. Hai peer cấu hình khác nhau MAY bất đồng về việc một byte stream có được chấp nhận hay không.

Giới hạn cấu hình là **phần thêm vào**, không thay thế kiểm tra normative ở §10.1. Không có cấu hình nào cho phép chấp nhận một `length` lớn hơn số byte còn lại.

---

# 13. Cross-SDK Guarantee

```
Mọi implementation v1 MUST sinh ra byte sequence giống hệt nhau
cho cùng một dữ liệu đầu vào.
```

Với float, "cùng dữ liệu đầu vào" nghĩa là **cùng bit pattern IEEE 754** (§2.3), không phải cùng giá trị toán học.

Nếu không, đó là bug của implementation, không phải của protocol.

# 14. Test Vector

Test vector là cặp **(giá trị, byte)**.

```
u32   100          → [64 00 00 00]
String "abc"       → [03 00 00 00 61 62 63]
Array<u32> [1,2,3] → [03 00 00 00 01 00 00 00 02 00 00 00 03 00 00 00]
bool  false / true → [00] / [01]
bool  [02]         → không hợp lệ
f32   3.14         → [C3 F5 48 40]
f32   Infinity     → [00 00 80 7F]
f32   -0.0         → [00 00 00 80]
enum  Status::OK   → [00 00 00 00]
enum  [63 00 00 00] khi tập value = {0,1} → không hợp lệ
String len=2 data=[FF FE] → không hợp lệ (UTF-8)
String len=[64 00 00 00] nhưng còn 5 byte → không hợp lệ (Length Overflow)

struct Item { id: u32; name: String }
Item{ id=42, name="Sword" } → [2A 00 00 00 05 00 00 00 53 77 6F 72 64]
```

Test vector cho float MUST viết theo **bit pattern**, không viết theo tên giá trị:

```
f32 bit pattern 0x7FC00000 → [00 00 C0 7F]
f32 bit pattern 0x7FC00001 → [01 00 C0 7F]
```

Cả hai đều là `NaN`. Viết `f32 NaN → [00 00 C0 7F]` là **sai** vì nó ngầm định một canonical NaN mà §2.3 không hề quy định. Một conformance suite so sánh trên "giá trị NaN" sẽ fail sai trên những platform sinh bit pattern khác.

# 15. Ví Dụ Hoàn Chỉnh

```
struct Vector3 { x: f32; y: f32; z: f32 }

struct GameMessage {
  playerId:   u32
  playerName: String
  position:   Vector3
  health:     u32
  isAlive:    bool
}
```

Giá trị:

```
playerId   = 42
playerName = "Knight"
position   = Vector3 { x = 10.5, y = 20.3, z = -5.1 }
health     = 100
isAlive    = true
```

Byte:

```
playerId   → [2A 00 00 00]
playerName → [06 00 00 00] [4B 6E 69 67 68 74]
position   → [00 00 28 41] [66 66 A2 41] [9A 99 A3 C0]
health     → [64 00 00 00]
isAlive    → [01]

[2A 00 00 00 06 00 00 00 4B 6E 69 67 68 74
 00 00 28 41 66 66 A2 41 9A 99 A3 C0
 64 00 00 00 01]
```

Đọc lại: đọc 4 byte → `playerId = 42`; đọc 4 byte length = 6, dịch con trỏ 6 byte → `playerName = "Knight"`; đọc 3 × 4 byte → `position`; đọc 4 byte → `health = 100`; đọc 1 byte → `isAlive = true`; con trỏ dừng đúng ở cuối stream.
