# RFC-0002 - Đặc tả Wire Format

## Trạng thái

Final

## Phiên bản

1.1.0

## Tác giả

Hà Duy Thắng

---

# 0. Đặc tả này là gì?

Đặc tả này trả lời đúng một câu hỏi:

> Làm thế nào để tạo hoặc đọc một mảng byte Fomoxa?

Đặc tả mô tả:

```
Cấu trúc của các byte.
```

Đặc tả KHÔNG mô tả:

```
API nào tạo ra các byte đó.
Việc dùng annotation.
Yêu cầu về sinh mã.
```

Vì vậy cùng một đặc tả có thể triển khai bằng:

```
Compiler sinh code
Reflection
Viết tay
FPGA
PLC
Vi điều khiển
Assembly
```

Miễn là hai phép chuyển đổi:

```
Dữ liệu logic  →  Byte
Byte  →  Dữ liệu logic
```

tuân thủ nghiêm ngặt các quy tắc dưới đây.

---

# 1. Các quy tắc

```
Luôn little-endian.
UInt32 luôn chiếm đúng 4 byte.
Enum luôn là UInt32.
Float ghi theo mẫu bit thô IEEE 754.
Model không chứa metadata.
Field ghi theo thứ tự khai báo, không theo bố cục bộ nhớ.
Không padding.
Không alignment.
Không tag ID.
Không object header.
Dữ liệu giống nhau → byte giống nhau.
```

# 2. Primitive

## 2.1 UInt32

Một `UInt32` chiếm đúng 4 byte little-endian.

```
Value

100

↓

Bytes

64 00 00 00
```

## 2.2 Bảng đầy đủ

| Kiểu | Hình dạng byte | Kích thước |
|------|----------------|-----------|
| `bool` | `0x00` = false, `0x01` = true, khác → không hợp lệ | 1 |
| `i8` / `u8` | 1 byte | 1 |
| `i16` / `u16` | 2 byte little-endian | 2 |
| `i32` / `u32` | 4 byte little-endian | 4 |
| `i64` / `u64` | 8 byte little-endian | 8 |
| `f32` | IEEE 754 single, little-endian, không normalize | 4 |
| `f64` | IEEE 754 double, little-endian, không normalize | 8 |

Không varint. Không variable-length encoding.

## 2.3 Float: mẫu bit

```
Float được serialize bằng cách giữ nguyên mẫu bit IEEE 754.

Không normalize. Không đưa về dạng canonical.
```

Encoder ghi đúng mẫu bit đang có, không sửa gì:

```
Infinity   → ghi nguyên bit
-0.0       → ghi nguyên bit, phân biệt với 0.0
NaN        → ghi nguyên bit
```

Trường hợp `NaN`:

```
CPU A

NaN

↓

0x7FC00001

CPU B

NaN

↓

0x7FC01234
```

Hai mẫu bit khác nhau, cả hai đều là `NaN`. Hai implementation giữ nguyên bit sẽ cho ra byte khác nhau.

Điều này không vi phạm giao thức. Thứ được serialize là mẫu bit IEEE 754, không phải khái niệm trừu tượng "NaN". Cam kết tương thích đa SDK (§13) áp dụng cho mẫu bit đầu vào, không áp dụng cho "giá trị NaN".

Implementation KHÔNG ĐƯỢC thay `NaN` bằng một mẫu bit chuẩn hoá.

## 2.4 Bool

```
Encoder CHỈ được phát ra 0x00 hoặc 0x01.
```

Encoder không ghi giá trị nào khác, kể cả những giá trị mà ngôn ngữ nguồn coi là "đúng" như `0xFF`, `0x02` hay con trỏ khác null.

Decoder gặp byte khác `0x00` và `0x01` thì luồng byte không hợp lệ (§10); decoder không áp dụng quy ước "khác 0 là đúng".

# 3. String

Một String được biểu diễn như sau:

```
Độ dài UInt32

↓

Số byte UTF-8
```

`Độ dài` là số byte UTF-8, không phải số ký tự.

```
ABC

↓

03 00 00 00

41 42 43
```

Chuỗi byte phải hợp lệ theo UTF-8.

---

# 4. Bytes

```
Độ dài UInt32

↓

Byte thô
```

Giống String nhưng không bị ràng buộc UTF-8.

# 5. Model

Model là một kiểu Fomoxa gồm một danh sách field có thứ tự. Mỗi field chứa một kiểu Fomoxa.

Specification không định nghĩa gì thêm về Model. Model ứng với khái niệm nào trong ngôn ngữ của bạn (`class`, `struct`, `record`, `data class`, `dict`, hay một nhóm biến rời) nằm ngoài phạm vi Specification. Hai ngôn ngữ dùng hai khái niệm khác nhau vẫn phải sinh ra cùng một chuỗi byte. Thứ được serialize là danh sách field có thứ tự, không phải cấu trúc ngôn ngữ chứa chúng.

Một Model được biểu diễn bằng cách ghép byte của từng field theo đúng thứ tự định nghĩa.

```
Player

Hp

↓

UInt32

Name

↓

String

↓

Bytes
```

Không metadata, không field ID, không padding giữa các field.

## 5.1 Thứ tự field

Field BẮT BUỘC được serialize theo thứ tự khai báo.

Thứ tự field là một phần của giao thức. Đổi thứ tự field là đổi toàn bộ chuỗi byte.

Thứ tự trên wire là thứ tự khai báo, không phải thứ tự trong bộ nhớ. Compiler được phép sắp xếp lại field trong RAM để bớt padding, nhưng việc đó KHÔNG ĐƯỢC làm đổi dù một byte đầu ra.

```
Khai báo          Bố cục RAM có thể có      Trên wire
───────────       ───────────────────       ─────────────────
a: u8             b (4 byte)                a
b: u32            a (1 byte)                b
c: u8             c (1 byte)                c
                  + padding                 (không padding)
```

Implementation nào xác định thứ tự field bằng bố cục bộ nhớ, thứ tự reflection hay bất kỳ nguồn nào ngoài thứ tự khai báo đều là lỗi implementation.

# 6. Array

```
UInt32 Count

↓

Element 1

↓

Element 2

↓

...
```

`Count` là số phần tử, không phải số byte. Mỗi phần tử ghi theo đúng định dạng byte của kiểu `T`.

---

# 7. Enum

```
Giá trị UInt32
```

```
Enum luôn là UInt32.

Đây là quyết định giao thức,
không phải tối ưu hoá lưu trữ.
```

Enum không được mã hoá thành `u8`, `u16` hay `i32`, và kích thước không co giãn theo số lượng thành viên. Mọi Enum, với mọi số lượng thành viên, chiếm đúng 4 byte little-endian.

Lý do: đặc tả nhỏ, compiler đơn giản, decode nhanh, không phải thương lượng giữa hai bên.

Giá trị nằm ngoài tập đã định nghĩa → luồng byte không hợp lệ. Decoder không xử lý suy giảm dần và không bỏ qua giá trị đó.

---

# 8. Encoder

Để ghi một Model:

```
1. Ghi field đầu tiên.

2. Ghi field thứ hai ngay sau đó.

3. Không chèn thêm byte nào khác.

4. Byte cuối cùng là byte cuối của field cuối.
```

---

# 9. Decoder

Khi đọc một Model:

```
1. Đọc field đầu tiên.
2. Đẩy con trỏ đúng số byte field đó chiếm.
3. Sang field tiếp theo.
4. Lặp cho tới hết Model.
```

Nếu số byte còn lại ít hơn số byte field cần, phải phân biệt vị trí con trỏ:

```
Con trỏ nằm giữa field (đã đọc một phần) và hết byte trước khi field đọc xong
→ Luồng byte không hợp lệ (EOF không mong đợi, §10)

Field trước đã đọc xong, con trỏ đứng đúng ranh giới field, và hết byte trước khi field tiếp theo đọc byte nào
→ Không phải lỗi. Xem chênh lệch phiên bản (§9.1)
```

Nếu mọi field của Model đã đọc xong mà luồng byte vẫn còn byte, phần dư cũng không phải lỗi. Xem §9.1.

## 9.1 Chênh lệch phiên bản

Model do người dùng định nghĩa, và định nghĩa đó đổi theo thời gian. Tại một thời điểm bất kỳ, Model bên ghi dùng và Model bên đọc dùng có thể khác nhau; trường hợp này gọi là chênh lệch phiên bản.

### Hai Model, vị thế ngang nhau

Fomoxa không nhúng thông tin phiên bản vào luồng byte (§11). "Cũ hơn" và "mới hơn" không phải thuộc tính đọc được từ byte. Với một cặp Model bất kỳ, nói bên này thêm một field ở cuối cũng đúng như nói bên kia bỏ một field ở cuối. Hai cách mô tả ứng với cùng một chuỗi byte và cùng một hành vi decode. Không phép kiểm tra nào phân biệt được chúng.

Chữ "phiên bản" ở đây chỉ nghĩa là đang tồn tại hai Model khác nhau và không hàm ý trình tự thời gian. Vì vậy mọi quy tắc trong phần này xây trên cặp (Model bên ghi, Model bên đọc), không xây trên thứ tự thời gian.

### Điều kiện hợp lệ

Chênh lệch phiên bản hợp lệ khi và chỉ khi:

```
Chuỗi kiểu của Model ngắn hơn là prefix chính xác
của chuỗi kiểu của Model dài hơn.

Gọi n là số field của Model ngắn hơn.
Tại mọi chỉ số từ 0 đến n-1, hai Model có cùng kiểu Fomoxa,
theo cùng thứ tự khai báo (§5.1).
Field bổ sung chỉ nằm ở phần cuối của Model dài hơn.
```

Ngoài điều kiện trên không có tiêu chí nào khác, và việc Model nào dài hơn không ảnh hưởng tới kết luận.

### Hai biểu hiện trên luồng byte

```
Thiếu byte ở cuối
──────────────────
Model bên ghi có ít field hơn Model bên đọc.
Luồng dữ liệu kết thúc đúng tại ranh giới field
→ các field còn lại của bên đọc không có dữ liệu.
```

```
Byte thừa ở cuối
────────────────
Model bên ghi có nhiều field hơn Model bên đọc.
Đọc hết các field bên đọc biết, luồng vẫn còn byte
→ byte thừa thuộc về những field bên đọc không có.
```

Cả hai trường hợp, decoder PHẢI coi đây là luồng byte hợp lệ.

Quy tắc dừng đọc:

```
1. Thiếu byte tại ranh giới field
→ dừng đọc Model tại đó; các field còn lại coi như không có.

2. Byte thừa sau field cuối mà Model biết
→ bỏ qua byte thừa, không đọc tiếp.
```

Cách implementation biểu diễn "field bị thiếu" (giá trị mặc định, `Option<T>`, ngoại lệ ở tầng ứng dụng) nằm ngoài Specification, giống như cách báo lỗi ở §10.

Model lồng trong field của Model khác áp dụng quy tắc này ở cấp của chính nó. Một Model con thiếu byte hoặc thừa byte tại ranh giới field của nó cũng là chênh lệch phiên bản, không phải lỗi.

### Khi nào KHÔNG phải chênh lệch phiên bản

Hai schema lệch nhau tại một chỉ số cụ thể thì điều kiện prefix không thoả:

```
Hai schema lệch nhau tại một chỉ số
→ field tại chỉ số đó khác nhau, vi phạm quy tắc thứ tự field ở §5.1
→ đây là thay đổi giao thức, không phải chênh lệch phiên bản,
và nằm ngoài phạm vi phần này.
```

Ví dụ với `Item { id: u32, name: String, hp: u16 }`:

| Model bên ghi | Model bên đọc | Prefix? | Kết luận |
|---|---|---|---|
| `{ id, name }` | `{ id, name, hp }` | có | chênh lệch phiên bản, hợp lệ |
| `{ id, name, hp }` | `{ id, name }` | có | chênh lệch phiên bản, hợp lệ |
| `{ id, name, hp }` | `{ id, hp }` - bỏ `name` ở giữa | không, lệch tại chỉ số 1 (`String` ↔ `u16`) | thay đổi giao thức |
| `{ id, name, hp }` | `{ id, lvl: u8, name, hp }` - chèn vào giữa | không, lệch tại chỉ số 1 (`String` ↔ `u8`) | thay đổi giao thức |
| `{ id, name, hp }` | `{ name, id, hp }` - đổi thứ tự | không, lệch tại chỉ số 0 (`u32` ↔ `String`) | thay đổi giao thức |

Hai hàng đầu là một cặp đọc/ghi hai chiều và cho cùng một kết luận, đúng như đã nêu: hướng thay đổi không ảnh hưởng tới biểu diễn trên wire.

### Phạm vi của phần này

Mô tả này chỉ áp dụng cho thứ tự và kiểu. Tên field và field ID không xuất hiện trên wire (§11); vị trí là yếu tố định danh duy nhất. Hai Model có cùng chuỗi kiểu nhưng field mang ý nghĩa khác nhau sẽ cho ra cùng bố cục byte, và §9.1 không phân biệt được chúng. Việc phát hiện và chặn các trường hợp đó thuộc về tầng schema cấp cao hơn, nơi có sẵn tên field và khai báo đầy đủ để so sánh, và nằm ngoài Specification.

# 10. Luồng byte không hợp lệ

| Lỗi | Điều kiện trên luồng byte |
|-----|---------------------------|
| EOF không mong đợi | Byte còn lại ít hơn byte field cần, và con trỏ đã đọc một phần field đó (thiếu byte tại ranh giới field không phải lỗi, xem §9.1) |
| Bool không hợp lệ | Byte của một `bool` không phải `0x00` hoặc `0x01` |
| Enum không hợp lệ | Giá trị `u32` nằm ngoài tập đã định nghĩa |
| UTF-8 không hợp lệ | Vùng byte của `String` không phải UTF-8 hợp lệ |
| Tràn độ dài | Trường độ dài/số lượng lớn hơn số byte còn lại, hoặc vượt giới hạn cấu hình (§12) |

Cách một implementation báo lỗi (ném ngoại lệ, trả về error, bật cờ, kéo chân GPIO) nằm ngoài Specification.

## 10.1 Tràn độ dài

```
Implementation PHẢI từ chối giá trị độ dài vượt quá số byte còn lại.
```

Phép kiểm tra này phải chạy trước khi cấp phát bộ nhớ.

```
Độ dài = 100

Còn lại 5 byte

↓

Lỗi
```

Ràng buộc này bắt buộc, không phụ thuộc cấu hình hay implementation. Một độ dài mà chính luồng byte không đáp ứng nổi luôn là luồng byte không hợp lệ.

Tên lỗi trùng nhau nhưng bản chất khác với giới hạn cấu hình ở §12:

| Nguồn | Điều kiện | Thuộc tính |
|-------|-----------|-----------|
| Luồng byte | `độ dài > số byte còn lại` | Bắt buộc. Mọi implementation PHẢI từ chối |
| Cấu hình | `độ dài > MaxStringLength…` | Không bắt buộc. Tuỳ cấu hình mỗi bên |

Áp dụng cả hai cùng lúc:

```
giới hạn hiệu quả = min(số byte còn lại, giới hạn đã cấu hình)
```

---

# 11. Không tồn tại trên wire

```
- Padding             - Alignment        - Nullable / Option<T>
- Version field/tag   - Compression      - Checksum
- Field ID / tag      - Object header    - Default value
```

Không version field và không version tag nào được ghi vào byte. Đây là phát biểu về hình dạng byte, không phải phát biểu về khả năng tương thích giữa hai phiên bản Model. Cách decoder xử lý chênh lệch giữa Model bên ghi và Model bên đọc nằm ở §9.1 và không mâu thuẫn với bảng trên.

---

# 12. Giới hạn (không mang tính quy phạm)

`u32` cho độ dài/số lượng cho phép tối đa 4GB. Một implementation cấp phát theo độ dài mà không kiểm tra sẽ bị tấn công DoS.

Vì vậy implementation NÊN có giới hạn cấu hình được: `MaxStringLength`, `MaxBytesLength`, `MaxArrayCount`, `MaxPacketSize`.

Các giới hạn này không thuộc giao thức. Hai đầu cuối cấu hình khác nhau CÓ THỂ bất đồng về việc có chấp nhận một luồng byte hay không.

Giới hạn cấu hình là phần bổ sung, không thay thế phép kiểm tra quy phạm ở §10.1. Không cấu hình nào cho phép chấp nhận độ dài lớn hơn số byte còn lại.

---

# 13. Đảm bảo tương thích đa SDK

```
Mọi implementation v1.1 PHẢI sinh ra byte giống hệt nhau cho cùng một dữ liệu đầu vào.
```

Với float, "cùng dữ liệu đầu vào" nghĩa là cùng mẫu bit IEEE 754 (§2.3), không phải cùng giá trị toán học.

Lệch nhau là lỗi implementation, không phải lỗi giao thức.

# 14. Test vector

Test vector là một cặp (giá trị, byte).

```
u32   100          → [64 00 00 00]
String "abc"       → [03 00 00 00 61 62 63]
Array<u32> [1,2,3] → [03 00 00 00 01 00 00 00 02 00 00 00 03 00 00 00]
bool  false / true → [00] / [01]
bool  [02]         → không hợp lệ
f32   3.14         → [C3 F5 48 40]
f32   Infinity     → [00 00 80 7F]
f32   -0.0         → [00 00 00 80]
enum  Status::OK   → [00 00 00 00]
enum  [63 00 00 00] khi tập value = {0,1} → không hợp lệ
String len=2 data=[FF FE] → không hợp lệ (UTF-8)
String len=[64 00 00 00] nhưng còn 5 byte → không hợp lệ (tràn độ dài)

model Item { id: u32; name: String }
Item{ id=42, name="Sword" } → [2A 00 00 00 05 00 00 00 53 77 6F 72 64]

model ItemV1 { id: u32 }
model ItemV2 { id: u32; name: String }

Ghi bởi ItemV1, đọc bằng ItemV2:
[2A 00 00 00] → id=42, hết byte đúng ranh giới trước name → hợp lệ, chênh lệch phiên bản (§9.1); name không có dữ liệu

Ghi bởi ItemV2, đọc bằng ItemV1:
[2A 00 00 00 05 00 00 00 53 77 6F 72 64] → id=42, dư 9 byte sau field id → hợp lệ, chênh lệch phiên bản (§9.1); phần dư bị bỏ qua

Ghi bởi ItemV2, đọc bằng ItemV2, byte bị cắt giữa field name:
[2A 00 00 00 05 00 00 00 53 77] → độ dài=5 nhưng chỉ còn 2 byte dữ liệu → không hợp lệ (EOF không mong đợi). KHÔNG phải chênh lệch phiên bản, vì hết byte giữa field chứ không phải tại ranh giới
```

Test vector cho float PHẢI ghi bằng mẫu bit, không ghi bằng tên giá trị:

```
mẫu bit f32 0x7FC00000 → [00 00 C0 7F]
mẫu bit f32 0x7FC00001 → [01 00 C0 7F]
```

Cả hai đều là `NaN`. Ghi `f32 NaN → [00 00 C0 7F]` là sai, vì nó ngụ ý một canonical NaN mà §2.3 không quy định. Một bộ conformance so sánh theo "giá trị NaN" sẽ báo lỗi sai trên các nền tảng sinh mẫu bit khác nhau.

# 15. Ví dụ hoàn chỉnh

```
model Vector3 { x: f32; y: f32; z: f32 }

model GameMessage {
    playerId:   u32
    playerName: String
    position:   Vector3
    health:     u32
    isAlive:    bool
}
```

Giá trị:

```
    playerId   = 42
    playerName = "Knight"
    position   = Vector3 { x = 10.5, y = 20.3, z = -5.1 }
    health     = 100
    isAlive    = true
```

Byte:

```
    playerId   → [2A 00 00 00]
    playerName → [06 00 00 00] [4B 6E 69 67 68 74]
    position   → [00 00 28 41] [66 66 A2 41] [33 33 A3 C0]
    health     → [64 00 00 00]
    isAlive    → [01]

    [2A 00 00 00 06 00 00 00 4B 6E 69 67 68 74
    00 00 28 41 66 66 A2 41 33 33 A3 C0
    64 00 00 00 01]
```

Đọc lại: đọc 4 byte → `playerId = 42`. Đọc 4 byte (độ dài = 6), đẩy con trỏ qua 6 byte → `playerName = "Knight"`. Đọc 3 × 4 byte → `position`. Đọc 4 byte → `health = 100`. Đọc 1 byte → `isAlive = true`. Con trỏ dừng đúng tại điểm kết thúc luồng.
