# RFC-0001 - Fomoxa là gì?

## Trạng thái

Final

## Phiên bản

1.1.0

## Tác giả

Hà Duy Thắng

---

# 1. Tóm tắt trong một câu

> Fomoxa là đặc tả binary wire format. Nó quy định cách biểu diễn dữ liệu thành byte. Cùng một dữ liệu luôn cho ra đúng một chuỗi byte, trên mọi ngôn ngữ, mọi runtime, mọi implementation.

Fomoxa định nghĩa một giao thức, không phải một implementation.

---

# 2. Fomoxa không phải là gì

Fomoxa không phải là:

```
- Networking Framework      - RPC Framework
- Game Engine               - Transport Protocol
- Serialization Library     - SDK độc quyền
```

Fomoxa không xử lý:

```
- TCP / UDP / QUIC      - Retransmission     - Packet ordering
- Matchmaking           - Prediction         - Replication logic
- Encryption            - Compression        - Checksum
```

Các thành phần đó nằm trên Fomoxa. Fomoxa chỉ trả lời một câu hỏi:

```
Dữ liệu phải tuân theo định dạng byte nào?
```

---

# 3. Vấn đề Fomoxa giải quyết

## 3.1 Kịch bản thực tế

Một hệ thống thực tế thường gồm:

```
server        Go
client        C# / Unity
Tool          Rust
Analytics     Python
Thiết bị      C trên vi điều khiển
```

Cả năm thành phần cùng hiểu một `Player`. Trong nhiều tình huống, chúng còn phải sinh ra byte giống hệt nhau.

## 3.2 Vì sao "byte giống hệt nhau" lại khó?

Mỗi ngôn ngữ có logic nội bộ riêng, và logic đó ảnh hưởng trực tiếp tới cách biểu diễn dữ liệu:

| Nguồn khác biệt | Ví dụ |
|----------------------|---------|
| Bố cục bộ nhớ | Compiler sắp xếp lại field để bớt padding |
| Alignment | `struct { u8; u32; u8 }` chiếm 12 byte trong RAM, không phải 6 |
| Endianness | Big-endian trên một số kiến trúc |
| Độ dài String | C#/Java đếm ký tự; Go/Rust đếm byte |
| Kích thước Enum | `int` là 4 byte ở đây, 8 byte ở chỗ khác |
| Float | Chuẩn hoá `NaN`, gộp `-0.0` vào `0.0` |

Mỗi khác biệt sinh ra một luồng byte khác. Rủi ro lớn nhất là:

```
schema sai thường KHÔNG báo lỗi.

Nó âm thầm sinh ra dữ liệu sai.
```

## 3.3 Vì sao các format phổ biến không giải quyết được

| Format | Vấn đề với yêu cầu "dữ liệu giống nhau → byte giống nhau" |
|-----------|-----------------------------------------------------------|
| JSON | Dựa trên văn bản; thứ tự khoá không xác định; cách in số thực thay đổi theo implementation; kích thước lớn |
| Protobuf | Tài liệu chính thức nêu rõ: quá trình serialize không đảm bảo canonical form. Thứ tự map, unknown field và khác biệt phiên bản đều làm đổi byte |
| MessagePack | Một số nguyên có nhiều cách biểu diễn hợp lệ (`int8`, `int16`, `int32`...) → nhiều luồng byte cho cùng một giá trị |
| Dựa trên reflection (`BinaryFormatter`, `pickle`...) | Phụ thuộc runtime và phiên bản; không chạy chéo ngôn ngữ |

Các format này được thiết kế cho tính linh hoạt, tức là cho phép nhiều cách hợp lệ để mã hoá cùng một dữ liệu. Với các bài toán ở §5.1, việc có nhiều cách hợp lệ chính là nguyên nhân gây lỗi.

## 3.4 Tóm tắt vấn đề

```
Với cùng một schema
và cùng một giá trị logic,

Model  →  Encode  →  Bytes
Bytes  →  Decode  →  Model

phải cho kết quả giống hệt nhau
trên mọi implementation tuân thủ.
```

Fomoxa chỉ đảm bảo điều trên.

# 4. Cách Fomoxa giải quyết

Fomoxa loại bỏ lựa chọn của encoder, vì mỗi chỗ còn lựa chọn là một chỗ hai implementation có thể làm khác nhau.

## 4.1 Năm quyết định thiết kế

### Không metadata trong wire

```
- Field name    - Type info    - Tag ID
- Object header - Padding      - Alignment
```

Luồng byte không tự mô tả mà chỉ chứa dữ liệu thô. Encoder và decoder đều biết trước schema.

### Vị trí là định danh duy nhất

Không có field ID. Decoder nhận diện field bằng thứ tự khai báo, không bằng bố cục bộ nhớ.

### Kích thước cố định, không varint

Một `UInt32` luôn chiếm 4 byte, kể cả khi giá trị bằng 0. Đổi lại, mỗi giá trị ứng với đúng một cách biểu diễn và không có dạng mã hoá ngắn hơn.

### Không Optional, không giá trị mặc định

Mọi field đều có giá trị và không field nào vắng mặt, nên không cần quy định cách mã hoá sự vắng mặt.

### Schema là nguồn sự thật duy nhất, chốt out-of-band

Luồng byte không mang schema theo. Schema phải giống hệt nhau ở hai đầu và được chốt trước khi trao đổi dữ liệu, bằng bất kỳ cách nào miễn không gửi kèm dữ liệu.

Quy định này là hệ quả trực tiếp của "không metadata trong wire", không phải một yêu cầu riêng.

## 4.2 Cái giá phải trả

Mỗi quyết định trên đều có giá:

| Lợi ích | Đánh đổi |
|------|-----|
| Byte mang tính tất định | schema chỉ được tiến hoá bằng thêm/xoá field ở cuối Model (RFC-0002 §9.1) |
| Wire format gọn, decode nhanh | Chèn/xoá field ở giữa, đổi thứ tự field, đổi kiểu field có sẵn = breaking change |
| Không phải parse metadata | Luồng byte không tự mô tả; lệch schema → dữ liệu hỏng ngầm |
| Không mơ hồ | Không Optional, không Nullable, không giá trị mặc định |
| schema chốt từ đầu, hai bên đều biết | Sửa field ở giữa Model vẫn buộc hai phía deploy đồng bộ. Chỉ thêm/xoá ở cuối mới chịu được lệch phiên bản tạm thời |

§5.3 liệt kê các trường hợp mà những đánh đổi này khiến Fomoxa không phù hợp.

---

# 5. Tại sao chọn Fomoxa

## 5.1 Khi tính tất định là bắt buộc

Có một nhóm bài toán mà "dữ liệu giống nhau → byte giống nhau" là điều kiện pass/fail:

| Trường hợp sử dụng | Lý do cần byte tất định |
|----------|------------------------------------|
| Ký / hash payload | Chữ ký bám vào byte. Byte đổi thì chữ ký hỏng, dù dữ liệu logic không đổi |
| Replay / lockstep | Hai máy phải đạt cùng một trạng thái từ cùng chuỗi đầu vào |
| Content-addressed / dedupe | Nội dung giống nhau phải ra cùng hash. Không thì cache và dedupe vô nghĩa |
| Kiểm thử chéo giữa các SDK | So byte là cách duy nhất để biết hai SDK có thật sự khớp nhau |
| Binary audit log | Bản ghi phải tái tạo lại được chính xác tuyệt đối |

Với nhóm này, một format decode đúng nhưng encode không tất định thì không dùng được.

Có hai loại "giống nhau":

```
Data equivalence    decode(bytes_A) == decode(bytes_B)     ← đủ cho hầu hết ứng dụng
Byte equivalence    bytes_A == bytes_B                     ← §5.1 yêu cầu cái này
```

Hầu hết format chỉ đảm bảo loại đầu, vì chúng cho phép nhiều chuỗi byte hợp lệ cùng biểu diễn một giá trị (§3.3). Trên thực tế hai lần encode *thường* ra byte giống nhau, cho tới khi đổi phiên bản thư viện, đổi ngôn ngữ, hoặc một `HashMap` duyệt theo thứ tự khác.

Hậu quả của việc chỉ "thường" giống nhau khác nhau theo loại ứng dụng:

```
Ứng dụng thường     Lệch byte → không ai phát hiện, vì decode vẫn ra dữ liệu đúng
Bài toán §5.1       Lệch byte → chữ ký hỏng, cache-miss khi hash, replay làm sai world-state
```

Lỗi này không lộ ra khi test mà lộ ra khi hai đầu chạy hai phiên bản khác nhau trên production. Với nhóm bài toán này, một format đúng 99,9% vẫn là format hỏng, chỉ là lỗi khó phát hiện hơn.

## 5.2 Khi băng thông và CPU bị giới hạn

```
Game networking      IoT / embedded      Real-time streaming
```

Wire format không có metadata, tag hay varint cần giải mã nên có kích thước nhỏ. Cấu trúc byte đủ đơn giản để implementation ánh xạ thẳng byte sang model, không cần tra cứu lúc chạy.

## 5.3 Khi nào KHÔNG chọn Fomoxa

| Tình huống | Lý do không hợp |
|-----------|------------------|
| API công khai cho bên thứ ba phát triển độc lập | v1.1 chỉ hỗ trợ thêm/bớt field ở cuối Model (RFC-0002 §9.1). Bên thứ ba chèn field vào giữa, đổi thứ tự hoặc đổi kiểu field có sẵn đều là breaking change mà Fomoxa không đỡ được |
| Cần chạy song song lâu dài client cũ với server mới, khi thay đổi nằm ở giữa Model | Cơ chế chịu lệch phiên bản (RFC-0002 §9.1) chỉ bao gồm thêm/bớt field ở cuối. Không có unknown-field skipping cho field chèn giữa, cũng không có giá trị mặc định |
| Model có nhiều field "optional" | v1.1 không có `Optional` / `Nullable` |
| schema đổi hàng tuần, không chỉ ở cuối Model | Mọi thay đổi đều buộc hai phía deploy đồng bộ |

Trong các trường hợp này, nên chọn format có tag ID và optional field.

# 6. Các khả năng của Fomoxa

Mục này mô tả hai loại khả năng, phân biệt theo nhãn sau:

```
§6.1  §6.2  §6.5      Thuộc Specification - có trong mọi implementation tuân thủ
§6.3  §6.4  §6.6      Thuộc Reference Implementation - wire format cho phép, nhưng không bắt buộc
```

## 6.1 Tính tất định ở cấp byte

```
Go SDK      encode Player{hp=100, name="Alice"}  →  chuỗi byte A
C# SDK      encode Player{hp=100, name="Alice"}  →  chuỗi byte A
Rust SDK    encode Player{hp=100, name="Alice"}  →  chuỗi byte A
```

Ba chuỗi byte giống hệt nhau tới byte cuối cùng. Lệch nhau là lỗi implementation, không phải tính năng của giao thức, và phát hiện được bằng một phép so mảng byte.

Mọi trường hợp sử dụng ở §5.1 (hash, chữ ký, replay protection, dedupe và conformance test) đều dựa trên tính chất này.

## 6.2 Wire format nhỏ gọn

Một `Player` đầy đủ (Model lồng nhau, String, Enum, bool, Array của Model):

```
Fomoxa    49 byte
JSON      ~140 byte cho cùng dữ liệu
```

Kích thước chênh gần 3 lần. Khoảng cách này không đến từ nén mà từ việc bỏ mọi phần không phải dữ liệu: tên field, dấu ngoặc, dấu phẩy, tag.

Kích thước cũng đoán trước được: nó được tính bằng phép cộng và không phụ thuộc nội dung.

## 6.3 Cho phép implementation không cần reflection

Specification không yêu cầu điều này, vì nó không quy định cơ chế triển khai (§6.5). Tuy nhiên wire format không chứa metadata, tag hay chỉ báo độ dài biến đổi, nên mọi quyết định encode/decode đều xác định được từ schema và không còn điểm mơ hồ nào lúc chạy.

Một implementation có thể chọn hướng sau:

```
Thời điểm build             Thời điểm chạy
──────────────────          ──────────────────
Đọc schema                  Ghi byte
Sinh codec                  Đọc byte
Kiểm tra hợp lệ             (hết)
```

Reference Implementation (RI) đi theo hướng này và thu được:

- Chạy được trên môi trường AOT: IL2CPP, console (Unity), mobile, hệ nhúng.
- Không cấp phát bộ nhớ cho việc phân tích kiểu lúc chạy.
- Không tra bảng metadata trên hot path.
- Không có "slow start" do khởi tạo reflection.

Một implementation dùng reflection vẫn hợp lệ nhưng không có các lợi ích trên. Byte sinh ra vẫn phải giống hệt.

## 6.4 Bắt lỗi ngay tại build time

Specification quy định những gì làm schema không hợp lệ (giá trị enum âm, tên trùng, đệ quy vô hạn, ràng buộc sai). *Thời điểm* bắt lỗi do từng implementation tự quyết.

RI từ chối schema không hợp lệ ngay khi định nghĩa schema, thay vì đẩy phép kiểm tra sang lúc chạy, để lỗi không lọt lên production.

## 6.5 Implementation thay thế được cho nhau

Specification chỉ mô tả bố cục byte. Nó không ép API, cơ chế sinh mã hay annotation, và có thể được triển khai bằng:

```
Compiler sinh code    Reflection    Viết tay
FPGA                  PLC           Assembly
```

Phép thử quyết định: *Có thể viết một encoder bằng assembly trên vi điều khiển 8-bit tuân thủ quy định này không?* Nếu không, quy định đó không thuộc về Specification.

Tiêu chuẩn là Specification, không phải Reference Implementation. Có thể thay toàn bộ phần triển khai mà wire format không đổi.

## 6.6 Kiểu dữ liệu của bạn vẫn là của bạn

Cần phân biệt hai khái niệm:

```
Model (RFC-0002 §5)   một kiểu Fomoxa: danh sách field có thứ tự
Kiểu của bạn          một class / struct / record trong ngôn ngữ của bạn
```

Specification định nghĩa khái niệm thứ nhất và không nói gì về khái niệm thứ hai. Từ luồng byte không thể biết phía bên kia dùng class, struct, DTO hay một mảng số thô; chỉ cần danh sách field có thứ tự khớp nhau.

*Phần dưới nói về Reference Implementation (RI).* Nó mô tả cách RI chọn rút dữ liệu, không phải yêu cầu tuân thủ.

RI không yêu cầu viết một lớp DTO song song để truyền qua mạng, không đòi kế thừa lớp cơ sở hay implement interface. Nó dựng Model từ kiểu có sẵn và chỉ rút các field được đánh dấu là network field. Phần còn lại (logic, phương thức, field nội bộ) bị bỏ qua.

Điều kiện duy nhất Specification đặt ra: thứ tự các network field khi ánh xạ vào schema phải khớp thứ tự khai báo trong schema đó (§4.1). Cách rút chúng ra do implementation quyết định.

# 7. Vị trí của Fomoxa

```
        Application
        (game logic, RPC, replication, prediction)
              ↑
        ┌────────────┐
        │   FOMOXA   │   Model ↔ Bytes
        └────────────┘
              ↑
        Transport
        (TCP / UDP / QUIC / serial / file)
```

Fomoxa không phụ thuộc lớp trên hay lớp dưới. Nó nằm tại chỗ dữ liệu đổi hình dạng.

# 8. Triết lý

Có hai bộ nguyên tắc, áp dụng ở hai lớp khác nhau và không được trộn lẫn.

## 8.1 Nguyên tắc của Specification

Đây là yêu cầu tuân thủ. Hệ thống vi phạm bất kỳ điểm nào thì không phải Fomoxa.

```
Specification First               Đặc tả là nguồn sự thật duy nhất
Protocol over Framework           Định nghĩa byte, không định nghĩa API
Minimal Wire Format               Chỉ gửi dữ liệu, không gửi mô tả dữ liệu
Deterministic by Design           Một dữ liệu = đúng một chuỗi byte
Language Neutral                  Không ngôn ngữ nào là ngôn ngữ chính
Implementation Independent        Không ép parser, macro hay bộ sinh mã cụ thể
Implementation Replaceable        Reference Implementation không phải tiêu chuẩn
```

## 8.2 Nguyên tắc của Reference Implementation

Đây là lựa chọn thiết kế, không phải yêu cầu tuân thủ. Implementation khác có thể làm khác, miễn byte đầu ra không đổi.

```
User Owns the Model          Không bắt viết lại model
Compile-time over Runtime    Xác định được lúc build thì làm lúc build
Zero Runtime Reflection      Lúc chạy chỉ đọc và ghi byte
```

## 8.3 Quy tắc ra quyết định

Với mọi thay đổi trong tương lai, hỏi hai câu theo thứ tự:

> 1. Đặc điểm này có quan sát được từ luồng byte không?
>
> Không → nó thuộc §8.2. Không đưa vào Specification.
>
> 2. Thay đổi này có vi phạm nguyên tắc nào ở §8.1 không?
>
> Có → nó không thuộc về Fomoxa.

Phép thử cụ thể cho câu 1 là phép thử ở §6.5: *Một người viết encoder bằng assembly trên vi điều khiển 8-bit có tuân thủ được đặc điểm này không?*
